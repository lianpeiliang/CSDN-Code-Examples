先把一个接收模块拆成下面几段：

```text
计划产生负载
  → 实际生成报文
  → 发送 API 成功接受
  → 网络与接收系统投递
  → 应用成功读取
  → 入队与等待
  → 解析、校验
  → 业务接受
  → 界面消费与显示
```

每个箭头都可能带来等待、拒绝或丢弃。“吞吐量”“丢失率”“延迟”都要写清它测的是哪一段。

全文统一使用三个层次的结果：

| 名称 | 在哪里计数 | 不应混淆 |
| --- | --- | --- |
| 发送成功数 | 发送 API 成功接受报文时 | 不代表报文已到达对端 |
| 读取数 | 接收 API 成功取出数据报时，业务过滤之前 | 不代表协议正确或业务已处理 |
| 业务接受数 | 完成要求的解析、校验及业务提交时 | 不自动代表已经显示、落盘或得到远端确认 |

要定位“哪一层丢了”，可配合阅读 [网络通信分层排障-20题学习讲解](./网络通信分层排障-20题学习讲解.md)。本文重点放在测量设计和结果判读。

## 第一部分：测试与指标基础

### 1. 测试和性能测试分别要回答什么问题？

**功能测试**回答“结果对不对”。例如发一条格式正确的 UDP 报文，接收端是否解析出预期字段。

**性能测试**回答“在规定负载和环境下，系统能否以可接受的速度和资源消耗完成工作”。例如每秒输入 5,000 条报文时，接收模块能否处理，延迟和丢失是否满足要求。

**稳定性测试**回答“持续运行或经历异常后，系统能否继续正确工作”。它会关注长时间运行、内存增长、句柄泄漏、偶发卡死、重连恢复等情况。

功能正确不代表性能达标：程序可能每条都处理正确，但处理速度只有输入速度的一半，队列会不断增长。性能很高也不代表功能正确：程序可能快速地把错误数据处理完。

**用同一个接收模块理解三种测试：**

| 类型 | 一个具体问题 | 主要证据 |
| --- | --- | --- |
| 功能测试 | 输入已知字节后，解析出的序号、温度和单位是否正确？ | 与独立期望结果逐项比较 |
| 性能测试 | 每秒 5,000 条输入时，处理延迟和未完成率是否达标？ | 实际输入、完成量、分位数和队列趋势 |
| 稳定性测试 | 持续运行 8 小时或经历停发恢复后，是否仍能正常处理？ | 长期指标、错误、资源趋势和恢复过程 |

长时间测试也可以同时测性能和功能，三种目标并不互斥。还应把故障恢复纳入实际需求：短暂断网、设备重启、无效报文之后能否继续运行，与“正常路径算对了”是不同问题。

**答题要点：**说明不同测试回答不同问题；真实验收通常需要同时验证正确性、性能和稳定性。

### 2. 常见性能指标各代表什么？

- **吞吐量：**单位时间内完成的工作量，可以是报文/秒、字节/秒或任务/秒。
- **延迟：**一项工作从起点到终点花费的时间，例如从报文生成到解析完成。
- **丢包率：**预期发送的唯一报文中，没有在规定接收点观察到的比例。必须明确发送数和接收数的统计口径。
- **CPU 使用率：**处理工作消耗的处理器资源；高 CPU 可能是计算量大，也可能与忙等、频繁拷贝等有关。
- **内存占用：**程序使用的内存量及其随时间的变化；持续上涨可能说明积压或泄漏。
- **队列长度：**尚未处理的工作量。队列长期增长通常说明生产速度高于消费速度。

评估 UDP 接收模块，通常先看**接收吞吐量、丢包率、延迟分布**；CPU、内存和队列长度用来解释为什么达不到目标。若接收端还要实时显示，界面响应也可能是重要指标。

**把指标写成能测的形式：**

| 指标 | 示例定义 | 必须带上的条件 |
| --- | --- | --- |
| 实际输入速率 | 测量窗口内成功提交发送 API 的报文数 / 实测秒数 | 生成计划、实际速率、负载大小、突发形态 |
| 业务吞吐量 | 窗口内首次业务接受的报文数 / 实测秒数 | 是否去重、是否包含预热和排空 |
| 本地处理延迟 | `业务接受时刻 - 成功读取时刻` | 时钟、计时位置、样本覆盖范围 |
| 应用接收缺失率 | 成功发送集合中，在截止前未被读取的唯一报文比例 | 会话与序号、截止规则，详见第 10 题 |
| CPU | 指定进程或线程的 CPU 时间占用 | 按单核还是整机归一化、采样窗口 |
| 内存 | 工作集、私有提交量、队列占用等分别记录 | 指标名和单位，不能只写“内存” |

如果只能先选三个，我会选：**业务接受吞吐量、到应用读取点的唯一报文缺失率、从读取到业务接受的延迟分布**。它们分别回答“处理多少”“到没到”“到达后多久完成”。这个本地延迟不含读取之前的网络与 Socket 排队；业务关心端到端时还要扩展计时范围。

另外要同时核对实际输入是否达标：配置 5,000 条/秒而实际只发了 2,000 条/秒，即使接收看起来很轻松，也没有完成原定负载测试。

**答题要点：**指标要与目标对应；不要把“CPU 低”单独等同于“性能好”。

### 3. 平均值为什么可能掩盖问题？

假设 99 条报文延迟约为 1 ms，另 1 条延迟为 500 ms。平均值约为 6 ms，但用户仍可能明显感到某条数据卡顿。平均值会把少数严重慢样本稀释掉。

延迟通常一起报告：

- **中位数（P50）：**一半样本不超过此值，描述典型体验。
- **P90、P95、P99：**描述较慢的一部分样本；P99 表示约 99% 样本不超过该延迟。
- **最大值：**帮助发现极端卡顿，但容易受偶发系统事件影响，不能单独代表常态。

样本量也要写清楚。只有几十条样本时，P99 的解释力很弱；长尾评估需要足够多、且采样方式合理的样本。

**动手算一次分位数。**先把 `N` 个样本从小到大排列。本文练习使用 nearest-rank 方法：`Pq = 第 ceil(q × N) 个样本`，下标从 1 开始。统计软件有不同的插值约定，小样本时尤其应注明方法。

对于上面的 100 个样本，平均值为 `(99 × 1 + 500) / 100 = 5.99 ms`；按本文方法，P99 取第 99 个样本，仍是 `1 ms`，最大值却是 `500 ms`。所以 **P99 也可能掩盖最慢的不足或等于 1% 的那部分体验**，可以同时报告超时条数和最大值。

还有两个很容易误判的地方：

- **只统计成功处理的样本。**若 10% 的报文根本没完成，剩下 90% 的 P99 很低，不能据此说整体响应好。缺失、超时和迟到要单列，不能当作 0 ms，也不能悄悄删除。
- **平均各轮的 P99。**两轮 P99 的平均数通常不是所有样本合起来的 P99。要报告各轮结果；需要整体分位数时，合并原始样本或兼容的直方图后重新计算。把“每秒 P99”再平均也有同样问题。

**推荐的报告句式：**“在 99,000 条已完成样本上，本地处理延迟 P50/P95/P99 为……；本轮预期 100,000 条，截止时未完成 1,000 条；超过 10 ms 的已完成样本有……条。”

**答题要点：**平均值回答“总体均值是多少”，分位数回答“慢的那部分有多慢”；按体验和风险选指标。

### 4. 怎样定义一个明确的性能目标？

“要快”没有测量终点；“少丢包”没有规定负载，也没有说明允许丢多少、测多久。一个可判定的目标要写明：

1. **负载：**报文大小、输入速率、突发模式、发送时长。
2. **测量范围：**从哪里开始计时，到哪个处理阶段算完成。
3. **阈值：**吞吐量、丢包率、延迟分位数，以及资源限制。
4. **环境：**机器、网卡、操作系统、构建配置等。

**一个更完整的目标示例：**在约定的两台电脑、有线网络和 Release 构建下，预热后正式输入 256 字节 UDP 负载，每秒 5,000 条，持续 10 分钟。每 1 秒核对实际成功发送数，允许偏差先约定为目标的 ±1%；发送器达不到要求时，该轮标记为负载未满足，不用于宣称目标性能通过。

对正式发送集合，在发送结束后等待约定的 2 秒排空期：应用接收缺失率不高于 0.01%；已读取合法报文的格式/解析错误为 0；应用队列主动丢弃为 0。本地“成功读取到业务接受”延迟 P99 不高于 10 ms，同时单列未完成、超过 10 ms 和排空期才完成的条数。队列容量示例设为 20,000 条，要求不溢出并记录高水位；后半程没有持续积压趋势。这里的数字只示范目标写法，不是通用标准。

如果业务真正要求“生成到业务接受”端到端 P99，必须把网络和读取前等待包括进去，并先说明跨机时钟误差控制方法，不能用本地处理延迟代替。

“内存不持续增长”也应具体化：选择工作集或私有提交量，约定预热后的基准、上限和观察窗口，再结合队列、活跃对象与停止输入后的恢复情况判断。一次系统缓存扩张不必然是泄漏。

**常见误区：**把“成功解析数少”全部命名为“网络丢包”。接收没读到、读到了却格式错、排队后主动丢弃，原因和修复办法都不同。

**答题要点：**别人能照着条件执行，并能明确判断通过或未通过。

### 5. 吞吐量和有效吞吐量有什么区别？

报文/秒描述处理了多少条消息；有效载荷字节/秒描述业务数据量。还要约定“有效”指什么：是完整 UDP 负载，还是其中真正的业务字段？假设两种测试都是 1,000 条/秒：

- 每条 64 字节有效载荷：64,000 B/s，即 64 kB/s；
- 每条 1,400 字节有效载荷：1,400,000 B/s，即 1.4 MB/s。

只比较报文/秒会把这两种完全不同的数据负荷看成一样。还要区分**应用有效载荷速率**与**线上总流量**：IP、UDP、链路层头部也会占带宽，包间隔和协议开销也会影响实际链路使用。

例如每条 UDP 负载 256 字节，其中 24 字节是应用报头，232 字节是业务内容；每秒首次接受 5,000 条：

```text
报文吞吐量       = 5,000 条/秒
UDP 负载吞吐量   = 5,000 × 256 = 1,280,000 B/s
业务有效吞吐量   = 5,000 × 232 = 1,160,000 B/s
UDP 负载比特率   = 1,280,000 × 8 = 10.24 Mbit/s
```

这些数都不等于完整线上带宽。无效、重复、重传和协议头是否计入，决定了指标代表哪一层。小报文可能更受每包处理开销限制，大报文可能更受带宽、拷贝或分片影响。

单位也要统一：`B` 是字节，`bit` 是位；`MB = 1,000,000 B`，`MiB = 1,048,576 B`。不把 Mbit/s 与 MB/s 直接当成同一个数比较。
**答题要点：**报告时写单位、报文大小和统计层级；不要把 payload 带宽说成网卡线上带宽。

## 第二部分：测量方法与测试设计

### 6. 如何保证性能测试可以重复？

性能数据只有在条件清楚时才可比较。至少记录：CPU、内存、操作系统版本、网卡和驱动、网络拓扑、程序提交版本、编译器及优化配置、测试参数、后台负载、温度或电源模式（能取得时）。

后台更新、杀毒扫描、其他网络流量和省电模式都可能改变结果。测试还要确保使用同一份程序、同一报文生成方式、同一接收机器和相同运行条件。若环境无法完全固定，就把差异记录下来，并多次重复测试。

**一份可以照填的环境记录：**

```text
test_id / 日期 / 操作者：
程序提交号 / 未提交改动 / 配置文件摘要：
发送机与接收机：CPU、逻辑核数、内存、系统版本
Qt / DDS 实现及版本 / 编译器 / 架构：
构建：Release 或 Debug、优化、断言、分析/检测工具
网络：网卡与驱动、接口、IP/前缀、MTU、链路与交换设备
应用：绑定、系统接收缓冲、应用队列容量、日志级别、UI 刷新策略
负载：生成器版本、数据集/随机种子、报文大小、速率与突发
电源/温度/后台任务/抓包与分析器状态：
```

Debug 与 Release 的结果分开报告；也不要把开了重型检测工具的结果，直接拿来代表生产构建。输入内容要固定或可重建，因为全零数据、真实字段和随机数据可能走不同解析路径。

为降低噪声可控制后台任务和供电模式，但必须保留产品真实需要的工作。生产环境要求写审计日志，就应测包括它的正式配置；关闭它的实验只用于分析开销。

**答题要点：**可复现不等于每次数字完全相同，而是条件可追溯、波动可估计、结论能重复。

### 7. 预热、运行时长和重复次数有什么影响？

程序刚启动时，内存页、缓存、分配器、连接初始化和系统频率状态可能与稳定运行阶段不同。先预热，再开始正式计量，可以避免把启动阶段混入稳定态数据。C++ 程序没有 JIT 编译，也仍可能有预热效应。

测试过短会漏掉队列持续增长、内存泄漏、周期性任务、温度降频等问题。测试多轮可以发现环境波动；报告中可给出每轮结果及中位数、范围或分位数，不要只挑最好的一轮。

时长和轮数取决于问题：微基准可短一些但要多次重复；稳定性测试通常需要更长时间。正式计时前后应明确如何处理预热期和排空期。

**把一轮测试分成四个明确阶段：**

```text
初始化/匹配 → 预热 → 正式输入 [t_start, t_stop) → 停发并等待排空 → 截止结算
```

例如预热 30 秒、正式 600 秒、排空 2 秒、重复 5 轮，只是便于起步的教学安排，不是适用于所有项目的固定标准。冷启动时间本身若是需求，应单独测量并报告，不能通过预热把它从验收中消失。

**要区分两种统计：**

- **窗口吞吐量：**在正式计量的 600 秒内完成多少条，就除以实测的这 600 秒；另外记录窗口起止的在途量。
- **正式发送队列的最终完成率：**只看正式阶段发送的那批唯一序号，在排空截止前最终完成多少。它允许完成发生在正式输入结束之后。

不要把排空期间补完成的数量全部加到窗口吞吐量分子，却只用正式输入时间做分母，并宣称这是稳定处理能力。预热报文如果延后完成，也不能混进正式发送批次；报文中标记阶段/轮次比简单清零计数器更可靠。

多轮结果按轮保留。三轮正常、两轮明显卡顿是重要现象，不应只汇报五轮平均。删异常值必须说明可核实的原因和规则，不能因为某轮“数字不好看”就删除。

预热和重复的工具化实现可参考 [Google Benchmark 用户指南](https://github.com/google/benchmark/blob/main/docs/user_guide.md)，但整机 UDP 实验还要另外控制发送与接收窗口。

**答题要点：**预热为了测稳定状态；长测为了发现随时间出现的问题；重复为了估计波动。

### 8. 如何测量端到端延迟？

先明确起点和终点。例如：

- `t0`：发送端生成报文；
- `t1`：接收程序从 Socket 读取报文；
- `t2`：报文解析完成；
- `t3`：结果进入界面更新队列；
- `t4`：界面实际刷新（通常较难精确测量）。

`t2 - t1` 是成功读取到解析完成的延迟，可能包括排队、校验和解析，不能直接称为解析函数的纯执行时间；`t3 - t1` 是成功读取到提交界面更新的延迟；`t4 - t0` 才接近用户看到结果的端到端延迟，但跨机器时间戳需要时钟同步。把不同阶段混成一个数字，会让人不知道该优化网络、解析还是界面。

**进一步拆开“等待”和“计算”。**有异步工作队列时，建议增加如下本机计时点：

| 时刻 | 记录位置 |
| --- | --- |
| `r_read` | 成功取出数据报后，业务处理之前 |
| `r_enqueue` | 数据放入工作队列时 |
| `r_start` | 工作线程开始处理这一条时 |
| `r_done` | 校验、解析与约定业务提交完成时 |
| `r_ui` | GUI 线程实际消费这次更新时 |

```text
工作队列等待 = r_start - r_enqueue
业务服务时间 = r_done - r_start
本地完成延迟 = r_done - r_read
GUI 消费延迟 = r_ui - r_read
```

例子：读取后立即入队，排队 8 ms，处理 0.2 ms，本地完成约 8.2 ms。只测解析函数会得到 0.2 ms，完全解释不了用户感受到的等待。

`r_read` 是应用读取时刻，不是网卡到达时刻，漏掉了读取前的系统排队。GUI 槽被执行也不等于像素已呈现到显示器，后者可能需要渲染/呈现层观测。报告里应使用准确的“提交”“消费”或“呈现”名称。

无论测哪一段，都用 `(test_id, sequence)` 把同一报文的时间点对应起来；不能把不同报文的时间点相减。

**答题要点：**先定义业务上关心的延迟，再在明确边界打时间戳；不同阶段分别记更容易定位。

### 9. 计时工具和时钟有什么要求？

测持续时间应使用**单调时钟**：读数不会因为用户校时或系统时间调整而倒退，适合测经过的时间。在 C++ 中通常用 `std::chrono::steady_clock` 测间隔。

系统墙上时间（如日期时间）适合日志标记，但不适合直接测短耗时。如果发送端和接收端在不同机器，分别读取本地单调时钟后相减没有意义，因为它们的时钟原点不同；即使使用墙上时钟，也可能有偏差和漂移。

可选办法：让两端进行足够精确的时钟同步并评估误差；或在单机记录开始和结束；或测往返时间（RTT），但 RTT 包含往返路径与对端处理，不能直接当作单向延迟。

**工具选择与精度边界：**

- C++ 的 `std::chrono::steady_clock` 适合测同机间隔；`high_resolution_clock` 这个名字本身不保证单调，不能只凭名称选择。
- Qt 可用 `QElapsedTimer`。按实际版本核对 API 和时钟；[Qt 文档](https://doc.qt.io/qt-6/qelapsedtimer.html)说明 Qt 6.6 起使用 `std::chrono::steady_clock`。
- 输出单位是 ns 不代表测量准确到 1 ns；还受实际时钟分辨率、调用开销、线程调度和取时间点的位置影响。
- 微小操作可以批量执行后测总时间以降低计时开销占比，但“批量总耗时/次数”是平均服务成本，不会自动给出逐报文 P99，也不包含真实队列等待。

跨机单向延迟可写成：`观测差值 = 真实延迟 + 两机时钟偏差 + 取点误差`。例如时钟偏差未知到 ±2 ms，就不能把测得的 0.3 ms 当成准确单向延迟；也不该把负延迟简单截成 0 后继续统计。应修正同步、明确误差，或改报本地处理延迟/RTT。

`RTT / 2` 只有在额外假设往返对称、对端处理已处理清楚等条件下才可能近似单程，不能当成普遍恒等式。单向延迟的时钟和误差问题可参考 [RFC 7679](https://www.rfc-editor.org/rfc/rfc7679)。

**答题要点：**同机测间隔用单调时钟；跨机单向延迟必须处理时钟同步误差。

### 10. 如何准确计算丢包率？

**先明确分母，再用唯一标识求差集。**给每条报文放测试轮次、发送源/会话标识和递增序号；序号统计范围要与正式阶段一致。

```text
G = 本轮实际生成且已尝试提交发送 API 的唯一报文集合
S = G 中被发送 API 成功接受的集合
R = 截止前被接收 API 成功读取的唯一报文集合
A = 截止前被业务接受的唯一报文集合

发送提交失败数     = |G - S|
应用接收缺失数     = |S - R|
读取后未接受数     = |(S ∩ R) - A|
业务未完成数       = |S - A|
应用接收缺失率     = |S - R| / |S| × 100%   （|S| > 0）
```

若 `R` 中还含别轮、非预期来源或不在 `S` 中的包，简单用 `|S|-|R|` 会错。只有确保接收集合属于同一预期发送集合、已去重且边界一致时，才可直接用数量相减。

计划但未生成、已生成但未尝试提交的报文另行记账，不能混入上述“提交失败”或悄悄从负载计划中消失。存在重传时，还要分开统计物理发送尝试与逻辑唯一报文。

如果无效报头让身份无法识别，单列“读取到但无法识别归属”的数量，保留原始样本；不能把它随意分配给某个缺失序号，更不能直接归因为网络路径丢失。

例如：实际生成 100,000 条，其中发送失败 100 条，`|S|=99,900`；预期范围内读取 99,800 个不同序号，业务接受 99,750 个：

```text
发送提交失败        = 100
应用接收缺失        = 99,900 - 99,800 = 100
应用接收缺失率      = 100 / 99,900 ≈ 0.1001%
读取后未接受        = 99,800 - 99,750 = 50
业务未完成          = 99,900 - 99,750 = 150
```

读取后未接受的 50 条还要由解析错误、业务过滤、队列丢弃或截止时仍在处理等原因解释。**不能把这 150 条统称为网络丢包。**发送 API 成功之后、应用读取之前还包括发送主机、网络、接收系统和 Socket 投递等环节。

边界情况也要设计：

- 收到 `1、3、2` 是乱序，`2` 在等待期内出现前只能称为暂时缺口。
- 收到 `1、2、2` 的接收调用次数为 3，但唯一序号数为 2。
- 发送端重启会话后序号可重新从 0 开始，用 `session_id` 防止误判为重复。
- 使用足够宽的无符号序号，定义回绕规则；不能简单把所有“小于历史最大值”的数当成重复。
- 为正式阶段报文定义半开窗口与排空截止；截止后的到达单列为迟到，或按预先约定的时限判失败，不能事后挪动规则凑结果。
- 分母为 0 时结果应为“不适用”，不能输出 0% 并称为通过。

**“没观察到丢包”不等于证明永不丢包。**在独立、同分布且丢失概率固定的简化模型下，观测 `N` 条全部成功，单侧 95% 上界为 `p_upper = 1 - 0.05^(1/N)`，大样本时约为 `3/N`。例如 100,000 条无缺失，上界约为 0.003%，而不是概率被证明等于 0。这个式子来自令 `(1-p)^N=0.05`；真实突发丢失往往相关，不能不检查模型就把它当成现场可靠性保证。

**答题要点：**先定义“发出”和“收到”的统计点；按唯一序号统计；区分丢失、重复、乱序。

### 11. 测量本身会怎样影响被测程序？

高频日志会做格式化、加锁和磁盘/控制台 I/O；抓包会消耗 CPU、内存和驱动资源；每条报文都更新 GUI 会额外制造工作。这些观测行为可能降低吞吐、增加延迟，甚至让抓包器自己丢包。

做法包括：先测未加重型观测的基线；减少逐包日志，改用周期统计或抽样；使用低开销计数器和直方图；分别比较开关抓包、详细日志和界面刷新的结果。还可以在报告里标注观测配置。

**建议把观测分成三个层次：**

1. 日常压测保留每条报文必要的低开销计数，每秒汇总一次吞吐、错误、队列和资源。
2. 延迟用预分配缓冲或直方图；必要时按事先规定的随机采样率采集，记录样本数和采样策略。不能只在“处理顺利时”取样。
3. 定位异常时，短时间启用指定序号或错误路径的详细跟踪；用开关对照估算影响。

可以用“观测打开后，业务吞吐变化多少、P99 变化多少、CPU 增加多少”报告成本。空循环计时或空处理路径可以提供开销线索，但计时、缓存和优化的作用并非总能线性相减，不能随意把一个平均开销从每条尾延迟里扣掉。

跨线程共用一个高频锁计数器也可能制造竞争；可考虑线程内局部计数再周期汇总，同时定义一致的统计快照。直方图若设置了量程，要统计溢出，不能静默丢掉最慢样本。
**答题要点：**测量结果包含了观测开销；用对照实验评估它，而非假设其为零。

### 12. 怎样把功能正确性纳入性能测试？

性能测试中如果错误解析、重复处理或悄悄丢弃数据，速度数字没有意义。测试报文应包含序号和可校验内容，接收端同时统计：唯一序号数、缺失数、重复数、解析失败数、校验错误数。

可以让接收端对每条数据做字段范围检查或校验和；负载允许时保留完整结果并与期望数据比较。对于极高吞吐场景，如果逐条完整校验开销过大，可以分层验证：先用较低负载做全量正确性检查，再在压测中保留序号、计数和抽样内容校验，并说明校验覆盖范围。

**让输入带有独立可计算的期望值。**例如规定：

```text
字段 value = sequence % 1000
字节序、长度、版本和单位固定
可变负载按事先固定的种子生成
```

接收端不仅比较序号数量，还检查解析出的 `value` 是否等于期望值。期望结果应来自清楚的协议规则、已知样本或独立实现，避免发送与接收复用同一个有缺陷的解析逻辑而“互相证明正确”。校验和一致也不证明字段单位和业务语义正确。

把测试分为：合法数据的性能基线、格式边界的功能测试、以及按固定比例混入错误数据的鲁棒性实验。对故意输入的错误包，正确拒绝是成功行为，要与合法包的意外解析失败分开统计。

如果抽样检查内容，只能说检查覆盖了这些样本，不能把结论写成“已逐条验证全部数据”。序号与基本记账尽量全量保留，内容抽样也要记录抽样率。
**答题要点：**必须说明在什么位置算“成功处理”，以及如何证明数据没有被错误处理。

## 第三部分：负载、瓶颈与稳定性

### 13. 负载测试、压力测试和长时间测试分别关注什么？

- **负载测试：**在预期正常或峰值业务负载下，检查系统是否达标。
- **压力测试：**逐步超过预期负载，找出性能退化或失效边界，以及恢复行为。
- **突发测试：**短时间输入远高于平均速率，检查队列和缓冲区如何应对。
- **长时间测试：**在持续负载下检查内存、句柄、队列、连接和性能是否随时间恶化。

它们回答不同问题。不能只做一次“跑得很快”的测试，就推断长期稳定或突发时也不会丢数据。

**先约定输入怎样随时间产生。**

| 负载形态 | 示例 | 它主要暴露什么 |
| --- | --- | --- |
| 平稳输入 | 每秒 5,000 条，分散发送 | 常态处理能力 |
| 短时突发 | 1 秒内的前 100 ms 发完 5,000 条，之后空闲 | 瞬时缓冲与接收调度 |
| 阶梯负载 | 每档维持一段时间，再提高输入 | 能力拐点、延迟和丢失如何退化 |
| 长时间输入 | 固定目标负载运行数小时 | 资源增长、温度、周期任务和长期退化 |
| 超载后恢复 | 超载一段时间，再降回正常输入 | 队列多久排空、服务能否恢复 |

前两种平均都是 5,000 条/秒，但突发时的瞬时输入达到约 50,000 条/秒，结果可能完全不同。报告平均速率时，仍要写明突发大小、持续时间和间隔。

**进一步区分开环和闭环：**

- 开环：按独立的计划时间产生新负载，不等待上一条完成，适合模拟持续外部 UDP 输入；仍要验证生成器有没有按计划执行。
- 闭环：等上一条完成或收到确认后才发下一条，适合测请求应答或指定并发数的业务，但被测系统变慢时，输入也会自动降低。

闭环不是错误模型，但不能拿它冒充固定外部到达率的压力测试。例如接收端卡 200 ms，发包工具也等 200 ms 才继续，卡顿期本来应该到来的负载就没有产生，结果可能显得“没丢包且很稳定”。

这种遗漏卡顿期间应有观测的风险常被称为 coordinated omission。优先用合适的负载模型，并记录计划时间、实际发出时间与发送迟滞；不要不了解输入过程就给直方图套“修正”。相关实现边界可参考 [HdrHistogram 的说明与源码](https://github.com/HdrHistogram/HdrHistogram/blob/master/src/main/java/org/HdrHistogram/AbstractHistogram.java)。

**答题要点：**按真实风险选择负载形态，并说明每种测试要发现什么。

### 14. 如何找到系统的处理能力边界？

从低于预期的速率开始，逐级提高输入，记录发送速率、接收速率、成功解析速率、延迟分位数、丢失、队列长度和 CPU。接近极限时常见现象包括：吞吐不再随输入增加、延迟快速上升、队列持续增长、丢包增加或 CPU 饱和。

**最大可持续处理能力**不是某一瞬间冲到的最高数字，而是在预先定义的时长内，正确性、延迟和资源指标仍满足阈值的最高负载。实际部署还要留余量，避免系统一直运行在拐点附近。

**还要先确认压力来自哪里。**配置输入 20,000 条/秒，发送器实际只有 12,000 条/秒，就不能说接收端已在 20,000 条/秒下通过。记录生成器 CPU、发送错误、实际发送率和短时间窗分布；必要时独立验证生成器容量。

Qt 的 `QTimer` 设为 1 ms 并不保证每秒准确回调 1,000 次；系统繁忙时会晚触发，多次超时也不会必然逐个补发通知。`0 ms` 更不等于固定速率。相关语义见 [QTimer 精度与超时说明](https://doc.qt.io/qt-6/qtimer.html#accuracy-and-timer-resolution)。

下面是教学数据，假定各档负载已满足、观测窗口相同，且第 4 题的延迟目标是 10 ms：

| 实际输入，条/秒 | 稳定业务输出，条/秒 | 本地 P99 | 队列趋势 | 判断 |
| --- | --- | --- | --- | --- |
| 5,000 | 5,000 | 2 ms | 稳定 | 满足此档示例条件 |
| 8,000 | 8,000 | 6 ms | 稳定 | 满足此档示例条件 |
| 10,000 | 10,000 | 18 ms | 有明显等待 | 吞吐跟上，但延迟已不满足 |
| 12,000 | 10,200 | 150 ms | 持续增长或队列满后丢弃 | 不可持续 |

这组数据只说明已验证通过到 8,000 条/秒，不能直接宣称精确边界就是 8,000。可以在 8,000～10,000 间加密取点，重复验证，并用真实峰值和波动决定部署余量。

大队列可能让短测“暂时不丢”，却持续增大延迟。输入停止后又处理很久，通常说明先前积压，不能把长时间排空掩盖成稳定吞吐达标。

**答题要点：**边界由业务验收条件决定，不只是看 CPU 达到 100% 或吞吐峰值。

### 15. 怎样用队列指标定位积压？

如果有接收、解析、界面更新等多个阶段，就分别记录每个队列的当前长度、最大长度、入队速率、出队速率和等待时间。队列长度长期上升，说明该阶段的输入长期大于输出；接收队列稳定、解析队列增长，优先检查解析；解析队列稳定、界面队列增长，优先检查 UI 更新。

仅看某一瞬间的长度不够，还要观察随时间的曲线。若队列有上限，还要记录满队列时采取的策略：阻塞、丢弃新数据、丢弃旧数据或合并更新。

**先做一条队列的收支核对：**

```text
队尾长度 = 队首长度 + 成功入队数 - 正常出队数 - 从队内主动移除数
```

队列满而拒绝的新数据没有成功入队，另记 `enqueue_rejected`，不能先算入队后又遗漏去向。工作线程取出但尚未完成的数据算“处理中”，不再属于队列长度。

例子：实际入队速率 10,000 条/秒，处理端出队速率 8,000 条/秒，从空队列开始、容量 20,000 条。理想化计算中，每秒增加 2,000 条，约 10 秒后填满。容量扩大为两倍，只是把溢出推迟到约 20 秒；长期吞吐缺口仍然存在。

**平均等待时间可以与队列长度交叉检查。**在稳定、边界一致、没有队内丢弃且平均量有意义的条件下，可用 Little 定律：

```text
平均排队条数 Lq = 实际入队/出队速率 λ × 平均排队时间 Wq
```

例如平均排队 1,000 条，稳定通过 5,000 条/秒，则平均等待约 `1,000/5,000 = 0.2 秒`。它描述平均值，不给出 P99，也不应直接套用到持续积压、未达到稳定的短时过程。

若队列满后阻塞接收线程，拥塞可能向上游传播到 Socket 缓冲；此时应用队列曲线不再上涨，但 Socket 处可能开始丢包。**队列长度稳定在上限，不代表系统健康。**

**答题要点：**在阶段边界计数；速率和随时间的趋势比一个孤立数字更有诊断价值。

### 16. 怎样判断 CPU、锁等待还是内存分配是瓶颈？

建议先确认现象可复现，并收集基线，再使用适当的性能分析工具：

1. **CPU 热点：**采样分析看时间花在哪里，是解析计算、拷贝、格式化还是其他函数。
2. **线程阻塞与锁竞争：**看线程是否经常等待、锁持有时间是否过长、是否有频繁上下文切换。
3. **内存分配：**看每条报文是否频繁创建临时对象或缓冲区，分配器是否占用显著时间。
4. **内存增长：**按时间记录常驻内存、队列长度和对象数量，区分泄漏与正常积压。

不要一看到 CPU 高就重写算法，也不要看到延迟高就先加线程。先让分析结果指出主要耗时或等待位置，再提出一次小改动，并用同一套测试验证。

**看现象时要防止几个误读：**

| 现象 | 应保留的解释 | 下一份证据 |
| --- | --- | --- |
| 整机 CPU 看起来很低，但接收跟不上 | 单个关键线程已占满一核；也可能在等锁或 I/O | 各线程 CPU、调用栈与等待原因 |
| CPU 很高但业务输出低 | 忙等、无效重试、日志格式化、拷贝或真正计算 | CPU 采样热点以及成功处理数 |
| 延迟高而 CPU 低 | 锁等待、磁盘/网络等待、事件循环未调度 | 阻塞栈、等待时长与线程调度 |
| 内存增加、队列也增加 | 活跃积压，未必是泄漏 | 停发后的队列和活跃对象是否减少 |
| 队列已空、活跃对象稳定，内存不回落 | 分配器保留、缓存或泄漏都有可能 | 分配/释放轨迹、存活对象与提交量趋势 |

如果工具把整机容量归一化为 100%，8 个逻辑核中的一个线程满负荷，整机占比可能只在 12.5% 左右；有的工具则把一个核心视为 100%。报告一定写清口径，不能只报“CPU 12%”。

Windows 的工作集表示当前驻留物理内存的页，私有提交量等指标含义不同。进程 RSS/工作集不下降不能单独证明泄漏；反过来，持续增长的活跃对象也不能被一句“系统缓存”解释掉。

工具可以从 Windows 的 WPR/WPA 入手，按实际需要捕获 CPU、线程调度和内存事件，保留符号信息，见 [Microsoft WPA 文档](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/windows-performance-analyzer)。工具采样结果仍要与同一时段的队列、吞吐和错误对应。

**如果单独测一个 C++ 解析函数：**使用真实数据，消费并核对输出，避免编译器把无用计算消除；把数据准备放在约定范围外或单独计时，批量测足够长时间。使用 Google Benchmark 时可按其文档评估 `DoNotOptimize` 等机制，不能简单添加 `volatile` 后就认为测量完全可信。

**答题要点：**性能分析工具回答“时间花在哪”；测量方案回答“改完有没有变好”。两者配合使用。

### 17. 如何评估界面更新对通信处理的影响？

如果每收到一条报文就跨线程发一个 UI 更新，事件队列可能快速变长；界面绘制和信号槽处理也会争用 CPU。按固定频率批量刷新，通常可以减少 UI 工作，但必须确认不会丢掉业务需要的状态或关键事件。

做对照实验时保持报文输入、解析逻辑和机器一致，只改变 UI 更新策略。分别记录接收数、解析数、丢失数、各队列长度、P99 延迟、CPU 使用率和界面响应。可比较“每包刷新”和“每 16/50 ms 批量刷新”等配置，具体周期由需求决定。

**把“保留全部数据”和“显示频率”分开。**假设每秒 5,000 条，界面每 50 ms 更新一次，理想情况下每批约 250 条：

- 如果显示当前温度曲线或最新状态，可以按规则汇总、降采样或只呈现最新快照。
- 如果每条都是告警、交易或必须保留的测量记录，不能为了 GUI 流畅就悄悄合并丢弃；应让业务路径保留完整记录，界面再按自身需求消费。
- 若要求画出每条原始点，批量提交不等于删除数据，需要验证绘图容量与延迟。

跨线程 queued 信号如果每包发一次，GUI 没处理完的调用也会积压。仅给绘制加定时器，但仍保留每包 GUI 事件，可能没有解决事件队列压力。可以让 GUI 定期拉取快照，或使用有界批次队列，并明确被合并/丢弃的是哪类展示数据。

测界面时至少分开记录：通信业务完成延迟、GUI 消费延迟、最新显示数据的年龄、交互卡顿。界面很流畅却显示几秒前的数据，也不符合实时需求。Qt 的线程归属和事件循环要求见 [Threads and QObjects](https://doc.qt.io/qt-6/threads-qobject.html)。

**答题要点：**别只看界面流畅度，也别只看收包数；同时观察通信完整性与用户看到更新的延迟。

### 18. 怎样公平比较两个实现或一次优化？

比较前固定：输入数据和速率、报文大小、机器和网卡、系统状态、编译器与优化等级、运行时长、预热方法、日志和抓包设置、正确性检查方式。每次只改一个主要因素，避免无法归因。

先测旧实现作为基线，再测新实现；交替或成对运行多轮，减少时间和环境漂移的影响。报告每轮数据、代表值和波动范围，同时比较正确性与资源占用。若新版本吞吐提高但 P99 延迟恶化或丢包上升，不能简单称为优化。

**一次可以执行的比较：**旧实现 A、新实现 B，在相同输入下安排 `A/B、B/A、A/B、B/A` 等成对实验，或者事先随机化顺序；每轮重新执行一致的预热与状态重置。不要把长期运行后的 A 与刚启动的 B 直接比较。

性能变化也要写对方向：

```text
吞吐提升率 = (新吞吐 - 旧吞吐) / 旧吞吐 × 100%
延迟降低率 = (旧延迟 - 新延迟) / 旧延迟 × 100%
```

例如稳定吞吐从 8,000 增到 10,000 条/秒是提升 25%；P99 从 10 ms 降到 8 ms 是降低 20%。“延迟下降 20%”不能直接改写成“吞吐提升 20%”，这两个指标不是这样换算的。

还要区分：

- **相同负载比较：**例如都输入 5,000 条/秒，比较资源和延迟。
- **各自容量边界比较：**按相同验收标准分别找最大可持续负载。

不能让 A 承受 10,000 条/秒、B 只有 5,000 条/秒，再用 B 的低延迟证明改进。样本量充足时可进一步报告成对差值与适当的置信区间；连续报文延迟通常相关，不能把百万条包机械地当成百万个完全独立重复实验。

若旧值是 0，百分比变化通常无定义；若提升只有 1% 而跨轮波动有 5%，应先报告“现有证据不足以确认提升”，继续检查噪声和设计。
**答题要点：**公平比较需要相同条件、重复测量和完整指标；优化要看是否满足目标，而不只是单个数字变好。

## 第四部分：综合性能验证

### 19. 怎样为 DDS 发布订阅设计性能实验？

比较 DDS 配置时，一次只改变一个主要因素，例如 QoS、传输方式或报文大小。固定发布者和订阅者数量、机器、网络、发布速率、运行时长、程序版本及数据内容。记录实际发布、接收和解析的序号，验证数据正确性。

测量吞吐量、延迟分布、丢失或重传相关统计、CPU、内存和队列。不同 QoS 可能在可靠性、资源消耗和延迟间取舍；应先写清实验想回答的问题，再选配置。若改变可靠性、历史深度或传输方式，要把这些配置完整记录，避免把不同语义的测试直接当作同一结果比较。

#### 19.1 先确定“比较的到底是什么”

以下是以 Fast DDS 为具体参照设计的实验思路。DDS 实现、版本和扩展不同，API 与统计项需按实际文档核实；不要套用一个未核实的默认 QoS。

例如问题可写成：“在固定双机拓扑、单 Writer/单 Reader、256 字节序列化业务数据和固定输入下，BEST_EFFORT 与 RELIABLE 在应用接收缺失、延迟、写入阻塞和资源占用方面有什么差异？”

此处是在比较不同可靠性语义的取舍。若改成“比较两个实现谁更快”，就应先让它们满足相同的可靠性与历史需求。

#### 19.2 除速率和大小外，还必须记录什么

| 条件 | 为什么会影响结果 |
| --- | --- |
| DDS 实现与版本、序列化类型、key/实例数量 | 每实例历史和资源占用可能不同 |
| Domain、Topic、类型、匹配数 | 先证明发现与 QoS 匹配成立，避免测试从未连上 |
| Reliability | 明确 Writer 提供与 Reader 请求的级别 |
| History 与 ResourceLimits | 记录 KEEP_LAST/KEEP_ALL、depth、样本及实例限制 |
| Durability 与读写端启动顺序 | 是否涉及晚加入者与历史样本 |
| 同步/异步发布及写入阻塞上限 | 成功 `write()` 的含义和发送线程压力不同 |
| 传输与同机快路径 | UDP/TCP、SHM、Data-sharing、进程内和零拷贝配置分别说明 |
| 订阅消费方式与回调工作量 | 是否及时 take、回调是否执行慢业务 |
| 过滤、时间相关策略、样本生命周期 | 有些未观察到的样本是配置行为，需要独立解释 |

Fast DDS 的标准 QoS 和兼容要求见 [官方 QoS 文档](https://fast-dds.docs.eprosima.com/en/stable/fastdds/dds_layer/core/policy/standardQosPolicies.html)。例如 BEST_EFFORT Writer 不能满足 RELIABLE Reader 的可靠性请求；先检查不兼容状态，不能把“没匹配”记成吞吐 0 的正常性能样本。

同机不代表在测 UDP 回环。[Shared Memory Transport](https://fast-dds.docs.eprosima.com/en/stable/fastdds/transport/shared_memory/shared_memory.html) 与 [Data-sharing](https://fast-dds.docs.eprosima.com/en/latest/fastdds/transport/datasharing.html) 是不同机制，配置允许时数据可能绕开预期的网络传输路径。对网络实验应明确并验证实际使用的路径，而不是只看配置里出现了 UDP。

#### 19.3 最小实验矩阵与执行顺序

| 组别 | 固定条件 | 改变的主要因素 |
| --- | --- | --- |
| D1/D2 | 双机、1 Writer/1 Reader、相同样本、速率与资源配置 | 两端一致切换 BEST_EFFORT/RELIABLE |
| D3/D4 | 固定可靠性、历史与拓扑 | 256 字节与 1,024 字节数据 |
| D5/D6 | 同机、固定其余条件 | 明确选择的网络路径与共享内存路径 |

D5/D6 回答同机传输选择问题，不能与双机结果混成一张“网络性能排名”。历史深度等参数若因实验语义必须调整，要列出调整理由，并承认比较条件发生了变化。

每轮可以这样执行：

1. 创建端点，等待预期匹配数和配置检查通过；设置超时，匹配失败则该轮无效。
2. 预热，确认接收端确实在消费；用新的正式阶段标识启动计量。
3. 按计划发布，分别记录尝试/成功/失败/超时、`write()` 调用耗时和实际速率。
4. Reader 及时取出可用数据，按 `SampleInfo` 区分有效业务样本与实例状态通知；对有效数据校验 ID、序号和内容。
5. 记录本地处理、跨机延迟或 RTT，按第 9 题说明时钟范围。记录可获取的丢失、拒绝、不兼容、deadline/liveliness 等状态，但这些状态不能一一替代应用序号差集。
6. 停发后按约定等待传输与业务排空，统计所有目标 Reader 的结果，再做下一轮。

#### 19.4 RELIABLE 也需要证明结果

不要把 RELIABLE 理解成“无限缓冲、无限等待、业务一定处理成功”。其结果仍受历史、资源、阻塞上限、消费速度和生命周期等条件影响。建议至少观察三层：

```text
应用调用 write() 成功
    → 中间件按其可靠性语义完成确认
    → 目标 Reader 的应用代码完成业务处理
```

支持的情况下，`wait_for_acknowledgments()` 可作为中间件确认层的辅助边界；它不代替接收业务自己的完成记录。具体返回条件见 [Fast DDS DataWriter API](https://fast-dds.docs.eprosima.com/en/stable/fastdds/api_reference/dds_pim/publisher/datawriter.html)。

几个 QoS 名称也容易误读：KEEP_LAST 表示有限历史保留，不能据此保证慢业务会取到每一个中间状态；Lifespan 等策略可能让样本到期失效；Deadline 关注同一实例的更新间隔，不能当作“每条报文端到端延迟已达标”的证明。应把预期策略行为与意外缺失分别报告。

**一个典型误判：**切到 RELIABLE 后缺失从 1% 变为 0%，但实际发布速率从 10,000 降到 4,000 条/秒，`write()` 阻塞明显增加。可以说该配置在更低实际输入下改善了交付，不能说它已经在原 10,000 条/秒负载下通过。

如果有多个 Reader，应分别报告各自唯一接收数、延迟和未完成数。业务若要求所有 Reader 都收到，还要计算全部目标 Reader 已完成的序号交集；把所有 Reader 计数相加会把同一业务样本的多份副本当成多条输入。

**答题要点：**控制变量、记录 QoS 和拓扑、同时测性能与正确性；不要只比较一个吞吐数字。

### 20. 综合设计：高频 UDP 接收模块的测试计划

可以按以下模板组织答案：

1. **测试目标：**明确成功处理的定义，以及目标吞吐、丢包率、P99 延迟、资源和运行时长。
2. **测试环境：**写明电脑、操作系统、网卡、网络拓扑、程序版本、编译配置和干扰控制。
3. **负载模型：**规定 UDP 负载大小、固定或变化的发送速率、突发模式、报文序号和持续时间。
4. **测量点：**区分发送、接收、解析完成和 UI 提交/显示时间；说明跨机器计时如何处理。
5. **正确性：**统计唯一序号、缺失、重复、乱序、解析失败和字段校验错误。
6. **性能数据：**记录每秒发送/接收/处理量、延迟 P50/P95/P99、队列长度、CPU、内存和错误数。
7. **测试阶段：**先低负载基线，再逐步加压、短时突发、长时间稳定运行；每种明确预热、计时和排空方式，并重复多轮。
8. **判读方式：**吞吐平台期、队列持续增长、延迟长尾、CPU 热点和丢包同时观察，用它们判断瓶颈阶段。
9. **复现记录：**保存程序提交号、参数、环境、原始结果和分析脚本，让别人能重跑。

一个重要习惯是分阶段增加复杂度：先确认低速时数据完全正确，再确认正常负载达标，然后提高速率寻找边界，最后才做突发和长时间测试。这样每次出现异常时，能把问题定位到更小的范围。

#### 20.1 把模板填成一份具体计划

下面是一份可改参数后使用的教学计划。先明确产品语义：**通信和业务路径保留每条有效报文，GUI 只以固定周期显示最新快照**。GUI 合并展示不计作通信丢失，必须保留的告警事件另走完整记录路径。

| 项目 | 示例约定 |
| --- | --- |
| 正常负载 | 固定 256 字节 UDP 负载，开环目标 5,000 条/秒 |
| 环境 | 双机有线网络、指定接口、固定 Release 程序与配置，记录第 6 题全部环境信息 |
| 正式阶段 | 预热 30 秒后，正式发送 600 秒，停发后排空 2 秒，正常负载重复 5 轮 |
| 输入有效性 | 每秒检查实际成功发送数及发送迟滞，示例容差 ±1%；未满足则标记负载无效 |
| 接收完整性 | 对正式发送集合 S，在截止前应用接收缺失率不高于 0.01% |
| 业务正确性 | 合法输入的格式/解析错误、应用队列丢弃为 0；截止时业务未完成率不高于 0.01% |
| 本地延迟 | 对已接受报文，读取到业务接受 P99 不高于 10 ms；单列超过时限、未完成和迟到数 |
| 队列 | 显式有界，示例容量 20,000 条；正常负载不溢出、不持续积压，记录高水位和等待分布 |
| CPU | 示例要求进程 CPU 不高于整机归一化容量的 60%，另报关键线程占用 |
| 内存 | 示例私有提交量不超过 512 MiB；长测比较队列、活跃对象与资源趋势，不能只看首尾两个点 |
| GUI | 50 ms 周期获取快照；测 GUI 消费的快照年龄和交互停顿，示例快照年龄 P99 不高于 100 ms |

跨机时钟未得到足够精确的验证时，GUI 快照年龄可先定义为同机“成功读取到 GUI 消费”的间隔，并明确它不包含网络段。若验收要求生成到显示，则必须扩展计时和时钟同步，不能偷换成这个本地指标。

这些阈值应在测试前确定；测试后因为结果不好而放宽阈值，属于修改需求，不能作为原目标已通过的依据。

#### 20.2 负载与测试矩阵

| 编号 | 测试 | 示例安排 | 通过或观察重点 |
| --- | --- | --- | --- |
| F0 | 功能与鲁棒性 | 少量合法、边界、重复、乱序与无效数据 | 对合法数据解析正确；对故意无效数据按规则拒绝并记账 |
| P1 | 低速基线 | 500 条/秒，正式 60 秒，3 轮 | 程序、测量点、计数与工具链可信 |
| P2 | 正常负载 | 5,000 条/秒，正式 600 秒，5 轮 | 满足预先约定的正常负载阈值 |
| P3 | 阶梯加压 | 如 1,000/2,000/5,000/8,000/10,000 条/秒，各维持 120 秒、3 轮 | 找到吞吐、延迟、队列和缺失的拐点，再加密验证 |
| P4 | 短时突发 | 每 500 ms 发 2,500 条，集中在前 50 ms，运行 120 秒 | 平均约 5,000 条/秒，突发约 50,000 条/秒，观察缓冲和调度 |
| P5 | 长时间稳定性 | 正常负载持续 4 小时 | 按时间窗检查资源、错误、队列、延迟退化 |
| P6 | 超载与恢复 | 超过已测容量短时输入，再降到已验证的正常负载 | 不崩溃、资源有界、丢弃可解释，按预定恢复时间验证 |

P3/P6 的超载阶段允许出现事先预期的受控丢弃或退化，验收点是失效边界和恢复行为；不能拿正常负载的零丢弃要求套住所有破坏性压力阶段。P4 的实际突发形态也要验证，配置参数不等于已产生该负载。

第 17 题的 UI 对照、第 11 题的观测开销对照，在固定负载下作为独立组执行，避免一次同时改 UI、缓冲和线程数。

配套网络文档的最小 Qt 程序适合少量收发验证，单轮限制为 200,000 条，不应直接冒充这里的完整压测器。600 秒正常负载约为 300 万条，4 小时约为 7,200 万条；需扩展控速、轮次、阶段标记、流式统计和有界记录能力，并先验证生成器自身容量。

#### 20.3 采集与记账

每条正式报文最少带 `test_id、sender/session_id、sequence、phase、version、length` 以及可校验业务内容。跨机测延迟时再加入约定的同步时间戳；否则优先在接收机测本地阶段。

建议输出：

- 每秒汇总：实际生成/发送/读取/业务接受量，错误、重复、乱序、队列长度/高水位、CPU 与内存。
- 每阶段延迟：P50/P95/P99、最大值、超阈值数和直方图样本数。
- 轮次结算：发送失败、唯一接收缺失、解析失败、过滤、应用队列丢弃、仍在处理及迟到，核对去向。
- 定位附件：必要时的抓包、系统/网卡统计差值、性能分析跟踪，以及影响结果的观测配置。

对数千万序号永久使用散列表或逐包文本日志可能成为新的瓶颈。可按协议与乱序容忍范围使用位图、区间或有界窗口，并说明何时把暂时缺口判为截止缺失；保留核对最终边界的能力。工具不能为了省内存而不记录遗漏的尾部。

每轮开测前验证发送器目标已匹配、接收端绑定与处理循环正常、计数器属于本轮、数据样本可正确解析。两边抓包若要用来归因，必须核实接口、过滤、捕获时段和捕获自身丢包。

#### 20.4 用一组结果练习判定

以下仅为教学数据。假设某轮正式 600 秒，实际成功发送 3,000,000 条，发送失败 0，逐秒输入也满足约定：

```text
截止前唯一读取：       2,999,800
重复读取：                   300
原始成功读取调用数：   3,000,100
合法输入解析失败：             20
应用队列丢弃：                  0
截止前唯一业务接受：   2,999,780
正式输入窗口内接受：   2,999,700
排空期补接受：                 80
截止时仍在处理：                0
本地处理延迟 P99：          4 ms
```

可以算出：

```text
应用接收缺失 = 3,000,000 - 2,999,800 = 200，约 0.00667%
业务未完成   = 3,000,000 - 2,999,780 = 220，约 0.00733%
读取去向     = 2,999,780 + 20 = 2,999,800 个唯一报文
窗口业务吞吐 = 2,999,700 / 600 = 4,999.5 条/秒
```

**结论：这一轮仍未通过示例目标。**缺失比例和已完成样本 P99 虽然满足对应阈值，但合法输入存在 20 条解析失败，违反正确性要求。还需看 CPU、内存、队列与 UI，不能只选两个好看的指标宣称全部通过。

其中 200 条没有读到，不能直接断定是网络设备丢失；要按相邻观测点进一步定位。20 条解析失败发生在读取之后，优先对照字节与解析逻辑。80 条排空期补完成用于最终完成率结算，不混入正式窗口业务吞吐。

#### 20.5 最后的答题组织方式

可以按“**目标 → 环境 → 负载与生成器验证 → 测量点和时钟 → 正确性记账 → 分阶段实验 → 验收与归因 → 复现材料**”回答。

如果只能用一段话作答：我会先明确业务完成点、目标输入与时延/完整性要求，在固定环境和 Release 构建下用带会话、阶段和序号的报文压测；验证实际输入，记录读取、入队、处理和 UI 消费时间，统计唯一序号去向、延迟分布及队列资源；依次覆盖低速、正常、阶梯、突发、长测与超载恢复，每轮区分预热、正式和排空；最后按全部预定阈值判定，用原始结果和配置保证能复现。

## 附录 A：计数与延迟记录模板

### A.1 每秒汇总建议保留什么

所有字段先规定单位与语义。计数可保存累计值，速率通过相邻快照差除以**实际经过时间**计算，不因为设置“每秒触发”就固定除以 1。

| 类别 | 示例字段 | 说明 |
| --- | --- | --- |
| 身份与窗口 | `test_id, phase, role, elapsed_ms, interval_ms` | 不混轮次；本机单调时间适合测间隔 |
| 生成与提交 | `planned_due_total, generated_total, send_attempt_total` | 暴露计划负载是否按时产生 |
| 发送结果 | `send_ok_total, send_error_total, send_lateness_max_us` | 实际输入和生成器迟滞 |
| 读取 | `read_raw_total, read_bytes_total, read_error_total` | 在业务过滤前记数，字节数指明是 UDP 负载 |
| 唯一报文 | `expected_unique_read_total, accepted_unique_total` | 按预期发送集合与序号去重 |
| 拒绝与遗漏 | `duplicate_total, other_test_total, invalid_total, filtered_total` | 规定每类原因，避免一个拒绝被加两次 |
| 应用队列 | `enqueue_rejected_total, queue_removed_total, queue_now, queue_high_water, processing_now` | 分开队列拒绝、队内移除与处理中 |
| 延迟 | 各段样本数、P50/P95/P99、最大值、`over_limit_total` | 保存直方图配置；窗口值和累计值名称分开 |
| 资源 | 进程与关键线程 CPU、工作集/私有提交量、句柄/线程数 | 统一单位与归一化方式 |

例如两个汇总点之间实际过了 1.2 秒，读取数增加 6,000 条，则该窗实际速率是 `6,000/1.2=5,000 条/秒`，不是 6,000 条/秒。

每秒的短窗口摘要用于看趋势，整轮最终汇总用于验收。不能只存每秒 P99，再声称能精确恢复整轮 P99；要保留可合并的样本或直方图。

### A.2 报文时间记录的建议格式

下面是字段设计，不要求每次压测都逐包输出 CSV：

```text
test_id, sender_session, sequence, phase,
recv_read_ns, enqueue_ns, work_start_ns, business_done_ns,
result, reject_reason
```

这些本地时间应来自同一约定的时钟域和原点。采样时保留 `sampled` 或对应规则，失败、尚未完成的字段保持缺失并单列状态，不填 0 来伪造低延迟。

量大时优先保存每秒摘要、延迟直方图、错误样本和有界序号记录。需要精确分析某些序号时，再有针对性地导出细节。

### A.3 最少核对三组关系

```text
没有发送重试时：
发送尝试数 = 发送成功数 + 发送失败数

单个应用队列：
期末长度 = 期初长度 + 成功入队 - 正常出队 - 从队内主动移除

同一预期发送集合且身份均可识别时：
成功发送的唯一数 = 截止前唯一读取数 + 应用接收缺失数
```

业务流水线还应核对“读取后接受、各种互斥拒绝、主动丢弃、仍在处理”的去向。若允许重复、过滤和多阶段转发，按程序真实路径设计计数关系，不把不相容的计数硬相加。

多个线程异步读取计数时，瞬间快照可能不完全一致；要么使用约定的一致快照，要么等排空后进行最终核对，并解释允许的短时偏差。不要用不一致的快照算出负丢包率后，再把它强行置零。

## 附录 B：五个计算练习与参考解答

建议先自己算，再看答案。下面全部是人为构造的练习数据。

### B.1 平均值与尾延迟

100 个已完成样本中，99 个为 1 ms，1 个为 500 ms。使用本文的 nearest-rank 方法，求平均值、P95、P99、最大值与超过 10 ms 的比例。

**解答：**平均值为 5.99 ms；P95、P99 均为 1 ms；最大值为 500 ms；超 10 ms 的比例为 1%。应同时报告样本数和极慢样本，不能只说“P99 才 1 ms”。

### B.2 丢失、重复与解析失败

正式阶段生成并尝试发送 100,000 条，其中发送失败 100 条。接收端读到预期报文共 99,850 次，含 50 次重复；唯一业务接受数为 99,750，剩下已读取的唯一报文因解析错误未接受，截止时没有在途处理。

求应用接收缺失、读取后未接受、业务未完成和应用接收缺失率。

**解答：**

```text
S = 99,900
唯一读取 R = 99,850 - 50 = 99,800
应用接收缺失 = 99,900 - 99,800 = 100
读取后未接受 = 99,800 - 99,750 = 50
业务未完成   = 99,900 - 99,750 = 150
接收缺失率   = 100/99,900 × 100% ≈ 0.1001%
```

150 条业务未完成里有 50 条已经被读取，不能说 150 条都在网络上丢失。

### B.3 队列多久填满

从空队列开始，入队 10,000 条/秒，出队 8,000 条/秒，容量 20,000 条，忽略速率波动。多久填满？如果正好满时停止输入，处理端仍保持 8,000 条/秒，约多久排空？

**解答：**积压每秒增加 2,000 条，约 10 秒填满。满队列停止输入后，排空约需 `20,000/8,000=2.5 秒`。这也说明预定 2 秒排空不一定足够；达到截止仍未完成的必须按规则记录，不能悄悄延长截止。

### B.4 “可靠且零丢失”是否意味着目标通过

DDS 切换 RELIABLE 后，目标仍为 10,000 条/秒，实际成功发布只有 4,000 条/秒，接收端无缺失且 P99 合格。能否说在 10,000 条/秒负载下通过？

**解答：**不能。实际输入没达到目标，此轮不足以验证原目标。要检查写入阻塞、生成器和资源配置；可以如实报告“实际 4,000 条/秒条件下的结果”，再重新设计实验。

### B.5 优化百分比与分位数汇总

同条件下旧版容量为 8,000 条/秒，新版为 10,000 条/秒，提升多少？另有两轮各 1,000 个延迟样本：第一轮 990 个 1 ms、10 个 100 ms；第二轮 990 个 2 ms、10 个 100 ms。各轮 P99 和合并 P99 是多少？

**解答：**容量提升 25%。两轮 P99 分别为 1 ms、2 ms，其平均为 1.5 ms；合并后有 2,000 个样本，P99 取第 1,980 个，为 2 ms。因此平均 P99 并不是合并 P99。

## 最后用这张检查表自查

回答任何性能问题时，可以问自己：

- 我测量的起点和终点是什么？
- 输入负载和环境是否写清楚？
- 有没有同时验证正确性？
- 平均数之外有没有看延迟分布和队列趋势？
- 测量工具本身有没有干扰结果？
- 结论有没有原始数据支持，别人能不能复现？
- 计划速率、实际生成、成功提交和实际业务输出是否分开记录？
- 发送失败、接收缺失、解析失败和应用丢弃是否分别解释？
- 有没有遗漏未完成/超时样本，只看成功样本的低延迟？
- 预热、正式窗口和排空期是否分开，统计是否属于同一批报文？
- 有没有错误地平均多个 P99，或把本机处理延迟写成跨机端到端延迟？
- 队列稳定是否只是因为已满、正在丢弃或阻塞上游？
- DDS 的端点匹配、QoS、实际传输路径与 write 成功含义是否已核实？
- 正常负载达标、超载退化和恢复行为是否分别判断？
