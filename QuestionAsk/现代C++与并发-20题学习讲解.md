# 现代 C++ 与并发：20 题学习讲解

本讲解与《现代C++与并发-20道渐进自测题》一一对应。你已经有 Qt/C++ 业务开发经验，这里重点补上几条贯穿工程的问题：对象什么时候失效，谁负责销毁资源，线程之间怎样交接数据，以及退出时如何保证没有线程继续使用已销毁的对象。

代码以 C++17 为主要基线；`std::jthread`、`std::stop_token` 等内容会标明需要 C++20。Qt 部分按照 Qt 6 的对象与线程规则说明。标注“错误示例”的代码用来分析问题，不要把运行时偶尔成功当作正确性的证明。除标为完整示例的代码外，各代码块是相互独立的教学片段，需要放入适当的函数或类中使用。

建议每次学习 2～3 题，读完后合上讲解，再用自己的话回答原题。解释代码时，先回答“谁拥有对象、谁在访问对象、用什么保证访问顺序”。这三个问题比记住某个 API 的拼写更有帮助。

## 1. 对象生命周期：指针还在，不代表对象还在

**原题关注：**对象怎样创建和销毁？局部对象与动态对象由谁控制？为什么不能返回局部变量的引用？

先区分两件事：**存储空间**是放置对象的地方，**对象生命周期**描述这个对象何时可以被正常使用。学习初期可以把创建过程理解为“取得空间，完成初始化”，结束过程理解为“执行必要的析构，再按存储方式回收空间”。更精确的底层规则涉及构造、析构期间的特殊限制，平时先掌握普通对象的使用边界即可。

```cpp
#include <memory>
#include <string>

void example() {
    std::string name = "receiver";             // 自动存储期对象
    auto number = std::make_unique<int>(42);   // number 是局部智能指针
                                              // 它管理的 int 是动态对象
} // number 先析构并释放 int，然后 name 析构
```

日常说的“栈对象”，通常指上面这样的局部自动对象；“堆对象”通常指动态分配的对象。它们是便于理解的说法，语言层面更准确的分类是自动、动态、静态和线程存储期。尤其要注意：局部变量 `number` 与它指向的动态 `int` 是两个不同对象。

引用和裸指针通常只提供访问路径，不延长被指向对象的寿命：

```cpp
// 错误示例：不要通过调用它来验证“是否碰巧可用”。
const std::string& badName() {
    std::string name = "receiver";
    return name;
} // name 已经析构，返回的是悬空引用

// 正确：返回一个值，调用者持有自己的结果。
std::string goodName() {
    return "receiver";
}
```

“原来那块内存看起来还有字符”也不能继续访问。对象已经结束生命周期，后续使用可能产生未定义行为。`const` 只限制修改，不会挽救这个返回局部引用的错误；返回指向局部字符串的 `std::string_view` 也存在同类问题。

局部对象通常按构造的相反顺序析构。类成员按**声明顺序**初始化、按相反顺序析构，因此线程成员与它依赖的队列、互斥锁的声明顺序，也可能影响退出是否安全。

**答题可以这样组织：**说明自动对象在离开作用域时销毁，动态对象依赖明确的所有者释放；引用和指针不会自动延寿；返回值可以把结果安全地交给调用者。返回按值的对象常能利用拷贝消除，不必为“省一次拷贝”返回悬空引用。

**检验理解：**一个函数返回 `buffer.data()`，但 `buffer` 是函数里的局部 `std::vector`。即使返回类型是 `const char*`，问题是否得到解决？

## 2. 裸指针与智能指针：先决定谁负责销毁

**原题关注：**三种指针表达什么关系，什么时候应该选哪一种？

所有权的意思是：**谁有责任让资源在合适的时间被释放**。指针能访问对象，与它是否拥有对象，是两个不同问题。

| 类型 | 常见含义 | 能否复制所有权 | 主要风险 |
| --- | --- | --- | --- |
| `T*`、`T&` | 借用已有对象；旧接口中裸指针也可能拥有资源 | 复制地址不等于合理地复制所有权 | 悬空、约定不清、重复释放 |
| `std::unique_ptr<T>` | 一个明确的独占所有者 | 不能拷贝，可以移动 | 把 `.get()` 得到的地址借用得太久 |
| `std::shared_ptr<T>` | 多个参与者共同维持对象生命 | 可以复制共享所有权 | 循环引用、共享关系过多、误以为对象自动线程安全 |

没有动态生命周期需求时，先考虑直接保存值，例如 `Packet packet;` 或 `std::vector<Packet>`。需要动态独占资源时，`unique_ptr` 往往最容易推理；确实需要多个独立参与者共同维持生命周期时，再考虑 `shared_ptr`。

```cpp
#include <memory>

struct Packet { int id = 0; };

void inspect(const Packet& packet) {
    // 只借用，调用结束后不保存 packet 的地址。
}

void takeOwnership(std::unique_ptr<Packet> packet) {
    // 所有权已经进入函数；也可以继续移动给另一个所有者。
}

void example() {
    auto packet = std::make_unique<Packet>();
    inspect(*packet);
    takeOwnership(std::move(packet));
    // packet 现在为空，不能再解引用。
}
```

不要对智能指针的 `.get()` 结果执行 `delete`；它没有把销毁责任交给你。也不要为了“方便”把所有对象都改成 `shared_ptr`，那会让实际存活范围更难理解。

在 Qt 中，父子对象树本身也是一种所有权机制。`new QUdpSocket(worker)` 可以由父对象管理，并不意味着见到 `new` 就一定泄漏。要避免同一对象同时由父对象和另一套独立的智能指针销毁。

**答题要点：**先说生命周期需要，再选指针；“智能指针”不是一个统一的所有权模型。

## 3. RAII 与异常安全：让释放跟着作用域走

**原题关注：**资源如何在正常返回、提前返回和异常时得到释放？

RAII 常译为“资源获取即初始化”。实用理解是：**用一个对象代表对资源的持有，构造时建立持有关系，析构时释放资源**。作用域结束会触发析构，从而减少依靠每条执行路径手动清理的负担。

```cpp
#include <mutex>
#include <stdexcept>

std::mutex mutex;

void update() {
    std::lock_guard<std::mutex> lock(mutex);
    throw std::runtime_error("更新失败");
} // 当异常向外传播并进行栈展开时，lock 析构，释放 mutex
```

如果改成先 `mutex.lock()`，最后再 `mutex.unlock()`，中间抛出异常就可能绕过手工解锁。RAII 同样用于文件流、动态缓冲区、操作系统句柄和 Socket 包装类。不同平台的资源要用匹配的释放函数，例如 Socket 不能一概用 `delete` 释放。

RAII 能帮助资源清理，但不自动保证业务状态回滚。例如转账时已经扣款，随后入账失败，互斥锁会正常释放，余额仍可能不一致。因此还要区分：

- **基本保证：**出错后不泄漏资源，对象仍满足自身约束。
- **强保证：**失败时，对外可见状态相当于本次操作没发生。
- **不抛异常保证：**操作承诺不向外抛异常。

如果一个对象的构造函数抛异常，这个尚未完整构造的对象不会执行自己的析构函数；已经构造好的成员和基类会清理。因此资源应尽早交给 RAII 成员，避免构造过程中先拿裸资源再执行可能失败的步骤。

RAII 依赖正常的销毁和异常栈展开，不保证进程被强杀或程序直接终止时仍执行析构。析构函数也应避免向外抛异常。

**答题要点：**解释作用域与析构怎样覆盖异常路径，并说明资源安全与业务事务回滚是不同层面的保证。

## 4. `shared_ptr`：共享的是寿命管理，不是对象的锁

**原题关注：**对象何时销毁，引用计数与数据访问的线程安全有什么区别？

可以把共享所有权想成几张有效的使用凭证。普通场景下，最后一个共享所有者释放所有权时，才会调用删除器销毁被管理的对象。实现一般用一个控制块维护引用计数等管理信息；有弱引用存在时，控制块可能比对象本身活得更久。

这里有三层必须区分：

1. **不同的 `shared_ptr` 对象共享同一份所有权：**各线程操作各自的句柄，可以安全地维护共享计数。
2. **同一个 `shared_ptr` 变量：**一个线程 `reset()`，另一个同时读取它，需要同步；C++20 的 `std::atomic<std::shared_ptr<T>>` 是一种选择。
3. **指针指向的 `T` 对象：**多个线程修改其中的普通字段，仍可能发生数据竞争。

```cpp
#include <memory>

struct State { int count = 0; };
auto a = std::make_shared<State>();
auto b = a; // a、b 是两个句柄，指向同一个 State

// 如果线程 A 执行 ++a->count，线程 B 同时执行 ++b->count，
// count 仍然需要互斥锁或合适的原子设计。
```

不要把相同裸地址分别交给两个独立构造的 `shared_ptr`，例如 `shared_ptr<T>(raw)` 写两次。它们可能产生两个独立控制块，最终重复销毁同一对象。也不要用 `use_count() == 1` 作为通用的并发独占证明，计数观察可能很快过时。

对象通常在最后一次释放发生的线程中销毁。若对象是具有线程归属要求的 Qt 对象，就必须额外设计销毁线程，不能只依靠默认删除器。

这些共享所有权边界可查阅 [C++ 标准草案的 shared_ptr 规定](https://eel.is/c++draft/util.smartptr.shared)。

**答题要点：**分别回答控制块、句柄变量、被管理对象；不要只说一句“shared_ptr 是线程安全的”。

## 5. `weak_ptr`：观察对象，不强行把它留住

**原题关注：**循环引用为什么不释放，怎样安全地访问弱引用？

设想 `A` 强持有 `B`，`B` 又强持有 `A`。外部所有者都离开后，两者仍各有一个强引用，计数无法归零。

```cpp
#include <memory>

struct Parent;
struct Child {
    std::weak_ptr<Parent> parent; // 反向关系只观察
};
struct Parent {
    std::shared_ptr<Child> child;
};
```

`weak_ptr` 不增加强引用计数，因此不会单独阻止对象销毁。访问时调用 `lock()`，尝试取得一个临时 `shared_ptr`：

```cpp
if (auto owner = child->parent.lock()) {
    // owner 存活期间，Parent 的生命周期有保障。
    // 若要并发修改 Parent 的字段，仍需另外同步。
} else {
    // Parent 已经不存在，可以放弃这次访问。
}
```

不要先判断 `expired()`，过一会儿再假定对象仍然存在。检查之后，其他线程可能刚好释放最后一个强引用。直接使用 `lock()` 的返回值，就把“尝试取得所有权”和“取得后暂时延寿”连在一起。此处的原子取得规则见 [weak_ptr::lock 的标准说明](https://eel.is/c++draft/util.smartptr.weak.obs)。

弱引用适合反向关联、缓存中的观察关系、可能比接收对象活得更久的异步回调。它不负责对象内部数据的线程同步。

**答题要点：**指出强引用环，把不应承担生命维持责任的一条关系改为弱引用；访问时保存 `lock()` 得到的强引用。

## 6. 拷贝与移动：移动表达资源转交

**原题关注：**为什么需要移动，源对象移动后还能做什么？

拷贝通常意味着产生另一份相应的值；移动允许新对象接管原对象的某些资源。对大块动态缓冲区，转交内部资源可能比复制所有数据便宜。不过移动的成本和具体效果依赖类型，不能认为所有移动都只交换一个地址。

从函数签名看，常见的拷贝构造是 `T(const T& other)`，移动构造是 `T(T&& other)`。新对象初始化时会参与相应的重载选择；已经存在的对象被赋值，则涉及拷贝赋值或移动赋值。`&&` 在这里表示右值引用，不是两个对象共同拥有同一份资源的声明。

```cpp
#include <memory>
#include <utility>

auto first = std::make_unique<int>(42);
auto second = std::move(first);
// second 成为所有者，first 保证为空。
```

`std::move` 本身做的是类型转换，使表达式能够参与移动重载选择；真正转移资源的是被选中的构造或赋值操作。类型没有合适的移动操作时，可能发生拷贝，甚至编译失败。对 `const` 对象使用 `std::move`，经常也不能调用常见的非 const 移动构造。

标准库类型在没有更具体规定时，移动后处于“有效但未指定状态”：可以析构，可以执行满足其前提条件的操作，但不要猜测内容。`unique_ptr` 移动后为空有明确保证；一般不能据此推断所有容器移动后必定为空。[标准库移动后状态说明](https://eel.is/c++draft/lib.types.movedfrom)也不应机械套用于所有自定义类型，自定义类需要维护自己的约束。

资源管理类还会涉及拷贝、移动、析构这几类特殊成员函数。业务类优先让 `vector`、`string`、智能指针等成员承担管理责任，争取使用默认的特殊成员函数，这常称为“零法则”。确实手工管理裸资源时，再完整设计相关操作，避免默认拷贝导致双重释放。合理的 `noexcept` 移动也能帮助容器在扩容时选择更合适的策略。

**答题要点：**说明移动适用于独占缓冲区、句柄等资源交接；`std::move` 不等于已经移动；移动后源对象仍存在，但可依赖的状态由类型契约决定。

**检验理解：**为什么 `return local;` 常常比随手写 `return std::move(local);` 更合适？思考它与命名返回值优化的关系。

## 7. 异步任务的所有权：任务结束前，数据必须还活着

**原题关注：**函数已经返回，后台任务却仍在使用局部变量，如何解决？

```cpp
// 错误示意：返回后，线程可能仍然访问已经析构的 data。
void badLaunch() {
    std::vector<int> data{1, 2, 3};
    std::thread([&data] {
        // 使用 data
    }).detach();
}
```

捕获引用只保存访问关系。线程调度没有承诺“肯定先用完 data，函数才返回”。加一个 `sleep` 也无法建立可靠的生命周期保证。

常见办法有三种：在局部数据离开作用域前等待任务结束；把数据按值复制或移动进任务；确实需要共同持有时，让任务保存自己的共享所有权。

```cpp
#include <thread>
#include <utility>
#include <vector>

std::thread launch(std::vector<int> data) {
    return std::thread([owned = std::move(data)] {
        // owned 是闭包持有的数据，可在这里独立处理。
    });
}

void caller() {
    auto worker = launch({1, 2, 3});
    worker.join();
}
```

这段代码把数据交给任务，把线程管理责任交给调用者。真实项目还需要处理创建线程后其他步骤抛异常的情况，第 15 题会介绍更方便的生命周期管理方式。

捕获 `[this]` 也不会自动延长当前对象寿命；按值捕获一个裸指针，只是复制地址。`std::span`、`std::string_view` 等视图通常也不拥有底层数据。UDP 接收时若把“指向复用接收缓冲区的指针”放进队列，下一次收包可能已经覆盖内容，任务交接必须同时解决数据存活和修改时机。

**答题要点：**说明捕获方式与生命周期的关系，并为每份异步数据指定所有者；共享寿命与并发修改的同步仍要分别考虑。

## 8. 数据竞争：不能靠“这条指令应该很简单”保证正确

**原题关注：**为什么多个线程访问普通整数，也会出问题？

先判断是否存在以下组合：多个线程可能并发访问同一内存位置，至少一个访问会修改它，且这些冲突访问没有合适的同步关系。若构成 C++ 定义的数据竞争，程序具有未定义行为；不只是最终数字偶尔少几次这么简单。更完整的规则见 [C++ 数据竞争定义](https://eel.is/c++draft/intro.races)。

```cpp
// 错误示意：多个线程无同步地对同一个 count 执行自增。
int count = 0;
// 线程 A：++count;
// 线程 B：++count;
```

把 `++count` 想象成“读旧值、加一、写回”，可以直观解释为什么两个更新可能互相覆盖。但语言层面的未定义行为还允许更广泛的优化结果。即使某个平台对齐后的整数读写不会撕裂，也不能消除没有同步的读写竞争。

`volatile` 不是通用的线程同步手段；`sleep`、输出日志和“我试了一千次都对”也不是同步保证。只读共享通常更容易安全，但也必须确保对象已正确发布、仍在存活，并且没有其他线程暗中修改。

还要区分“没有数据竞争”和“业务逻辑正确”。例如两个原子操作之间夹着一个业务判断，可能完全没有数据竞争，却仍然因为检查和执行分离而产生逻辑竞争。

**答题要点：**说明冲突访问、写操作和缺少同步这几个条件；指出硬件读写宽度不能替代 C++ 同步规则。

## 9. 互斥锁：保护一组必须一起成立的状态

**原题关注：**互斥锁解决什么问题，锁的范围怎样决定？

互斥锁让遵守同一把锁规则的线程轮流进入临界区，并提供相应的内存同步。它不会自动阻止没有加锁的代码访问数据，所以读写双方必须遵守相同规则。

```cpp
#include <mutex>

class Counter {
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mutex_);
        ++value_;
    }

    int value() const {
        std::lock_guard<std::mutex> lock(mutex_);
        return value_;
    }

private:
    mutable std::mutex mutex_;
    int value_ = 0;
};
```

读取也加锁，因为另一个线程可能正在修改。`mutable` 允许只读接口为同步而操作互斥锁，不代表对外修改了计数值。

锁的范围要覆盖完整的业务约束。例如“队列不为空就取出一个元素”应该作为一个受保护操作；即使 `empty()` 和 `pop()` 各自加锁，把它们分开调用仍可能在中间被其他消费者改变队列。

范围过大时，线程会因为解析、磁盘 I/O、界面刷新等无关工作相互等待；范围过小时，本来必须一起完成的检查和修改被拆开。常见做法是在锁内取走拥有自己生命周期的数据，锁外做耗时处理。

锁对象要有名字并活到临界区结束。单独写 `std::lock_guard<std::mutex>{mutex_};` 会创建一个随语句结束立刻销毁的临时对象，后续代码并没有受到保护。

**答题要点：**先说保护的是哪份状态和哪条约束，再说明加锁范围；不要用“每个函数都加锁”代替整体推理。

## 10. 死锁：双方都在等对方释放资源

**原题关注：**怎样形成两线程、两把锁的死锁，如何避免？

```cpp
// 错误示意：两个线程使用相反的顺序取得锁。
// 线程 A：锁住 first，接着等待 second。
// 线程 B：锁住 second，接着等待 first。
```

死锁的经典条件是：资源互斥、持有一部分资源同时等待另一部分、不能直接强行夺走资源、形成循环等待。在这个例子中，A 不释放 first 就拿不到 second，B 不释放 second 就拿不到 first，双方都无法继续。

可以采用两类常用策略：所有路径遵守统一的全局加锁顺序；或者需要同时持有多把锁时，用标准库的组合加锁工具。

```cpp
#include <mutex>

std::mutex first;
std::mutex second;

void updateBoth() {
    std::scoped_lock lock(first, second); // C++17
    // 同时保护相关状态。
}
```

`scoped_lock` 对多把锁采用避免这种加锁死锁的策略，离开作用域时释放；其规则见 [scoped_lock 标准说明](https://eel.is/c++draft/thread.lock.scoped)。这不代表任意程序都不会死锁：锁内调用未知回调、重复锁住同一个非递归 mutex、拿着锁等待另一个线程退出，仍可能形成其他等待环。

加 `sleep` 只会改变发生概率。可维护的方案要能解释为什么等待环无法形成。

**答题要点：**画出等待关系，再解释统一顺序或组合加锁如何打破它；补充尽量避免嵌套持锁和锁内调用未知代码。

## 11. `lock_guard` 与 `unique_lock`：固定作用域与灵活持锁

**原题关注：**什么情况下简单的作用域锁不够用？

| 特性 | `std::lock_guard` | `std::unique_lock` |
| --- | --- | --- |
| 常规用途 | 整个作用域持续持锁 | 等待、延迟取得、提前释放或转移锁所有权 |
| 析构时 | 按约定释放所持互斥锁 | 仅在当前拥有锁时释放 |
| 主动 `lock()` / `unlock()` | 不提供 | 提供 |
| 与 `std::condition_variable::wait` 配合 | 不适用 | 使用 `unique_lock<mutex>` |
| 拷贝 | 不可拷贝 | 不可拷贝，可以移动 |

```cpp
#include <mutex>

void example(std::mutex& mutex) {
    std::unique_lock<std::mutex> lock(mutex, std::defer_lock);
    // 当前还没有持锁，此处不能据此访问受保护数据。
    lock.lock();
    // 检查并更新共享状态。
    lock.unlock();
    // 进行不依赖共享状态的耗时处理。
}
```

条件变量等待时需要暂时释放互斥锁，让生产者有机会修改状态；唤醒后又需要重新取得锁。因此需要能够表达“当前是否持锁”的 `unique_lock`。

简单的固定作用域优先使用清晰的 `lock_guard`；需要灵活性时才使用 `unique_lock`。灵活性不是额外的线程安全保证，提前解锁以后不能继续随意访问共享数据。

**答题要点：**解释持锁方式的区别，并用等待或缩小临界区举一个具体场景。

## 12. 原子变量：单个操作正确，不等于整个协议正确

**原题关注：**原子计数与“发布一组普通数据”分别需要什么？

原子变量适合计数器、标志或经过设计的状态转换。下面的一次原子读改写，可以避免多个线程的计数更新互相覆盖：

```cpp
#include <atomic>
#include <cstdint>

std::atomic<std::uint64_t> received{0};
void countOne() {
    received.fetch_add(1, std::memory_order_relaxed);
}
```

这里如果只关心计数本身，`relaxed` 可以满足需求。它不自动发布计数以外的数据；原子类型是否无锁也取决于类型与实现，不能把 `atomic` 一律理解为“没有锁且一定更快”。

`count.store(count.load() + 1)` 是两次原子操作，不等于一次原子自增：两个线程可能读到相同旧值并写回相同新值。这通常是逻辑上的更新丢失，不能因为每一步都是原子操作就认为整体正确。

发布普通数据时，需要建立跨线程的顺序关系。下面是一个**完整的 C++17 一次性发布示例**：

```cpp
#include <atomic>
#include <iostream>
#include <string>
#include <thread>

int main() {
    std::string data;
    std::atomic<bool> ready{false};

    std::thread producer([&] {
        data = "packet parsed";
        ready.store(true, std::memory_order_release);
    });

    std::thread consumer([&] {
        while (!ready.load(std::memory_order_acquire)) {
            std::this_thread::yield();
        }
        std::cout << data << '\n';
    });

    producer.join();
    consumer.join();
}
```

推理链是：写入 data，随后 release 发布 ready；消费者 acquire 读到这次发布的值后，才读取 data。相应同步关系让发布前的数据写入对后续读取成立。默认的 `seq_cst` 原子读写也可以满足这个简单场景；单纯把标志改为 relaxed 则不能提供这组普通数据所需的发布关系。[原子内存顺序的标准定义](https://eel.is/c++draft/atomics.order)给出了 release/acquire 的条件。

这个例子假设只有一次发布，发布后不再并发修改 data。若生产者循环覆写 data，消费者还在读，单个 ready 标志并不能自动让重复交接安全。真实的连续报文交接更适合用队列或正确同步的快照。示例中的自旋只用于展示顺序，长时间等待更适合条件变量等阻塞等待工具。

**答题要点：**先说原子保护什么，再说数据发布需要什么顺序；能说明一次性交接的前提和循环复用的额外风险。

## 13. 条件变量：等待状态满足，不是保存一次通知

**原题关注：**为什么必须检查谓词？通知早于等待怎么办？

条件变量可以让线程在没有工作时睡眠，状态变化后再唤醒。但它不替你保存“已经有一个通知”的业务事实，**真正应该保存的是共享状态**。

下面是消费者一侧的典型结构，`ready` 和 `value` 都由同一把互斥锁保护：

```cpp
#include <condition_variable>
#include <mutex>

std::mutex mutex;
std::condition_variable changed;
bool ready = false;
int value = 0;

int consume() {
    std::unique_lock<std::mutex> lock(mutex);
    changed.wait(lock, [] { return ready; });
    return value;
}

void produce() {
    {
        std::lock_guard<std::mutex> lock(mutex);
        value = 42;
        ready = true;
    }
    changed.notify_one();
}
```

`wait(lock, predicate)` 在等待前检查条件，等待期间原子地完成“释放锁并进入等待”，返回前重新取得锁，并再次检查谓词。不带谓词时，调用者需要自己写检查循环。[条件变量的标准规定](https://eel.is/c++draft/thread.condition.condvar)允许虚假唤醒，所以醒来不代表业务条件已经满足。

即使是正常通知，另一个消费者也可能先取走工作，因此队列条件仍要重新检查。若生产者先执行，`ready` 已经为 true，消费者后来检查时便不需要睡眠；关键在于状态检查与修改遵守同一把锁的协议。

等待标志还要包含退出条件。只等“队列非空”，停止时队列为空，线程可能永远醒不过来。第 14 题将把关闭状态放进等待谓词。

**答题要点：**通知用来促使重新检查，状态决定是否能继续；使用同一把锁保护谓词，循环检查，并纳入停止条件。

## 14. 生产者—消费者队列：交接数据，也交接责任

**原题关注：**收包和解析怎样协作，消费跟不上时怎么办？

一个常见模型是：接收线程取得一份拥有独立生命周期的报文，放入队列；解析线程取出报文，再在队列锁外进行解析。队列必须保护容器本身，并保证消费者等待和关闭逻辑正确。

下面是一份 **C++17 有界报文队列的教学实现**。它选择“满时拒绝新报文，关闭后排空已有报文”的策略。它展示同步协议，不是无分配的高性能队列；容器分配仍可能失败并抛异常，需要由调用边界处理。

```cpp
#include <condition_variable>
#include <cstddef>
#include <cstdint>
#include <mutex>
#include <optional>
#include <queue>
#include <stdexcept>
#include <utility>
#include <vector>

using Datagram = std::vector<std::uint8_t>;
enum class PushResult { accepted, full, closed };

class DatagramQueue {
public:
    explicit DatagramQueue(std::size_t capacity)
        : capacity_(capacity) {
        if (capacity == 0) {
            throw std::invalid_argument("capacity must be positive");
        }
    }

    PushResult tryPush(Datagram data) {
        std::unique_lock<std::mutex> lock(mutex_);
        if (closed_) return PushResult::closed;
        if (queue_.size() >= capacity_) return PushResult::full;
        queue_.push(std::move(data));
        lock.unlock();
        changed_.notify_one();
        return PushResult::accepted;
    }

    std::optional<Datagram> pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        changed_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });
        if (queue_.empty()) return std::nullopt;
        Datagram data = std::move(queue_.front());
        queue_.pop();
        return std::optional<Datagram>{std::move(data)};
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            closed_ = true;
        }
        changed_.notify_all();
    }

private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable changed_;
    std::queue<Datagram> queue_;
    bool closed_ = false;
};
```

阅读代码时注意五点：

1. 检查队列大小与入队在同一临界区，避免多个生产者同时突破容量。
2. `pop()` 返回数据的所有权，不返回队列元素的引用，避免解锁后引用失效。
3. `close()` 唤醒等待者；队列空且关闭时，`pop()` 返回空结果，消费者可以退出。
4. 关闭不立即丢弃已有数据；消费者继续取出剩余元素，再结束。立即取消需要另一套明确策略。
5. 析构队列之前，外部必须确保所有访问它的线程都已退出；`close()` 本身不等于线程已经结束。

`tryPush` 按值接收报文。如果调用者传入 `std::move(packet)`，即使返回 full，该实参也已经交给函数并可能被销毁，不能依赖原 packet 仍有内容。这个接口选择了拒绝时直接丢弃传入数据；若业务需要重试，就应该设计能保留或退还数据的接口。

仅限制条数不一定限制总字节数，还要限制报文长度或累计字节。生产长期快于消费时，扩大队列只能推迟问题。可选策略包括拒绝新数据、丢旧数据、合并同类状态、降低上游速率或增加真正有效的处理能力。对 UDP 接收线程阻塞等待队列空间，并不会自动让远端减速，反而可能让内核接收缓冲区溢出。

**答题要点：**涵盖数据所有权、同一把锁、等待谓词、容量策略和关闭后行为，不能只说“加个 mutex”。

## 15. 线程的启动与退出：请求停止、完成执行、回收管理是三件事

**原题关注：**`thread`、`join`、`detach` 与 `jthread` 分别承诺什么？

`std::thread` 对象与它代表的执行线程不是同一个概念。线程函数可能已经执行完，但只要还没有 `join()` 或 `detach()`，对应的 `thread` 仍可能是 joinable。若 joinable 的 `std::thread` 对象析构，将调用 `std::terminate()`，而不是自动等待；见 [thread 析构规则](https://eel.is/c++draft/thread.thread.destr)。

| 操作 | 做了什么 | 没有自动解决什么 |
| --- | --- | --- |
| `join()` | 等待目标线程完成，并结束当前对象对它的关联 | 不会替你要求线程停止 |
| `detach()` | 放弃通过该 thread 对象等待执行线程 | 不保证被访问的数据继续存活，也不负责业务清理 |
| 发出停止请求 | 通知任务希望结束 | 不保证任务已响应或已完成 |

一个 `while (true)` 的线程，即使调用 `join()` 也不会自己结束。相反，只调用停止标志、不等待完成，就马上销毁队列，也仍然可能出现悬空访问。

C++20 的 `std::jthread` 在仍然 joinable 时，析构会先请求停止再 join。其停止机制是协作式的：线程代码要检查 `stop_token` 或使用与它配合的等待方式。[jthread 析构规则](https://eel.is/c++draft/thread.jthread.cons)没有提供强制杀死线程的语义。

下面是一个**完整的 C++20 示例**：

```cpp
#include <chrono>
#include <stop_token>
#include <thread>

int main() {
    std::jthread worker([](std::stop_token stop) {
        while (!stop.stop_requested()) {
            // 实际任务应当按有限工作量分批处理。
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
        }
    });

    worker.request_stop();
    worker.join();
}
```

停止请求不会自动打断 `sleep_for`，也不会自动解除普通 `condition_variable::wait` 或任意阻塞 Socket 调用。需要相应的唤醒或取消方案：例如关闭并唤醒队列、使用支持停止令牌的等待方式、在所属线程处理 Socket 停止，或使用有界等待。

若类内的工作线程访问类成员，必须在线程真正退出后再销毁那些成员。成员按声明逆序析构可以帮助安排生命周期，但显式设计停止、唤醒、等待顺序更容易审查。不要持有线程退出所需的互斥锁去 `join()`，也不能让线程等待自己结束。

**答题要点：**能区分 joinable 与“正在运行”；说明 `jthread` 减少漏 join 的风险，但仍需要正确的停止协议。

## 16. 线程中的异常：异常不会自动跳回创建者

**原题关注：**后台抛异常后，谁负责捕获和报告？

创建线程处的 `try/catch`，主要捕获创建过程中发生的失败，不会自动捕获后台线程日后抛出的异常。普通 `thread` 或 `jthread` 的线程入口如果让异常逃逸，将调用 `std::terminate()`。

因此应在线程任务边界捕获异常，把失败变成明确的结果或事件。下面是一个**完整的 C++17 示例**：

```cpp
#include <exception>
#include <iostream>
#include <stdexcept>
#include <thread>

int main() {
    std::exception_ptr error;

    std::thread worker([&] {
        try {
            throw std::runtime_error("解析任务失败");
        } catch (...) {
            error = std::current_exception();
        }
    });

    worker.join();

    try {
        if (error) std::rethrow_exception(error);
    } catch (const std::exception& ex) {
        std::cout << ex.what() << '\n';
    }
}
```

这里 `error` 不需要额外互斥锁的前提是：只有该工作线程写它，主线程只在成功 join 之后读取。线程完成与 join 建立了相应顺序。如果主线程在线程运行期间也读 error，或者多个工作线程同时写它，就必须重新设计同步。

工程里可以使用 `promise/future` 传递结果或异常，也可以发送带上下文的错误消息。不要只打印一行“出错了”后继续运行，却留下其他线程永远等待。发生不可恢复错误时，应更新停止状态，唤醒相关等待者，保存必要信息，并按退出协议清理。

还要区分异常与普通业务失败：收到一个非法报文可能只需增加错误计数并跳过；持续的资源失败可能需要停止模块。错误上报通道本身应尽量可靠，尤其不要依赖一个已经被销毁的界面对象。

**答题要点：**说明线程边界捕获、结果传回、其他线程的唤醒和资源清理；不要把“捕获后忽略”作为通用策略。

## 17. 线程、任务与结果：分别考虑执行、完成和取消

**原题关注：**需要返回值、异常和取消时，怎样组合工具？

| 工具 | 主要角色 | 适合思考的问题 |
| --- | --- | --- |
| `std::thread` / `std::jthread` | 管理一个执行线程 | 谁启动它，谁让它退出，谁等待它结束？ |
| `std::async` | 启动一个可获得结果的任务 | 是否真的异步执行，结果何时被取走？ |
| `std::future<T>` | 取得某个异步结果或异常 | 什么时候可以等待，等待会不会阻塞关键线程？ |
| `std::promise<T>` | 从生产一侧设置结果或异常 | 所有执行路径会不会最终报告完成？ |

一次性计算可以这样表达：

```cpp
#include <future>

void example() {
    auto result = std::async(std::launch::async, [] {
        return 6 * 7;
    });
    int value = result.get(); // 若任务抛异常，这里会重新抛出。
    (void)value;
}
```

显式 `std::launch::async` 表达异步执行要求。默认策略允许延迟执行，不能假设任务一调用就已在后台工作。普通 `future` 通常只允许 `get()` 取结果一次，取完后不再有效；需要多个消费者共享同一结果时，另有 `shared_future` 等机制。

必须留意两个阻塞位置：`get()` 可能等待任务完成；由 async 异步启动任务产生的共享状态，在释放最后一个相关引用等条件下，析构也可能等待任务结束。不能把一个临时 async 返回值随手丢掉，就认为它一定是自由运行的后台任务。[async 标准说明](https://eel.is/c++draft/futures.async)解释了策略和共享状态的行为。

`future.wait_for()` 超时只说明没有等到结果，不会自动取消任务。若需要结果、错误和取消，可以组合：

1. 由 `jthread` 管理执行与协作式停止。
2. 将 `promise` 移入工作任务，调用者持有对应的 future。
3. 成功时设置结果，失败时设置异常，取消时设置明确的取消状态或异常。
4. 所有路径都结束任务，控制方最终等待线程完成。

Qt GUI 线程不宜直接调用可能长时间阻塞的 `get()`；可以通过完成信号或其他非阻塞调度方式交接结果。不要为每个高频 UDP 报文创建一个 async 任务；任务数量、调度成本和资源上限都需要设计。

**答题要点：**把执行线程、结果通道、停止协议拆开说明，再按任务长短与频率组合，而非把 future 当成线程本身。

## 18. Qt 线程与事件循环：对象在哪个线程，调用就要遵守哪里的规则

**原题关注：**GUI、网络对象和耗时任务怎样分工，数据怎样安全交接？

事件循环可以理解为一个不断取出事件并执行处理函数的调度循环。`readyRead`、定时器和排队的跨线程槽调用都依赖相应调度。如果某个处理函数一直不返回，后面的事件就可能无法及时处理。

`QWidget` 等 GUI 对象应在 GUI 主线程中使用。`QUdpSocket`、`QTimer` 等事件驱动对象，应遵守其线程归属和事件循环要求。不能因为给跨线程调用包上一把 mutex，就忽略它们对所属线程的要求。[Qt 的线程与 QObject 文档](https://doc.qt.io/qt-6/threads-qobject.html)说明了这些约束。

Qt 文档中的“可重入”通常表示不同线程可以使用各自独立的数据或对象实例；它不等于多个线程可以随意同时操作同一个实例。阅读网络类文档时，要区分这一点与明确标注的线程安全接口。[Qt 对这两个术语的定义](https://doc.qt.io/qt-6/threads-reentrancy.html)值得单独看一次。

这里有两个经常混淆的概念：

- `QThread` 管理的执行线程，与 `QThread` 这个 QObject 实例的线程归属不同。后者通常仍在创建它的 GUI 线程。
- 普通 C++ 方法调用不会自动切换线程。即使 worker 已经 moveToThread，GUI 中直接调用 `worker->doWork()`，这次调用仍在调用者线程执行。

常用的 worker 对象模式是：先创建一个无父对象的 worker，将它移动到工作线程；让启动槽在工作线程执行，并在该槽中创建以 worker 为父对象的 Socket。这样 Socket 从创建开始就属于正确线程。对象的普通 C++ 成员若没有建立父子关系，不会因为 worker 移动就自动全部迁移。

跨线程传结果可以用带接收上下文的排队连接：

```cpp
// 示意：Receiver、Window 以及它们的信号/槽由实际工程定义。
QObject::connect(receiver, &Receiver::sampleReady,
                 window, &Window::applySample,
                 Qt::QueuedConnection);
```

排队槽在接收对象所属线程的事件循环中执行。传递自定义值类型时，要满足元类型和复制要求，必要时用 `Q_DECLARE_METATYPE`、`qRegisterMetaType` 注册。[QObject 的线程归属说明](https://doc.qt.io/qt-6/qobject.html#thread-affinity)也提醒：没有运行中的接收线程事件循环，排队调用无法正常交付。

传值或持有不可变数据通常比传裸地址容易保证生命周期。把一个裸指针作为信号参数复制到队列，并不复制其指向的数据；发送方复用或销毁缓冲区，接收方仍可能拿到失效内容。

正常读取待收 UDP 数据，通常会处理所有当前挂起的数据报；[QUdpSocket 官方说明](https://doc.qt.io/qt-6/qudpsocket.html)也提供了这种读取结构。高频持续流量下，单次回调若无休止地循环，也可能推迟停止和其他事件。需要时可限制单次处理预算，并显式安排后续继续读取；不能单纯留下未读报文，然后假设一定会重新收到一次 readyRead。

若收包、重解析和绘制都在 GUI 线程，一次耗时操作就可能同时拖慢界面与通信。可以先把收包与解析移到工作侧，再根据测量决定是否继续分线程。线程不是越多越好，跨线程交接也有成本。

**答题要点：**说明 GUI 线程、对象归属、事件循环与排队连接，并解释传递数据时的生命周期，而不仅是“用信号槽”。

## 19. 高频 UDP 与背压：队列能缓冲波动，不能消除持续超载

**原题关注：**怎样确定瓶颈，怎样面对界面跟不上的情况？

把链路拆成几个有边界的阶段，分别观察：

| 位置 | 建议记录的数据 | 帮助回答的问题 |
| --- | --- | --- |
| 从 Socket 读出 | 报文数、字节数、序号、读取错误 | 应用实际取到了多少数据？ |
| 报文队列入口 | 接受数、满队列拒绝数、关闭拒绝数 | 是否在自己的交接队列丢弃？ |
| 队列内部 | 当前/最大长度、等待时间 | 是否持续积压，延迟从哪里增加？ |
| 解析任务 | 成功数、失败数、处理耗时 | 是否计算太慢或数据不符合协议？ |
| GUI 显示 | 实际刷新频率、状态滞后、事件积压 | 是否只是显示更新跟不上？ |

统计口径和时间窗口要一致，停止输入后要考虑排空在途和排队数据。只有在同一批序号、同一统计边界下，计数关系才容易解释。Wireshark 抓包数与应用接收数之差，只是进一步调查的线索，不能单凭差值断定内核丢了多少。

假设每秒输入 10,000 条，解析只能完成 8,000 条，无界队列就会以约 2,000 条/秒增长。扩大队列只是延后耗尽内存的时间，也使旧数据越来越晚被处理。要解决长期超载，必须降低输入、减少每条工作量、增加有效处理能力，或实施符合业务语义的取舍。

界面尤其要区分两类数据：

- **最新状态：**例如当前温度或当前位置，GUI 可以周期性取得最新快照，中间未显示的旧状态可以合并。
- **不可遗漏事件：**例如告警、操作确认或需要留存的记录，不能因为“界面只显示最新值”就悄悄抛弃，需要独立的保存或可靠处理策略。

如果解析结果每秒产生 10,000 次，却给 GUI 发 10,000 个排队更新，界面很可能承担大量无意义工作。对最新状态，可以用受保护的快照和 GUI 定时读取，或使用“至多一个待处理通知”的合并机制。后者仍需设计正确的并发协议，单纯换成 queued signal 并不自带容量限制。

背压表示下游能力对上游产生约束。在进程内可以阻塞或拒绝生产者；在普通 UDP 链路上，接收方暂停读取并不会自动让远端减速。需要发送方限速、应用协议反馈或明确丢弃策略，才能真正控制流量。

**答题要点：**先按阶段建立证据，再选择限流、合并或丢弃；方案必须匹配数据语义，并且所有主动丢弃可统计。

## 20. 综合设计：一个可持续收包，也能可靠退出的模块

**原题关注：**把线程分工、所有权、同步、错误处理、容量和排障连成一个可解释的系统。

下面是一种学习用架构。它不是每个项目的唯一答案；先从简单结构测量，只有明确需要时再增加线程和队列。

```mermaid
flowchart LR
    A[设备] -->|UDP| B[I/O 线程：QUdpSocket]
    B --> C[有界报文队列]
    C --> D[解析线程]
    D --> E[受锁保护的最新状态]
    E -->|定时读取快照| F[GUI 线程：显示]
```

**第一步：明确所有权和线程职责。**

| 对象/资源 | 生命周期与访问规则 |
| --- | --- |
| GUI 控制器 | 负责启动与停止；服务成员一直活到相关线程完全退出 |
| I/O worker | 属于 I/O 线程，负责创建、绑定、读取和关闭 Socket |
| QUdpSocket | 在 I/O 线程创建，以 worker 为父对象，在同一线程使用 |
| 有界报文队列 | 由服务拥有，收包与解析线程按队列接口同步访问 |
| 原始报文 | 入队时转交一份有所有权的数据，出队后由解析任务持有 |
| 最新状态快照 | 由短临界区保护；GUI 复制快照后在锁外更新界面 |
| 线程管理对象 | 由控制层持有，相关共享状态销毁前完成 join/wait |

这里完全可以让线程借用服务成员，而不是处处用 shared_ptr。前提是控制层严格保证“先让线程结束，后销毁被借用数据”。如果做不到，必须重新明确生命周期，而非依靠猜测。

**第二步：明确运行流程。**

I/O worker 在自己的事件循环中收包，只做轻量校验、记录必要元数据并尝试入队。队列满时记录拒绝，不无限增长。解析线程取出报文，在队列锁外解析。普通遥测状态更新到最新快照，GUI 按合适频率读取；需要完整保存的事件走单独设计的处理通道。

锁仅保护队列容器或快照交接，不跨越耗时解析、绘制或等待线程结束。报文保留序号，便于把接收、入队、解析等计数对齐。解析错误与资源失败分别报告，避免单个非法报文直接终止整个接收服务。

**第三步：设计停止顺序。**

这里选择“停止接收后，排空已经接受的报文”。一种可行流程是：

1. GUI 控制器进入 stopping 状态，禁止重复启动，并停止继续安排显示更新。
2. 向 I/O worker 排队提交停止操作；操作在其线程执行，标记不再接收新工作，并关闭 Socket。
3. I/O worker 关闭报文队列，唤醒解析线程；然后结束自己的事件循环。这个关键清理过程不应依赖 GUI 再执行一个回调才能继续。
4. 解析线程处理已入队报文。看到队列关闭且排空后退出；它不能等待 GUI 确认每次显示才完成退出。
5. 控制器确认工作完成，再 join 解析线程、wait I/O 线程，最后释放队列、快照和其他被借用状态。

有些步骤可能并行完成，必须保持的是依赖关系：不再产生新工作，唤醒等待者，等待使用者结束，最后销毁资源。为保持界面响应，可以先异步观察完成，再做最终等待。若 GUI 线程同步等待，必须确保工作线程不会反过来等待 GUI 执行某个槽，否则可能相互等待。

Qt 的 worker 清理常采用下面的连接，符合 [QThread 官方 worker 示例](https://doc.qt.io/qt-6/qthread.html#details)：

```cpp
QObject::connect(&ioThread, &QThread::finished,
                 worker, &QObject::deleteLater);
```

这不是“在任意时刻调用 deleteLater 都必定及时销毁”的承诺。要按 Qt 的生命周期机制安排清理，不能在事件循环已经停止后随意投递清理工作并期待其正常执行，也不能在工作线程仍使用对象时直接销毁它。

若业务要求立即取消而不是排空，就要明确记录被放弃的报文、唤醒所有等待者，并让解析任务在安全边界退出。队列的关闭、jthread 的停止请求和线程结束不是同一事件，需要选择一致的策略。

**第四步：按证据定位故障。**

偶发丢报文时，先核对测试负载、发送序号和统计窗口，再看 Socket 实际读取数、入队拒绝数、解析失败数与队列等待。配合抓包、系统 UDP 统计、CPU 与线程状态，逐层缩小范围。界面刷新次数少，不一定代表原始数据丢失，因为状态显示可能采用了合并策略。

退出崩溃时，保存调用栈，记录停止请求、Socket 关闭、队列关闭、线程完成和关键对象析构的时间与线程 ID。重点检查悬空捕获、复用缓冲区、跨线程删除 Qt 对象、等待者未唤醒、未 join 的线程和先销毁共享状态等问题。

在支持的平台和工具链上，可使用地址检查、线程竞争检查或调试器辅助定位；工具支持随平台而异，没有报告也不构成安全证明。应先通过日志和线程关系验证生命周期，再对可疑路径制作最小复现。

**答题要点：**给出一套从启动、运行、超载、出错到退出都能解释的方案。关键不是画出多少线程，而是每次交接和销毁都有明确的前提。

## 学完后可做的四个小实验

这些实验可以帮助你把文字转成可验证的理解，不要求一口气做完。

1. **生命周期记录：**为一个 Packet 类打印构造、移动和析构。分别观察局部对象、unique_ptr 和按值捕获任务的销毁顺序。不要把某次打印顺序推广成没有同步保证的线程先后顺序。
2. **安全计数：**先用 mutex 实现计数器，再用原子 fetch_add 实现。让多个线程完成固定数量的更新，join 后检查总数。比较实现与成本，不需要通过运行有数据竞争的版本来“证明它偶尔会错”。
3. **队列关闭：**用第 14 题队列验证空队列关闭、满队列拒绝、关闭后排空三种路径；确认消费者最终退出，再销毁队列。
4. **GUI 更新：**在一个小型 Qt 示例中比较每包更新与定时读取最新状态。记录收包、解析、队列和界面响应，观察合并显示与丢失原始数据的区别。

## 回答 20 题时可反复使用的检查框架

描述任何并发模块时，尝试依次回答：

- **所有权：**每个对象由谁持有，什么时候可能销毁？
- **访问者：**有哪些线程读写同一份状态？
- **同步：**哪把锁或哪种发布关系保证顺序，是否覆盖整个约束？
- **等待：**等待什么条件，谁修改它，停止时谁唤醒？
- **容量：**工作积压在哪里，超限时怎样处理？
- **完成：**谁等待线程真正退出，最后怎样清理资源？
- **证据：**发生异常时，哪些计数、时间点和调用栈可以验证推断？

## 容易混淆的说法

| 常见说法 | 更准确的理解 |
| --- | --- |
| 有指针就能用对象 | 还必须保证被指向对象存活，并且访问满足同步规则 |
| shared_ptr 线程安全 | 要区分不同句柄、同一变量和被管理对象 |
| std::move 之后一定移动 | 它允许参与移动重载选择，实际行为取决于类型 |
| 原子变量能保护旁边所有数据 | 还需要正确的发布关系与后续修改协议 |
| 通知一次就一定有一个任务 | 条件变量通知不代替共享状态与等待谓词 |
| close 队列就是结束线程 | close 只是改变状态并唤醒，仍需确认线程完成 |
| join 会让线程停止 | join 等待结束，停止由任务协议控制 |
| jthread 一定很快析构 | 它可能等待不响应停止或仍在阻塞的任务 |
| queued signal 自动限制积压 | 接收线程仍可能被大量事件淹没，需要合并或容量策略 |
| 试了很多次都没崩就安全 | 生命周期与同步需要有规则依据，测试只能补充证据 |
