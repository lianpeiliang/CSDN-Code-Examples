## 先建立一张排障地图

可以把发送报文想成寄一封信：应用程序写信，Socket 把信交给本机系统，网络负责运输，对端系统按地址和端口找到收件箱，接收代码取信，业务代码读懂内容。

不过，类比只能帮助入门：UDP 没有自动提供“签收回执”，中间也可能丢失、重复或乱序。

```text
发送端业务生成报文                         接收端业务得到有效结果
    │                                              ▲
    ▼                                              │
UDP 发送 API                                  校验、过滤、解析
    │                                              ▲
    ▼                                              │
发送端内核：UDP/IP、路由、邻居解析              应用读取 Socket 数据报
    │                                              ▲
    ▼                                              │
驱动、网卡、发送队列                          内核匹配并放入接收队列
    │                                              ▲
    └──── 网络路径：交换机、路由器、无线链路 ──► 网卡、驱动、接收协议栈

抓包是旁路观察：在特定接口和捕获位置取得报文副本。
抓包位置与防火墙、卸载、协议栈之间的先后关系依平台而异。
```

“分层排障”关注的是**实际经过的组件和证据边界**，不用为了套 OSI 七层而把每个函数硬塞进某一层。

以后遇到“收到没有”，先追问一句：**在哪个位置算收到？**

| 证据 | 能支持的结论 | 不能单独证明的事 |
| --- | --- | --- |
| `writeDatagram()` 返回完整长度 | 本次发送被本机发送接口成功接受 | 报文已上物理链路、到达对端或处理成功 |
| 发送端本机抓包看到 | 发送侧捕获位置看到了对应报文 | 网卡最终确实把它发送到线上 |
| 接收端正确接口抓包看到 | 接收侧捕获位置观察到了对应报文 | 报文通过所有内核检查并进了目标 Socket |
| `receiveDatagram()` 得到有效数据报 | 该 Socket 已把报文交给应用读取 | 协议字段正确、业务已接受 |
| 解析成功且业务计数增加 | 报文到达了定义好的业务完成点 | 如果还要落盘、显示或回执，这些后续步骤也已成功 |

本文中的 `192.168.10.10`、`192.168.10.20`、端口 `45454` 都是实验示例，使用时替换为实际地址。`0.0.0.0` 是本地绑定通配地址，不是让发送方发送到“任意机器”的目的地址。

## 第一部分：通信路径与基本概念

### 1. 一条报文经过哪些环节？

**先理解：发送 API 是起点之一，不是整条通信链路。**

以两台电脑的 IPv4 单播为例：

1. 发送业务按协议编码字段，生成一段字节。
2. `QUdpSocket::writeDatagram()` 把负载和目标地址、端口提交给本机网络栈。
3. 系统处理 UDP/IP，查路由，选择出口和源地址。以太网场景还可能需要 ARP 查出下一跳 MAC。
4. 驱动和网卡把报文发出；交换机、路由器等设备按各自规则转发。
5. 对端网卡和驱动接收，协议栈完成相应检查；可能涉及 IP 分片重组、防火墙和 UDP 校验。
6. 系统根据地址族、本地地址、端口以及可能的对端限制等条件，寻找接收 Socket。
7. 数据进入 Socket 接收队列；Qt 的事件机制通知可读，应用执行接收操作。
8. 应用检查长度、来源、协议版本和字段，最后完成业务处理。

本机回环和虚拟网络的实际路径会不同，不一定经过物理网卡。硬件卸载也可能改变某些处理发生的位置。

**应该在哪些地方留下证据？**

| 位置 | 建议记录 |
| --- | --- |
| 编码完成 | 本轮测试 ID、序号、负载长度、目标地址与端口 |
| 发送调用后 | 返回值、失败错误码、成功/失败计数 |
| 两端抓包 | 对应序号、接口、方向、地址、端口、捕获时间 |
| 接收 API 后 | 读取数、实际字节数、来源、原始数据摘要 |
| 业务处理后 | 接受数、过滤数、解析失败数及原因 |

**参考回答：**报文从业务编码经过 Socket、发送协议栈、路由、驱动和网卡，再经过网络路径到对端网卡和协议栈，匹配接收 Socket 后由应用读取、解析。我会在发送调用、两端抓包、Socket 读取和业务接受位置分别记录同一测试 ID 和序号。

**常见误区：**把“调用了发送函数”写成“对端已收到”，跳过中间所有可能出错的环节。

### 2. “发出去了”具体指什么？

**先把这句话拆成不同层次。**

```cpp
const qint64 n = socket.writeDatagram(payload, targetAddress, targetPort);
if (n != payload.size()) {
    qWarning() << "send failed" << n << socket.error()
               << socket.errorString();
}
```

UDP 是数据报接口，成功时应检查返回长度等于整条负载长度；失败时记录错误。不要把 UDP 当 TCP，遇到异常返回就把“剩余字节”另发一次，否则会变成另一条数据报。

成功返回表示本机发送接口接受了本次数据，不包含对端签收语义。之后仍可能遇到出口队列丢弃、网络拥塞、防火墙丢弃、对端无匹配 Socket 等问题。

如果想逐层确认：

- **到达发送侧捕获点：**本机正确出口抓到该序号。它仍可能发生在驱动或硬件真正发送之前。
- **确实经过物理链路：**在外部 TAP 或已正确配置的交换机镜像位置取证，并核实监测设备自身没有漏抓。网卡发送计数的变化可作辅助，但通常不是逐报文证明。
- **到达对端接收侧：**对端正确接口抓到同一序号，结合接口和捕获位置解释其含义。
- **到达对端应用：**对端读取日志记录了该序号。
- **业务处理成功：**对端处理完成日志，或由协议定义的应用 ACK 证明。ACK 也可能丢失，收到 ACK 与没收到 ACK 的证据强度不同。

**参考回答：**UDP 发送成功只说明本机接口成功接受了报文。我要用发送侧和接收侧抓包确认观察到的位置，再用对端接收与处理日志确认应用交付。需要严格证明上物理链路时，应增加独立的外部观测点。

**常见误区：**把 `bytesWritten()`、发送成功日志或本机出站抓包当成远端送达保证。

### 3. 抓包和 Socket 收包有什么区别？

**Wireshark 是观察者，Socket 是系统按规则投递的接收端点。**

Windows 上 Wireshark 通常通过 Npcap 获取接口流量副本；Qt 通常通过操作系统的 Socket API 获取已经交付给该 Socket 的 UDP 数据。

```text
某接口捕获路径 ──► Npcap / Wireshark ──► pcapng 文件

操作系统接收路径 ──► 检查与匹配 ──► UDP Socket 队列 ──► Qt 读取
```

上图强调两条观察路径，不规定所有系统上的精确执行先后。不能简单断言“Wireshark 永远在防火墙前面”。

抓到的数据可能是：

- 目的端口不是本程序的端口。
- 目的 IP 不是本机应接收的单播地址；在镜像或混杂捕获场景能看到，不代表内核要投递给本机应用。
- 正确到达捕获位置，但后来被安全策略、协议检查或接收队列限制影响。
- 已经进入 Socket 队列，但 Qt 所在线程长时间没有执行接收代码。

**参考回答：**Wireshark 通过捕获机制观察接口上的报文副本，Qt 通过 Socket 取得操作系统投递的数据。两者的筛选条件和观察位置不同，因此抓到报文只能证明捕获点看到了它，不能证明目标 Socket 已收到。

**常见误区：**看到 Wireshark 有一行 UDP 就停止检查目标地址、端口和本机绑定。

### 4. IP 地址和端口组成了什么？

假设抓到：

```text
IPv4 UDP
192.168.10.10:50000  →  192.168.10.20:45454
源 IP        源端口     目标 IP        目标端口
```

源 IP 和源端口表示这条报文在当前观察位置上的发送端点；目标 IP 和目标端口表示目的端点。加上协议 UDP，可以把它作为常说的“五元组”。NAT、隧道或地址转换可能使不同位置看到的字段不同。

普通单播接收端通常应：

```cpp
socket.bind(QHostAddress("192.168.10.20"), 45454);
// 或在 IPv4 场景绑定所有本地 IPv4 地址：
socket.bind(QHostAddress::AnyIPv4, 45454);
```

绑定对应的是**报文的目标地址和目标端口**。它不是把远端设备 IP 填入本地绑定地址。若绑定远端地址，通常会因该地址不属于本机而失败。

发送方若未固定本地端口，系统通常自动选择临时源端口，所以不能假定源端口也等于 `45454`。如果对 UDP Socket 调用了 `connectToHost()`，还应检查其对端限制；这不是 TCP 式握手，不代表对端服务存在。

**参考回答：**源和目标 IP、端口分别标识两端端点；接收 Socket 的本地端口要匹配目标端口，本地绑定地址要能接收该目标地址，并匹配地址族。远端 IP 不应拿来作为本机 `bind()` 地址。

**小练习：**程序绑定 `127.0.0.1:45454`，设备向 `192.168.10.20:45454` 发包。端口虽然一致，绑定地址却不匹配，不能据此期待收到。

### 5. 怎样确认程序真的绑定成功？

**第一步看返回值，第二步看实际状态，第三步交叉检查系统端点。**

```cpp
const bool ok = socket.bind(QHostAddress::AnyIPv4, 45454,
                           QAbstractSocket::DontShareAddress);
if (!ok) {
    qCritical() << "bind failed" << socket.error() << socket.errorString();
    return;
}
qInfo() << "bound" << socket.localAddress() << socket.localPort()
        << "address_family" << socket.localAddress().protocol()
        << "state" << socket.state();
```

示例使用独占绑定，便于先排除重复进程。`bind()` 失败后应停止依赖该绑定的接收流程。`isValid()` 不能替代“绑定到预期地址端口”的检查。若端口传 `0`，系统会分配端口，要读 `localPort()` 才知道实际值。

在 Windows PowerShell 中交叉检查：

```powershell
Get-NetUDPEndpoint -LocalPort 45454 |
    Select-Object LocalAddress,LocalPort,OwningProcess

# 将 1234 替换为上一步查到的 OwningProcess。
Get-Process -Id 1234
```

如果没有相应 cmdlet，可用 `netstat -ano -p udp`，再核对端口与 PID。UDP 端点不像 TCP 监听端点那样依赖 `LISTENING` 字样来判断是否绑定。

另一个进程占用端口时，独占绑定通常失败并报告地址/端口已使用或访问受限一类错误。实际结果还取决于平台、绑定地址和共享选项；共享绑定也不保证多个程序各收到相同单播副本。

**参考回答：**我会检查 `bind()` 返回值，失败时保存错误码和错误文字；成功后记录本地地址、端口、地址族和状态，并用系统 UDP 端点和 PID 交叉核对。端口冲突时先确定占用者及共享模式，不直接加复用标志掩盖问题。

官方定义可查 [QAbstractSocket 的绑定、状态与错误说明](https://doc.qt.io/qt-6/qabstractsocket.html)；系统端点查询见 [Get-NetUDPEndpoint](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netudpendpoint)。

## 第二部分：地址、接口与网络路径

### 6. 绑定特定地址和绑定所有地址有什么区别？

**绑定具体地址是在限制本地接收目的地址，通配绑定是在扩大匹配范围。**

| 绑定方式 | 适用理解 | 需要核实 |
| --- | --- | --- |
| `127.0.0.1:45454` | 只接收相应 IPv4 回环目标 | 外部设备发到网卡 IP 的报文不匹配 |
| `192.168.10.20:45454` | 只匹配这个本地 IPv4 目标地址的普通单播 | 地址必须确实在本机，且仍有效 |
| `AnyIPv4:45454` | 匹配本地 IPv4 通配地址和端口 | 仍受系统投递规则、防火墙等条件影响 |
| `AnyIPv6:45454` | IPv6 通配地址 | 不要拿它当然接收 IPv4 测试包 |
| `Any:45454` | Qt 的任意 IP/双栈绑定用法 | 实际地址族及平台行为；IPv4 组播应按 Qt 要求使用 `AnyIPv4` |

例如电脑有有线 `192.168.10.20` 和 Wi-Fi `192.168.50.20`，设备向前者发送，但程序绑定后者，端口对也可能收不到。

还要区别两个概念：绑定具体 IP 不等同于跨平台通用的“锁定某块物理网卡”API。多网卡、弱主机/强主机模型和路由行为有系统差异；**接收地址约束、发送出口选择、组播入组接口**应分别检查。

**参考回答：**具体地址绑定只接收匹配该本地目的地址的流量；`AnyIPv4` 用于本地 IPv4 通配接收。多网卡时要核对报文目标和绑定地址。不能把通配地址理解成所有抓到的报文都能收到，也不能把地址绑定和物理接口锁定混为一谈。

### 7. 单播、广播和组播的排查点有什么不同？

**三种发送方式对应不同的接收条件。**

| 类型 | 示例目标 | 重点检查 |
| --- | --- | --- |
| 单播 | `192.168.10.20` | 目标确实是接收机地址、端口、路由、绑定、策略 |
| IPv4 广播 | 在 `/24` 子网中的 `192.168.10.255` | 实际子网掩码、广播地址、出口接口、发送侧广播能力、接收端绑定与策略 |
| IPv4 组播 | 实验组 `239.255.10.10` | 绑定端口、加入目标组、入组接口、组播转发及 TTL |

广播地址要由真实网络前缀计算，不能见到 `.255` 就认定是广播。`255.255.255.255` 是受限广播，通常不会被路由器转发；定向广播跨路由也常被限制。IPv6 不使用 IPv4 这种广播方式。

**组播：绑定端口还不够。**Qt 的典型 IPv4 组播接收片段如下，假定 `receiver` 为已有 `QUdpSocket`，`iface` 为已按本机信息选出的有效 `QNetworkInterface`：

```cpp
if (!receiver.bind(QHostAddress::AnyIPv4, 45454)) {
    qCritical() << receiver.errorString();
    return;
}
const QHostAddress group("239.255.10.10");
if (!receiver.joinMulticastGroup(group, iface)) {
    qCritical() << "join failed" << receiver.errorString();
    return;
}
```

先用单接收进程验证；确实需要多个本地进程接收时，再按平台和部署需求评估共享绑定。发送方还要确认组播出口、TTL；跨网段需要网络设备支持组播转发，接收方入组不能替代网络配置。

**参考回答：**单播主要核对目标地址、端口和绑定；广播还要核对真实广播地址、出口和网段范围；组播必须在正确接口成功加入目标组，并确认网络组播转发条件。IPv4 组播在 Qt 中应绑定 `AnyIPv4`，不能只绑定端口就认为一定能接收。

Qt 的接口要求见 [QUdpSocket 组播说明](https://doc.qt.io/qt-6.9/qudpsocket.html#joinMulticastGroup)。

### 8. 怎样确认抓的是正确的网卡？

**先把地址、系统接口、抓包接口对上号，再看流量。**

Windows 上可以查看：

```powershell
Get-NetAdapter | Select-Object Name,InterfaceDescription,ifIndex,Status,MacAddress
Get-NetIPAddress -AddressFamily IPv4 |
    Select-Object InterfaceAlias,InterfaceIndex,IPAddress,PrefixLength
Find-NetRoute -RemoteIPAddress 192.168.10.20
```

最后一条应在发送机上执行；如果从接收机查询发送方向，要把远端 IP 改成发送机地址。它帮助你确定**本机发往指定远端**的最佳路由，不替远端说明它的路由。

操作顺序：

1. 查发送/接收 IP 属于哪个接口，记下接口描述、MAC 和索引。
2. 在 Wireshark 接口列表中匹配相应设备；不要只凭“以太网”这个名字猜。
3. 发少量带独特序号的测试包，确认抓到预期目标、端口和负载。
4. 如果走 VPN，分别检查隧道内层与物理接口外层：物理侧可能只看到加密封装流量。
5. 仍不确定时，可短时间选择多个候选接口捕获，并根据接口信息区分；避免把重复观察计作重复业务包。

接口流量曲线跳动只能说明接口上有流量。背景下载也会让曲线上升，它不能证明你的目标 UDP 正经过这里。

**参考回答：**我会结合本机 IP、MAC、接口索引和到目标的路由，把系统接口与 Wireshark 接口对应起来，再发送带唯一标识的测试包验证。VPN 或虚拟网络需要区分内外层封装和捕获位置。

### 9. 本机回环通信有什么特殊之处？

**同一台电脑上的通信可以在本机协议栈里完成。**

`127.0.0.1` 是 IPv4 回环地址，`::1` 是 IPv6 回环地址。发送到这些地址的数据通常不经过物理网卡；Windows 使用支持回环捕获的 Npcap 时，应选择相应回环捕获接口，而不是只抓有线或无线网卡。

即使目标填写本机某块网卡的 IP，系统也可能走本地交付路径，不一定把它送上物理链路再绕回来。回环抓包接口的显示名称与驱动版本可能不同，可查 [Npcap 官方用户指南](https://npcap.com/guide/npcap-users-guide.html)。

建议分别做三组实验：

- `127.0.0.1 → 127.0.0.1`：隔离外部网络，检查应用和本机投递。
- 发往本机真实 IP：进一步核对绑定和本地地址选择，但仍不是物理网络验收。
- 两台不同机器互发：验证物理/无线链路、交换网络和跨机策略。

**参考回答：**本机 UDP 可能通过回环或本地交付路径完成，发往 `127.0.0.1` 的数据不应期待在物理网卡上看到。要选回环捕获接口，并匹配 IPv4/IPv6。回环通过只能缩小排查范围，不能证明两台机器的链路也正常。

### 10. 路由和目标地址怎样影响 UDP 报文？

**系统按目的地址选择路由，再决定出口和下一跳。**

在普通 IPv4 路由场景，系统优先匹配更具体的目的前缀；同等条件再按路由/接口度量及系统规则选择。目标在直连网络时通常直接找目标邻居；目标不在直连网络时，可能交给匹配路由的网关。默认路由只是没有更具体匹配时的候选，不是所有跨网段通信都固定走同一个网关。

```text
本机 192.168.10.10/24
目标 192.168.10.20  → 通常走直连网络，ARP 查询目标
目标 192.168.20.20  → 可能走网关 192.168.10.1，ARP 查询网关
```

Windows 排查：

```powershell
Find-NetRoute -RemoteIPAddress 192.168.20.20
Get-NetRoute -AddressFamily IPv4
Get-NetNeighbor -AddressFamily IPv4
ipconfig /all
```

| 问题 | 发送端可能看到 | 接收端可能看到 |
| --- | --- | --- |
| 目标 IP 填错但仍可路由 | 发送成功，抓到发向错误目标 | 预期接收机没有对应包 |
| 选到 VPN 或错误出口 | 别的接口上出现该流量/封装 | 原预期路径看不到 |
| 下一跳邻居解析失败 | 重复 ARP、邻居状态异常；UDP 调用可能已成功 | 没有实际到达的数据报 |
| 没有可用路由 | 发送可能直接报错，或之后异步失败 | 没有对应数据报 |
| 回程路由错误 | 请求到达，回复走错路 | 接收业务正常，但发送方收不到回复 |

异步错误能否报告、何时报错有平台差异，不要用“没报错”推断路径畅通。`ping` 测 ICMP，`Test-NetConnection -Port` 通常测 TCP；它们不能直接证明某个 UDP 端口可接收。

**参考回答：**系统依据目标地址和路由表选出口、源地址及下一跳。我会在发送机查最佳路由、接口与邻居信息，确认抓包中的实际目标，再与接收端同一序号对照；路由或目标错误可能表现为本机发送成功而预期对端没有报文。

路由查询命令的含义见 [Find-NetRoute 官方说明](https://learn.microsoft.com/en-us/powershell/module/nettcpip/find-netroute)。

## 第三部分：报文内容与应用接收

### 11. UDP 的报文边界意味着什么？

**UDP 交付的是一条条数据报，TCP 交付的是字节流。**

```text
发送 UDP： [消息 A，100 字节] [消息 B，200 字节]
正常接收： 一次取出 A       下一次取出 B

发送 TCP： [写入 A，100 字节] [写入 B，200 字节]
接收可能： [取出 40 字节] [取出 260 字节]
```

UDP 不保证 A、B 都到达，也不保证顺序；但通过正常的数据报接收接口读取时，不会为了凑满你的缓冲区，把两条独立 UDP 数据报拼成一条。

**缓冲区太小怎么办？**在 Qt 的 `readDatagram()` 用法中，如果 `maxSize` 小于数据报长度，多出的部分会丢失，不能下次接着读剩余部分。通常可以直接用 `receiveDatagram()` 读取完整数据报；如果手动分配，则先检查 `pendingDatagramSize()`，限制允许长度后按需分配。

此外，合法 UDP 负载可以是 **0 字节**。`pendingDatagramSize()` 返回 `0` 不等于没有待收数据，`-1` 才表示没有数据报可读；判断有无数据宜用 `hasPendingDatagrams()`。业务协议可以拒绝空包，但要把它计作收到后长度不符。

**IP 分片不是应用层拆包。**一个较大的 UDP 数据报可能被 IP 分片；接收端要重组成功，才有完整 UDP 数据报交付。缺一个分片可能使整条数据报无法交付。Wireshark 的帧数因此不一定等于应用数据报数。

在以太网 MTU 1500、IPv4 无选项且无其他封装的常见条件下，1472 字节 UDP 负载加 20 字节 IPv4 头与 8 字节 UDP 头正好到 1500。这个数只是特定条件下的计算例子，VPN、IPv6、路径 MTU 等条件会改变可用大小。

**参考回答：**UDP 保留数据报边界，一次数据报接收取一条，不按 TCP 字节流方式继续拼接；缓冲区太小可能截断并丢弃余下内容。Qt 应及时循环取出完整数据报，分别校验每条长度；IP 分片由协议栈处理，不能把分片帧数当成应用报文数。

### 12. 报文抓到了，但解析结果不对，怎么分层检查？

**既然应用已经取得字节，优先对照线上的协议格式与应用手中的原始数据。**

按下面顺序查，比直接怀疑网卡更有效：

1. **确认比的是同一条。**用测试 ID 和序号定位抓包与日志。
2. **核对长度。**抓包的 `udp.length` 包含 8 字节 UDP 头；Qt 的接收数据通常是 UDP 负载，不包含该头。检查截断、可变长字段、声明长度与实际长度。
3. **比较原始十六进制。**先比较字节，不先比较解释出来的数字。高频时只抽样保存，避免日志本身拖慢接收。
4. **核对字段偏移。**从 UDP 负载偏移 0 开始算，不从整个以太网帧偏移 0 开始算。
5. **核对字节序和类型。**协议规定大端还是小端？字段是有符号还是无符号，16 位还是 32 位？业务负载不会因为用了 UDP 就自动转换成网络字节序。
6. **核对序列化方式。**不要直接把跨平台协议负载强转成 C++ 结构体；内存对齐、填充、类型宽度和未对齐访问都可能出问题。`#pragma pack` 也不会解决字节序和版本问题。
7. **核对协议版本和数据语义。**版本、消息类型、单位、缩放比例、字符串编码是否一致？使用 `QDataStream` 时还要统一字节序和流版本。

例如协议定义：

| UDP 负载偏移 | 字节数 | 含义 |
| --- | --- | --- |
| 0 | 2 | magic，大端，值 `0xCAFE` |
| 2 | 2 | version，大端，值 `1` |
| 4 | 4 | sequence，大端 |

样本 `CA FE 00 01 00 00 00 2A` 应解析为 magic=`0xCAFE`、version=`1`、sequence=`42`。

```cpp
// 假定 data 是 QByteArray，以下在使用字段前先检查最小长度。
if (data.size() < 8) {
    // 记录 bad_length 后返回。
    return;
}
const uchar *p = reinterpret_cast<const uchar *>(data.constData());
const quint16 magic = qFromBigEndian<quint16>(p);
const quint16 version = qFromBigEndian<quint16>(p + 2);
const quint32 sequence = qFromBigEndian<quint32>(p + 4);
// 需要 #include <QtEndian>；随后检查 magic/version/业务字段。
```

**参考回答：**我会先用序号对应抓包和应用数据，比较实际负载长度与十六进制，再按协议核对偏移、字节序、字段类型、对齐和版本。若原始负载一致而字段值不同，排查重点应转向解析与协议约定。

**常见误区：**业务数字不对就认定网络传坏了，却没有先比较原始字节。

### 13. 怎样区分“Socket 没收到”和“业务代码丢弃了”？

**把“接收数量”拆成多个处理阶段，所有报文都要有去向。**

建议定义：

| 计数器 | 在哪里增加 | 用来回答什么 |
| --- | --- | --- |
| `ready_events` | `readyRead` 处理入口 | 处理入口执行了几次 |
| `read_ok` / `read_bytes` | 成功取到一条数据报后，过滤之前 | 实际读到了几条、多少负载字节 |
| `read_errors` | 接收 API 失败时 | 是否有读取错误 |
| `filtered` | 来源、消息类型等业务规则拒绝处 | 是否读到了但被规则排除 |
| `bad_length` / `bad_version` / `parse_errors` | 各类协议校验失败处 | 为什么解析不成立 |
| `accepted` | 达到定义好的业务接受点 | 有效业务结果有多少 |
| `queue_dropped` | 应用有界队列满、主动丢弃处 | 是否在应用排队阶段丢失 |

同步处理并把拒绝原因设为互斥时，排空后应能核对：

```text
read_ok = accepted + filtered + bad_length + bad_version + parse_errors
```

如果有异步队列，统计等式还要加上队列内和正在处理的报文，以及主动丢弃数。计数用同一个边界和时间窗口，避免一条包既算“坏版本”又算“解析失败”。

`ready_events` 不是报文数。一次通知可能已有多条报文等待；应通过 `while (socket.hasPendingDatagrams())` 连续读取。Qt 文档提示收到可读通知后要读取待收数据，不能假设留下的包总能再次触发期望的通知。

**当 `read_ok` 不增加时怎么继续？**检查绑定状态、Socket 生命周期、信号连接、线程归属、事件循环是否运行，以及在 Socket 所在线程检查是否还有待读数据。仅凭“槽函数没日志”不能确定内核队列是空的。不要让另一个线程随意调用同一个 Socket 来探测。

**参考回答：**我会在可读处理入口、成功读取后、每个过滤与解析失败出口、业务接受点放计数。读取数正常而接受数少，问题在读取后的处理；读取数本身少，则继续查投递、队列和读取调度。通知次数与数据报数必须分开统计。

### 14. 接收缓冲区和高频报文有什么关系？

**接收链路里有多个队列，不只是一个“缓存”。**

```text
网卡接收描述符/硬件队列
  → 驱动与协议栈处理
  → Socket 内核接收队列
  → 应用任务队列
  → 解析、落盘或界面处理
```

任一阶段持续处理不过来，都可能积压。队列满后的表现取决于所在阶段和策略，常见是丢弃新报文、主动丢旧报文或处理延迟增加。UDP 没有 TCP 那样的端到端流量控制来保证接收应用慢时发送方自动降速。

**缓冲区能扛短暂停顿，不能补上长期吞吐缺口。**

假设每秒 10,000 条，每条 256 字节负载，接收线程阻塞 100 ms，仅这段时间就有约：

```text
10,000 × 0.1 = 1,000 条
1,000 × 256 = 256,000 字节负载
```

实际队列占用还包括系统对象开销，不能直接拿该负载字节数当作准确所需缓冲值。若长期输入 10,000 条/秒而处理只能完成 8,000 条/秒，增大缓冲只会延后溢出。

Qt 中可设置系统 Socket 接收缓冲选项，例如在成功绑定后：

```cpp
socket.setSocketOption(QAbstractSocket::ReceiveBufferSizeSocketOption,
                       4 * 1024 * 1024);
qInfo() << "receive buffer reported by OS"
        << socket.socketOption(QAbstractSocket::ReceiveBufferSizeSocketOption);
```

这个 4 MiB 只是实验参数。系统可能限制或调整它，要读取实际报告值。不要把 `setReadBufferSize()` 当成 UDP 内核接收队列调优的等价替代。

应同步测量：

- 实际发送率、突发大小、`read_ok` 增速、唯一序号缺口。
- 接收处理耗时、长时间未被调度的间隔、事件循环定时器延后程度。
- 应用队列长度、高水位、处理速率和主动丢弃数。
- 网卡丢弃/错误、系统 UDP 接收错误及其测试前后增量。
- 抓包进程的丢包统计和 CPU/磁盘负载。

Windows 可用 `Get-NetAdapterStatistics` 和 `netstat -s -p udp` 获取辅助统计；它们通常不是本进程、某个 Socket 的精确丢包计数。某些系统接收缓冲错误归因还需要更细的跟踪手段。

**参考回答：**高频时要检查网卡、协议栈、Socket 和应用队列各阶段积压，结合序号、处理延迟、队列水位和系统丢弃增量判断。扩大接收缓冲有助于吸收突发，但长期处理能力低于输入速率时仍会丢包。

网卡统计字段范围见 [Get-NetAdapterStatistics](https://learn.microsoft.com/en-us/powershell/module/netadapter/get-netadapterstatistics)。

### 15. UDP 的可靠性边界是什么？

**UDP 不保证送达、顺序或只到达一次，也没有内建重传。**这并不意味着“完全没法判断”，而是需要应用协议补充信息和规则。[RFC 768](https://www.rfc-editor.org/rfc/rfc768) 定义了基本 UDP 机制及其交付边界。

一个适合排障的应用报头可包含：

| 字段 | 为什么需要 |
| --- | --- |
| `test_id` / `session_id` | 区分不同测试轮次与进程重启 |
| `sequence` | 识别单轮内的缺口、重复和乱序 |
| `version` / `message_type` | 识别格式及业务类别 |
| 声明长度 | 检查协议格式是否完整一致 |
| 发送时间戳 | 在时钟条件允许时辅助分析时延 |
| 业务校验字段 | 按业务需求检查负载完整性；不能因此自动获得可靠交付 |

例如依次收到 `100、102、101、102`：

- 收到 `102` 时，`101` 只是暂时缺失，不能立刻认定永久丢失。
- 后来收到 `101`，说明发生了乱序到达。
- 再收到 `102`，该轮这个序号出现了重复。
- 测试发送结束、等待约定排空时间后，仍未收到的预期序号才按该测试口径计为缺失。

这里“排空时间”是测量约定，不是 UDP 给出的绝对送达截止保证。序号还要考虑回绕、发送端重启、多个发送源；不能只凭一个小于历史最大值的数就断言重复。

若业务必须可靠交付，还需设计 ACK、超时重传、去重、窗口和拥塞控制，或选择提供所需语义的传输协议。ACK 应写清表示“收到”“校验通过”还是“业务提交成功”。即使重传后能去重，也不能仅靠 UDP 宣称业务副作用恰好执行一次。

**参考回答：**UDP 不提供送达、顺序和去重保证。我会增加会话标识、递增序号及协议校验字段，用接收集合判断重复与最终缺口，用首次到达顺序判断乱序；需要可靠性时再定义确认、重传和业务幂等规则。

## 第四部分：抓包证据与综合定位

### 16. 抓包过滤器会怎样影响排查？

**捕获过滤器决定什么能进入这次捕获，显示过滤器决定已捕获的内容里显示什么。**

| 类型 | 生效位置 | 写错可能造成什么 | 正确示例 |
| --- | --- | --- | --- |
| 捕获过滤器 | 捕获阶段 | 目标包根本没有记录到文件中 | `udp dst port 45454` |
| 显示过滤器 | 已捕获数据的显示/分析阶段 | 包被隐藏，清除过滤后可再分析 | `udp.dstport == 45454` |

常用示例：

```text
捕获过滤器：
udp port 45454
udp dst port 45454 and dst host 192.168.10.20

显示过滤器：
udp.port == 45454
udp.dstport == 45454 && ip.dst == 192.168.10.20
udp.dstport == 45454 && ipv6.dst == ::1
```

不要把两种语法放错位置。只写目标端口会隐藏反向回复；IP 写错、方向写反，也会制造“没有报文”的假象。

初次定位可短时间不加捕获过滤器，之后用显示过滤器收窄。高流量环境需要控制捕获量，另存原始文件并记录捕获条件。若怀疑分片，端口捕获过滤器可能漏掉不含 UDP 头的后续 IPv4 分片，可先用合适的主机/IP 条件保留相关分片，再进行重组分析。

还应检查捕获丢包统计、截断长度和捕获时段。工具报告“0 dropped”也不必然证明网卡之前或所有路径都没有丢包，统计覆盖范围取决于捕获机制。

**参考回答：**捕获过滤器在采集时筛选，漏掉的包事后无法靠显示过滤找回；显示过滤器只隐藏已捕获数据。我会先验证接口、方向、时间窗口和过滤条件，并检查捕获自身丢包，避免把观测不完整当成网络没到达。

两种过滤机制分别见 Wireshark 官方的 [捕获过滤](https://www.wireshark.org/docs/wsug_html_chunked/ChCapCaptureFilterSection.html) 和 [显示过滤](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkDisplayFilterSection.html)。

### 17. 入站报文被 Wireshark 看到，Socket 却收不到，怎么列假设？

**先验证便宜、直接、可重复的条件，再深入检查系统投递和性能。**

| 优先级 | 假设 | 验证证据 |
| --- | --- | --- |
| 1 | 抓到的不是这次测试的入站目标包 | 同一测试 ID/序号、方向、真实负载和接口 |
| 2 | 目标 IP 或端口不匹配 | 抓包目标字段对照 `localAddress()`/`localPort()` |
| 3 | 绑定失败、绑定后关闭、进程看错 | 绑定返回值、生命周期日志、系统端点与 PID |
| 4 | IPv4/IPv6 不匹配，或 UDP 已限制对端 | Socket 协议、绑定地址、连接对端与报文来源 |
| 5 | 组播没入组、入错接口 | `joinMulticastGroup()` 返回值、组地址和接口 |
| 6 | 防火墙或安全软件丢弃 | 与程序、端口、地址、配置文件对应的规则及丢弃日志 |
| 7 | IP/UDP 层不能交付 | 校验状态、分片是否完整、重组/协议错误统计 |
| 8 | Socket 队列溢出或资源问题 | 系统丢弃增量、接收停顿、缓冲调整对照与更细跟踪 |
| 9 | Qt 没及时读取 | `readyRead`、事件循环、线程归属、待收状态和耗时日志 |
| 10 | 业务收到了却没有计入 | `read_ok` 对照过滤、解析失败和接受数 |

防火墙排查优先检查有效规则、网络配置文件和日志，必要时在隔离实验中添加精确到程序/端口/来源的临时规则；不把“关闭所有防护”当成通用起手动作。

**关于校验和的一个陷阱：**发送端本机抓包显示校验和不正确，有时是因为网卡尚未完成校验和卸载，并不代表线上报文真的错误。应结合捕获位置、卸载状态和对端观察判断，见 [Wireshark 卸载说明](https://wiki.wireshark.org/CaptureSetup/Offloading)。反过来，不能拿这条解释替所有真实入站校验错误开脱。

**参考回答：**我先确认是同一条真实入站报文，再比对地址、端口、绑定、进程和地址族，之后查组播、策略、协议检查和队列，最后核对 Qt 读取与业务去向。按容易获取的证据排序，每排除一个条件再缩小范围。

### 18. 怎样比较发送端和接收端的抓包结果？

**比较同一条逻辑报文，而不是只比较两个窗口的总帧数。**

建立对应关系前，先记录两端：接口名称与描述、IP/MAC、捕获方向、过滤表达式、开始结束时间、截断长度、丢包统计。提前启动两边捕获，再启动发送，发送结束后留出排空时间。

用 `(test_id, sequence)` 匹配报文；有多个发送源时加入源身份。跨 NAT 时允许地址和端口发生预期转换；跨 VPN 时区分内外层；IP 分片、重复捕获和重组也会改变帧数关系。

| 观察结果 | 下一步判断 |
| --- | --- |
| 发送调用失败，发送抓包也没有 | 先解决本机发送错误 |
| 发送调用成功，预期出口没有 | 先核对路由、邻居、实际出口和捕获配置 |
| 发送侧有，对端捕获没有 | 核实两边观测可靠后，把可疑范围缩到两捕获点之间 |
| 两端都抓到，对端 `read_ok` 没有 | 查接收侧策略、协议投递、Socket 和读取调度 |
| 对端 `read_ok` 有，`accepted` 没有 | 查应用过滤、解析和业务处理 |

“两个捕获点之间”不一定只含交换机：发送侧捕获点之后的驱动、网卡及接收侧捕获点之前的组件也可能在范围内。若要继续缩小，可加入交换机镜像/TAP、交换机端口丢弃统计、VLAN/ACL、无线重试和网卡统计证据。

两机时钟不准时，不能拿抓包时间直接相减当作准确单向延迟。先用序号证明身份；要测跨机延迟，再单独解决时钟同步和误差。

**参考回答：**我先确认两端接口、方向、过滤和捕获质量一致，再用测试 ID 与序号对应数据报，并考虑 NAT、隧道和分片。发送侧有而接收侧没有，只能先定位到两个可靠观测点之间，随后用网络设备与网卡证据继续缩小。

### 19. 如何设计一个可复现的排障实验？

**先建立低频、固定格式、可计数的基线，再一次改变一个条件。**

#### 19.1 实验约定

两端使用附录 A 的 `udp_probe`。每次启动发送端生成一个 64 位 `test_id`，序号从 0 递增。实验负载格式如下，整数按大端编码：

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| 0 | 4 | ASCII `UDP1`，用于识别本实验 |
| 4 | 1 | 版本 `1` |
| 5 | 1 | 保留字节，值 `0` |
| 6 | 2 | UDP 负载总长度 |
| 8 | 8 | `test_id` |
| 16 | 8 | `sequence` |
| 24 起 | 可变 | 填充数据 |

每轮记录操作系统、Qt 版本、网卡、地址、路由、二进制版本、负载长度、发送间隔、计划条数和抓包条件。一次运行只接收一轮测试；下一轮重启接收端，避免混入上一轮统计。

接收端按“成功读取、格式不符、其他测试轮次、首次接受、重复”记账；乱序作为首次接受中的附加属性统计。发送端记录尝试数、成功数和失败数，失败序号单独定位。

#### 19.2 阶段一：本机回环

两个终端先后执行，先启动接收端：

```powershell
# 接收 15 秒；示例绑定所有本地 IPv4 地址。
.\udp_probe.exe recv 45454 15

# 另一终端：发送 100 条，计时器间隔 10 ms，负载 64 字节。
.\udp_probe.exe send 127.0.0.1 45454 100 10 64
```

在 Wireshark 选择回环捕获接口，显示过滤器用 `udp.port == 45454`。发送完成后留出时间，让接收端统计稳定。

理想基线为发送成功 100、接收读取 100、首次接受 100、格式不符 0、重复 0。没有达到时，先解决本机程序、绑定、事件循环和策略问题。

#### 19.3 阶段二：同网段两台机器

假设接收机实际 IP 为 `192.168.10.20`，接收命令不变；发送机执行：

```powershell
.\udp_probe.exe send 192.168.10.20 45454 100 10 64
```

在两端正确物理接口提前启动捕获，检查路由、网卡地址、接收机端点和针对程序/端口的防火墙配置。保持条数、间隔、长度不变，从回环切换到双机是这一阶段的主要变量。

如果回环正常而双机异常，可优先检查新引入的路径、远端目标地址和跨机策略；但绑定范围、源地址过滤等应用差异也要保留。

#### 19.4 阶段三：逐步增加负载

先把测试时长和条数配好，再逐渐减小间隔：如 `10 ms → 2 ms → 1 ms → 0 ms`。`0 ms` 表示尽可能频繁触发计时器，不是准确的固定 PPS。Qt 定时器受调度影响，实际速率以成功发送数/实测时长为准。

```powershell
# 尽快发送 100,000 条，每条 256 字节；观察实际吞吐和接收缺口。
.\udp_probe.exe send 192.168.10.20 45454 100000 0 256
```

每轮重启接收端并保证接收时长覆盖完整发送和排空期。可以分别比较：

- 原始接收与加入实际解析。
- 不逐包打印与逐包打印。
- 原接收缓冲与较大接收缓冲。
- 接收与 GUI 同线程、接收迁到有运行事件循环的工作线程。
- 固定速率与平均速率相近的短突发。

每次只改变一个因素，记录结果，防止“多个参数一起调好了”却不知道原因。抓包本身也消耗 CPU、内存和磁盘，高频结果要记录是否正在捕获。

#### 19.5 怎样核对结果

用集合而不是只用最大序号做最终核对：

```text
S = 发送接口成功接受的唯一 (test_id, sequence) 集合
R = 接收 API 实际读取的唯一标识集合
A = 业务接受的唯一标识集合

应用接收缺失集合 = S - R
读取后未接受集合 = R - A
应用接收缺失率 = |S - R| / |S| × 100%    （|S| > 0）
```

`S-R` 包含从本机发送接受之后到接收 API 之前的所有可能丢失，**不能直接命名为纯网络丢包**。要定位网络路径，还要加入发送和接收捕获点集合，并核实捕获完整性。

附录示例为了简化日志，没有导出所有集合：当发送失败为 0、测试轮次一致且序号从 0 连续生成时，发送成功数减接收首次接受数可用于核对该实验的有效报文缺失。它同时受传输丢失、格式拒绝和实验限制影响，必须看其他计数解释。有失败或其他复杂条件时，要额外导出序号集合后再精确求差。

**参考回答：**我会设计固定二进制格式，加入测试 ID 和序号，两端记录发送返回值和各接收阶段计数，提前启动抓包并检查地址、端口、路由和策略。先回环低频，再双机低频，最后逐步提高速率和突发强度；每轮只改一个条件，以唯一序号对应各观察点。

### 20. 综合故障：抓包正常，但 Qt 偶发收不到

**已知现象只能提出假设：接收或处理能力可能不足，尚不能确定根因。**

降低发送频率后减轻，符合队列溢出、事件循环阻塞、逐包日志开销或网络拥塞等多种情形。“Wireshark 偶尔能看到”甚至还不足以说明所有预期报文都到达接收捕获点。

#### 20.1 先定义“程序数量偏少”的统计位置

先问当前数的是 `readyRead` 次数、成功读取数、解析成功数，还是界面刷新次数。若每 100 ms 合并刷新一次 GUI，界面更新次数少于 UDP 数据报数完全可能符合设计。

给所有阶段加测试 ID、序号和互斥去向计数，明确观察窗口与排空时间。

#### 20.2 按通信路径收集证据

| 检查顺序 | 要验证的内容 | 必须留的证据 |
| --- | --- | --- |
| 1. 发送程序 | 是否真按预期生成并成功提交 | 计划、尝试、成功、失败数；失败序号；实际速率与突发 |
| 2. 发送侧接口 | 路由和出口是否正确，是否有发送侧异常 | 出口与源地址、邻居状态、发送捕获、网卡错误/丢弃增量 |
| 3. 网络路径与接收接口 | 同一序号是否到达接收捕获点 | 双端捕获集合、捕获丢包、交换机端口/VLAN/ACL及网卡统计 |
| 4. 接收操作系统 | 是否允许并能完成投递 | 策略日志、分片/校验情况、UDP 错误增量、必要的系统跟踪 |
| 5. Socket | 绑定是否正确、队列是否受压 | 实际本地端点、地址族、缓冲大小、读取数、接收停顿 |
| 6. Qt 接收线程 | 是否及时执行可读处理并持续取包 | 线程归属、事件循环、处理耗时、定时器延后、逐包日志开销 |
| 7. 应用处理 | 是否读后拒绝、异步积压或主动丢弃 | 来源过滤、格式失败、队列丢弃、业务接受数与具体原因 |

这个顺序用于覆盖完整链路；实际执行时可先做绑定、端口、计数口径这些成本最低的检查，不必等网络设备日志齐全才检查自己的代码。

#### 20.3 怎样区分几个相似故障

| 候选原因 | 支持它的现象 | 还需要什么证据 |
| --- | --- | --- |
| 网络路径中的丢失 | 发送捕获有指定序号，接收捕获缺少 | 两端捕获质量可靠；追加中间观测点，排除捕获点之后/之前的主机组件 |
| Socket 接收队列溢出 | 接收捕获有，应用读取少；系统接收错误增加 | 错误统计口径或更细跟踪；增大缓冲、缩短接收停顿后的对照 |
| Qt 线程阻塞 | 接收回调长时间不执行，定时器明显延后 | 慢函数/锁等待/日志栈证据；去掉阻塞或调整线程后重复实验 |
| 业务过滤 | `read_ok` 包含该序号，过滤计数增加 | 记录命中的具体规则，确认协议与来源是否符合要求 |
| 解析失败 | 原始读取已记录，长度/版本/字段校验失败 | 对照抓包负载和解析样本，定位出错字段与协议差异 |
| 应用队列满 | 读取及时，业务队列高水位及丢弃数增加 | 有界队列策略、消费速率与排队延迟 |
| 抓包漏抓 | 应用已读到某序号，当前抓包却没有 | 核实相同测试与身份后，检查接口、过滤、捕获时段和捕获丢包 |

队列溢出和线程阻塞常构成因果链：**线程长时间不读 → Socket 队列积压 → 缓冲满 → 新到报文丢失**。不要把二者误当成互相排斥的解释。

#### 20.4 一个把计数对齐的例子

以下数字只展示推理方法。假设测试结束并排空后，同一轮发送成功 100,000 条，抓包已经按唯一逻辑数据报去重、重组并核实观测条件：

```text
发送成功：            100,000
发送捕获观察到：      100,000
接收捕获观察到：       99,800
接收 API 实际读取：    98,500
业务过滤：               300
格式/解析失败：           200
业务接受：             98,000

98,500 = 300 + 200 + 98,000
```

可以得到：

- 200 条未在接收捕获点出现，可疑范围在两个观察点之间，仍要结合抓包质量和其他证据确认。
- 1,300 条在接收捕获点出现却没有被读取，可疑范围在接收捕获点到应用读取之间；不能仅靠差值断言全是 Socket 溢出。
- 500 条已经被应用读取，但按业务规则或格式校验没有进入接受数；原因在应用内有明确去向。

如果同时发现 100 ms 级接收线程停顿、UDP 接收错误随测试增加，且“去掉同步日志/长操作”后问题消失，才有更强理由判断主要因果链是接收不及时造成队列压力。还要在相同负载下复测，排除只是实际发送变慢了。

#### 20.5 修改应针对已经获得的证据

- 接收处理只做快速取包、最小校验和必要统计，重处理交给有界工作队列。
- 避免在 `readyRead` 里同步落盘、频繁刷新 UI、等待锁或执行耗时业务。
- 在 Socket 所在线程创建和使用它，保证该线程事件循环运行；跨线程传递已取得的数据，而不是随意跨线程操作同一个 Socket。
- 以实测速率、突发和停顿时间评估缓冲；系统缓冲与应用队列分别管理。
- 日志优先做每秒汇总、错误采样和指定序号跟踪，避免逐包输出影响结果。
- 若持续超载，提升消费能力、限制发送速率，或明确选择最新数据优先/丢弃策略，并统计主动丢弃。

**参考回答：**我先确认偏少的是哪一层的计数，再用测试 ID 和序号串起发送返回值、双端抓包、系统统计、Socket 读取及业务去向。接收捕获前缺失看路径，捕获后读取前缺失看系统投递、队列与线程，读取后减少看过滤、解析与应用队列。降频好转提示容量或调度问题，但必须由相邻观察点和对照实验确认根因。

Qt 的线程和事件循环约束见 [Threads and QObjects](https://doc.qt.io/qt-6/threads-qobject.html)。

## 附录 A：最小 Qt 收发程序

将下面两个代码块分别保存为 `CMakeLists.txt` 和 `main.cpp`，放进同一实验目录。程序没有 GUI；收发分别启动进程，不需要自定义 QObject 类。

**示例的范围与限制：**

- 只演示 IPv4 单播，IPv4 回环也可使用；广播和组播需按第 7 题另行配置。
- 负载范围 24～1400 字节，单轮最多 200,000 条。1400 是为了保持实验简单的限制，不保证所有隧道或路径都不分片。
- 接收端只跟踪第一轮合法测试，其他 `test_id` 计入 `other_test`；每轮应重启接收端。
- 用 `QSet` 保存序号方便学习，带有内存分配和统计开销；不把它当成极限性能实现。
- 示例在可读时循环取包；持续无限流量下也要评估处理公平性，必要时设计有预算且能主动续读的调度，不能仅改成 `if` 后任由待收数据滞留。
- `gap_so_far` 是截至当前最大序号的暂时缺口，不知道发送尾部是否全部到达。最终完整缺失仍要与发送端结果核对。

### A.1 CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.16)
project(udp_probe LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
find_package(Qt6 REQUIRED COMPONENTS Core Network)
add_executable(udp_probe main.cpp)
target_link_libraries(udp_probe PRIVATE Qt6::Core Qt6::Network)
```

### A.2 main.cpp

```cpp
#include <QCoreApplication>
#include <QElapsedTimer>
#include <QHostAddress>
#include <QNetworkDatagram>
#include <QRandomGenerator>
#include <QSet>
#include <QTimer>
#include <QUdpSocket>
#include <QVariant>
#include <QtEndian>
#include <QDebug>
#include <algorithm>
#include <cstring>

static constexpr quint64 MaxPackets = 200000;

static bool integerArg(const QString &text, int min, int max, int &out)
{
    bool ok = false;
    const int value = text.toInt(&ok);
    if (!ok || value < min || value > max)
        return false;
    out = value;
    return true;
}

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    const QStringList args = app.arguments();
    auto usage = [] {
        qCritical().noquote()
            << "recv: udp_probe recv <port> <seconds:1..3600>\n"
               "send: udp_probe send <IPv4> <port> <count:1..200000> "
               "<intervalMs:0..1000> [size:24..1400]";
        return 1;
    };
    if (args.size() < 2)
        return usage();

    QUdpSocket socket;
    QObject::connect(&socket, &QUdpSocket::errorOccurred, &app,
        [&](QAbstractSocket::SocketError error) {
            qWarning() << "socket_error" << error << socket.errorString();
        });

    if (args[1] == "recv") {
        int port = 0, seconds = 0;
        if (args.size() != 4 || !integerArg(args[2], 1, 65535, port)
            || !integerArg(args[3], 1, 3600, seconds))
            return usage();
        if (!socket.bind(QHostAddress::AnyIPv4, quint16(port),
                         QAbstractSocket::DontShareAddress)) {
            qCritical() << "bind_failed" << socket.error()
                        << socket.errorString();
            return 2;
        }
        qInfo() << "bound" << socket.localAddress() << socket.localPort()
                << "address_family" << socket.localAddress().protocol()
                << "state" << socket.state()
                << "rcvbuf" << socket.socketOption(
                       QAbstractSocket::ReceiveBufferSizeSocketOption);

        quint64 events = 0, read = 0, bytes = 0, errors = 0;
        quint64 invalid = 0, other = 0, duplicate = 0, reordered = 0;
        quint64 activeTest = 0, highest = 0;
        bool haveTest = false;
        QSet<quint64> seen;
        QElapsedTimer clock;
        clock.start();
        qint64 lastTick = 0, maxTimerLateMs = 0;
        quint64 previousRead = 0;

        auto report = [&](const char *tag) {
            const quint64 unique = quint64(seen.size());
            const quint64 gap = unique ? highest + 1 - unique : 0;
            qInfo() << tag << "elapsed_ms" << clock.elapsed()
                    << "test_id" << activeTest << "ready_events" << events
                    << "read" << read << "bytes" << bytes
                    << "accepted_unique" << unique << "duplicate" << duplicate
                    << "reordered_unique" << reordered
                    << "invalid" << invalid << "other_test" << other
                    << "read_errors" << errors << "gap_so_far" << gap
                    << "max_timer_late_ms" << maxTimerLateMs;
        };

        QObject::connect(&socket, &QUdpSocket::readyRead, &app, [&] {
            ++events;
            while (socket.hasPendingDatagrams()) {
                const QNetworkDatagram datagram = socket.receiveDatagram();
                if (!datagram.isValid()) {
                    ++errors;
                    break;
                }
                const QByteArray data = datagram.data();
                ++read;
                bytes += quint64(data.size());
                if (data.size() < 24 || data.size() > 1400) {
                    ++invalid;
                    continue;
                }
                const auto *p = reinterpret_cast<const uchar *>(data.constData());
                if (std::memcmp(p, "UDP1", 4) != 0 || p[4] != 1 || p[5] != 0
                    || qFromBigEndian<quint16>(p + 6) != data.size()) {
                    ++invalid;
                    continue;
                }
                const quint64 test = qFromBigEndian<quint64>(p + 8);
                const quint64 seq = qFromBigEndian<quint64>(p + 16);
                if (test == 0 || seq >= MaxPackets) {
                    ++invalid;
                    continue;
                }
                if (!haveTest) {
                    activeTest = test;
                    haveTest = true;
                    qInfo() << "first_packet" << "test_id" << test << "seq" << seq
                            << "from" << datagram.senderAddress()
                            << datagram.senderPort();
                }
                if (test != activeTest) {
                    ++other;
                    continue;
                }
                if (seen.contains(seq)) {
                    ++duplicate;
                    continue;
                }
                if (!seen.isEmpty() && seq < highest)
                    ++reordered;
                highest = std::max(highest, seq);
                seen.insert(seq);
            }
        });

        QTimer stats;
        stats.setInterval(1000);
        QObject::connect(&stats, &QTimer::timeout, &app, [&] {
            const qint64 now = clock.elapsed();
            const qint64 dt = now - lastTick;
            maxTimerLateMs = std::max(maxTimerLateMs,
                                     std::max(qint64(0), dt - 1000));
            const double rate = dt > 0 ? (read - previousRead) * 1000.0 / dt : 0;
            qInfo() << "read_per_second_actual" << rate;
            report("stats");
            lastTick = now;
            previousRead = read;
        });
        stats.start();
        QTimer::singleShot(seconds * 1000, &app, [&] {
            report("receiver_final");
            app.quit();
        });
        return app.exec();
    }

    if (args[1] == "send") {
        int port = 0, count = 0, interval = 0, size = 64;
        if ((args.size() != 6 && args.size() != 7)
            || !integerArg(args[3], 1, 65535, port)
            || !integerArg(args[4], 1, int(MaxPackets), count)
            || !integerArg(args[5], 0, 1000, interval)
            || (args.size() == 7 && !integerArg(args[6], 24, 1400, size)))
            return usage();
        const QHostAddress destination(args[2]);
        if (destination.isNull()
            || destination.protocol() != QAbstractSocket::IPv4Protocol) {
            qCritical() << "A numeric IPv4 destination is required";
            return 1;
        }
        quint64 test = QRandomGenerator::global()->generate64();
        if (test == 0)
            test = 1;
        quint64 attempted = 0, succeeded = 0, failed = 0;
        QElapsedTimer clock;
        clock.start();
        QTimer timer;
        timer.setTimerType(Qt::PreciseTimer);
        timer.setInterval(interval);
        qInfo() << "sender_start" << "test_id" << test
                << "target" << destination << port << "planned" << count
                << "interval_ms" << interval << "payload_size" << size;

        QObject::connect(&timer, &QTimer::timeout, &app, [&] {
            const quint64 seq = attempted++;
            QByteArray data(size, 'x');
            auto *p = reinterpret_cast<uchar *>(data.data());
            std::memcpy(p, "UDP1", 4);
            p[4] = 1;
            p[5] = 0;
            qToBigEndian<quint16>(quint16(size), p + 6);
            qToBigEndian<quint64>(test, p + 8);
            qToBigEndian<quint64>(seq, p + 16);
            const qint64 n = socket.writeDatagram(data, destination, quint16(port));
            if (n == data.size()) {
                ++succeeded;
            } else {
                ++failed;
                qWarning() << "send_failed" << "test_id" << test << "seq" << seq
                           << "returned" << n << "error" << socket.error()
                           << socket.errorString();
            }
            if (attempted == quint64(count)) {
                timer.stop();
                const qint64 ms = clock.elapsed();
                const double rate = succeeded * 1000.0 / std::max(qint64(1), ms);
                qInfo() << "sender_final" << "test_id" << test
                        << "attempted" << attempted << "succeeded" << succeeded
                        << "failed" << failed << "elapsed_ms" << ms
                        << "approx_success_per_second" << rate;
                QTimer::singleShot(250, &app, &QCoreApplication::quit);
            }
        });
        timer.start();
        return app.exec();
    }
    return usage();
}
```

代码中有两个值得核对的统计关系：

```text
attempted = succeeded + failed
read = accepted_unique + duplicate + invalid + other_test
```

`read_errors` 没有成功得到数据报，不计入 `read`；`reordered_unique` 是 `accepted_unique` 的子集，也不再加到右边。示例把所有格式拒绝合为 `invalid`，实际项目可进一步拆成长度、版本等互斥原因。

`max_timer_late_ms` 只是接收事件循环调度的线索，受系统调度和定时器误差影响，不等同于每条报文的精确排队延迟。最终报告定时器触发也不代表网络已绝对排空，要由实验时长安排保证。

### B.3 用一套顺序串起 20 题

1. **画路径：**解释从编码到业务接受的主要组件。（第 1～3 题）
2. **核对端点：**地址、端口、绑定和地址族是否一致。（第 4～6 题）
3. **确认路线：**单播/广播/组播、接口、回环和路由。（第 7～10 题）
4. **检查交付：**完整数据报有没有被及时读取，读后去了哪里。（第 11～14 题）
5. **标识数据：**用测试 ID 和序号处理缺口、重复、乱序。（第 15 题）
6. **验证观测：**过滤和捕获质量可靠，双端能对应同一条。（第 16～18 题）
7. **做对照实验：**回环、双机、负载递增，形成可复查的因果证据。（第 19～20 题）

### B.4 给自己的答案打分

每题可以按四项各给 0～1 分，不必纠结用词是否与本文相同：

- 是否准确说出了该题涉及的处理位置或概念？
- 是否给出了可以实际执行的检查动作？
- 是否写明观察到什么才支持自己的判断？
- 是否保留了证据尚不能排除的可能性？

20 题共 80 分。0～1 分的题优先回看概念，2 分的题补实际检查方法，3～4 分的题尝试脱离文档讲给别人听。最终应能独立解释第 20 题，并用相邻位置的证据缩小故障范围。
