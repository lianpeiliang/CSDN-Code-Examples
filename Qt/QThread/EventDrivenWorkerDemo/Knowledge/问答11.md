# 问答11：关闭窗口时，为什么使用阻塞排队调用取消任务？

## 问题十六：普通排队调用能保证取消请求在线程退出前执行吗？

窗口析构时，项目中使用了以下代码：

```cpp
QMetaObject::invokeMethod(
    worker, "cancelTask", Qt::BlockingQueuedConnection);

workerThread.quit();
workerThread.wait();
```

阻塞排队调用会让 GUI 线程等待 `cancelTask()` 执行完，再继续调用 `quit()`。

如果将连接类型改成普通的 `Qt::QueuedConnection`，后面仍然紧接着调用 `quit()` 和 `wait()`，能保证 `cancelTask()` 在线程退出前执行吗？为什么？

### 我的回答

我认为不能保证。

使用 `Qt::QueuedConnection` 时，`QMetaObject::invokeMethod()` 会把调用 `cancelTask()` 的请求投递到工作线程的事件队列中，GUI 线程不需要等待这个槽执行完，就可以继续运行。

接下来，GUI 线程立即调用 `quit()`。此时，取消请求可能仍在队列中，尚未得到处理。如果工作线程的事件循环先退出，`cancelTask()` 就没有机会执行。

因此，我认为这里不能直接改成普通排队连接，否则无法保证先完成取消，再退出线程。

### 反馈与解释

这个判断正确。关键是区分“请求已经入队”与“请求已经执行”。

#### 普通排队调用只完成请求投递

采用 `Qt::QueuedConnection` 时，可能出现这样的过程：

```text
GUI 线程                         工作线程

投递 cancelTask() ────────────→ 请求入队
继续调用 quit()                 可能尚未处理该请求
                               ↓
                               事件循环退出
```

实际运行时，工作线程可能很快处理了取消请求，也可能在处理它之前就退出了事件循环，因此无法保证执行顺序。

`quit()` 请求事件循环退出，不保证先清空事件队列。`wait()` 只负责等待线程结束，也不会让队列中的槽执行完。

#### 阻塞排队调用确定了先后顺序

原代码使用 `Qt::BlockingQueuedConnection`，使 GUI 线程在投递请求后等待，直到工作线程执行完 `cancelTask()` 才继续：

```text
GUI 投递 cancelTask()，并等待
        ↓
工作线程执行 cancelTask()
        ↓
cancelTask() 返回，GUI 结束等待
        ↓
GUI 调用 quit()，再调用 wait()
```

这样，调用 `quit()` 时，取消槽已经执行完成。在当前示例中，如果任务仍在运行，`cancelTask()` 会修改运行状态、停止定时器并发出任务已取消的信号。这并不意味着 GUI 已经处理完该信号对应的界面更新。

这种安排依赖工作线程能够及时处理取消请求。本例每个任务步骤都很短，会返回事件循环，因此能够处理这个阻塞排队调用；如果以后把某一步改成长时间阻塞操作，关闭窗口时 GUI 线程也会等待这一步返回。

#### 能否使用普通排队连接设计退出流程？

如果要保留当前代码“先完成取消，再请求退出”的顺序，就不能只把连接类型直接换成普通排队连接。

普通排队连接也可以用于退出流程，但需要重新安排后续步骤。例如，先投递取消请求，等 Worker 确认取消完成后，再请求线程退出。

另外，“取消请求卡在队列里”表示这次调用未被处理，并不表示工作线程阻塞在那里。工作线程仍然可以正常退出，`wait()` 也可以返回，只是取消槽未必得到执行。
