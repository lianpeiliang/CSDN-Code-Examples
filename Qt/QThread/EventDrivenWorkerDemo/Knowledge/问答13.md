# 问答13：不同线程之间的阻塞排队调用也会死锁吗？

## 问题十八：GUI 与 Worker 相互阻塞等待会怎样？

问答12讨论了同一线程中的阻塞排队调用。现在换成两条不同的线程：假设把 Worker 的完成信号连接改为阻塞排队连接：

```cpp
connect(worker, &EventWorker::taskFinished,
        this, &EventDrivenWorkerDemo::onTaskFinished,
        Qt::BlockingQueuedConnection);
```

窗口析构时，仍然使用：

```cpp
QMetaObject::invokeMethod(
    worker, "cancelTask",
    Qt::BlockingQueuedConnection);
```

任务正在运行时关闭窗口，工作线程会执行 `cancelTask()`，其中包含：

```cpp
emit taskFinished(true);
```

这两处调用都跨越了不同线程，是否就能安全执行？还是仍可能死锁？请分别判断 GUI 线程与工作线程在等待谁。

### 补充提问：connect() 的第五个参数指定阻塞排队连接是什么意思？

在判断执行结果之前，我希望先了解：`connect()` 的第五个参数设为 `Qt::BlockingQueuedConnection` 时，具体表示什么？它会阻塞哪个线程，又会在什么时候结束阻塞？

### 参数解释

`connect()` 的第五个参数指定信号发出时，采用什么方式调用槽函数。

在这条连接中：

```cpp
connect(worker, &EventWorker::taskFinished,
        this, &EventDrivenWorkerDemo::onTaskFinished,
        Qt::BlockingQueuedConnection);
```

`this` 是属于 GUI 线程的窗口对象。Worker 在工作线程中发出 `taskFinished` 信号时，Qt 会把 `onTaskFinished()` 的调用请求排到 GUI 线程，并让发出信号的工作线程等待这个槽执行完。

需要区分两个时刻：执行 `connect()` 时，只是建立连接关系，没有发出信号，也不会等待槽执行。之后执行 `emit taskFinished(true)` 时，阻塞排队调用才真正发生。

如果 GUI 线程能够正常处理事件，过程是：

```text
工作线程                         GUI 线程

emit taskFinished(true)
        │
        ├── 投递槽调用 ─────────→ 请求入队
        │                         ↓
        │ 等待                    执行 onTaskFinished(true)
        │                         ↓
        │                         槽函数返回
        ↓                         │
结束等待 ←────────────────────────┘
继续执行 emit 后面的代码
```

其中，`Queued` 表示槽调用排队，由接收对象所属的线程执行；`Blocking` 表示发出信号的线程阻塞，直到接收槽返回。

它与 `invokeMethod()` 中的同名参数含义相同。`invokeMethod()` 直接发起调用请求；`connect()` 先建立连接关系，等发出信号时再触发调用。

### 我的回答

我认为这里会发生死锁，因为 GUI 线程与工作线程形成了互相等待的关系。

任务正在运行时关闭窗口，GUI 线程会通过阻塞排队调用，请工作线程执行 `cancelTask()`，并等待它返回。

工作线程执行 `cancelTask()` 时，又会发出 `taskFinished(true)`。由于这条信号连接也使用阻塞排队方式，工作线程需要等待 GUI 线程执行完 `onTaskFinished()`，才能继续执行并让 `cancelTask()` 返回。

因此，GUI 线程要继续执行，依赖于 `cancelTask()` 返回；而 `cancelTask()` 要返回，又依赖于 GUI 线程执行完 `onTaskFinished()`。两条线程互相依赖，导致死锁。

### 反馈与解释

这个推理正确。这次是两条线程互相等待的死锁。

完整的等待关系是：

```text
GUI 线程
阻塞在 invokeMethod()
等待工作线程执行完 cancelTask()
                ↓
工作线程
在 cancelTask() 中发出 taskFinished()
阻塞等待 GUI 执行完 onTaskFinished()
                ↓
GUI 线程仍在等待，无法处理这个槽调用
                ↓
两条线程都无法继续
```

关键在于：GUI 线程阻塞等待期间，不会继续处理自己的普通事件队列，因此排队过来的 `onTaskFinished()` 无法执行。

这说明，`Qt::BlockingQueuedConnection` 即使用于不同线程，也需要检查调用链中是否形成循环等待。

原项目中，`taskFinished` 到 `onTaskFinished` 的连接使用默认的 `Qt::AutoConnection`。信号从工作线程发出，而窗口属于 GUI 线程，因此这次调用采用普通排队方式。

工作线程发出信号后可以继续执行，让 `cancelTask()` 返回，GUI 线程也就能够结束 `invokeMethod()` 中的等待。这里并不要求 GUI 在结束等待之前完成界面更新；窗口析构过程中，界面更新也可能不再得到处理。

以上双向阻塞连接是用于分析的假设，当前项目保留默认的完成信号连接。
