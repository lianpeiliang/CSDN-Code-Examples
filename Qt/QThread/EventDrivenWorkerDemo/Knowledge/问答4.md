# 问答4：停止定时器后，工作线程也会结束吗？

## 问题

`cancelTask()` 中调用了：

```cpp
timer->stop();
```

停止定时器后，Worker 所在的工作线程也会结束吗？如果再次点击“开始任务”，Worker 还能接收到新的开始请求吗？为什么？

## 我的回答

停止定时器后，Worker 所在的工作线程不会结束，它的事件循环仍在运行。

我的理解是，此时界面状态会更新，表示本次由定时器推进的任务已经结束。再次点击“开始任务”后，Worker 仍然能够接收到新的开始请求，并再次调用定时器的 `start()`，重新开始任务。

## 反馈与补充

主要判断正确：停止定时器后，工作线程的事件循环仍然运行，所以还能接收新的开始请求。

需要补充的是，取消任务时不仅修改了界面状态。Worker 会执行：

```cpp
running = false;          // 标记任务不再运行
timer->stop();            // 停止定时触发
emit taskFinished(true);  // 通知 GUI 任务已取消
```

GUI 收到通知后，才更新状态文字和按钮。

再次点击“开始任务”，请求会排队到工作线程，执行 `startTask()`，重置任务进度并重新启动定时器。

任务结束与工作线程结束是两个不同的状态。当前示例取消任务时没有请求退出工作线程的事件循环，因此工作线程会继续运行，等待后续请求。

## 问题五：工作线程睡眠时，GUI 和取消请求分别会怎样？

如果在 `processOneStep()` 中加入：

```cpp
QThread::sleep(3);
```

让每一步都阻塞工作线程 3 秒，那么这 3 秒期间：

1. GUI 的“界面心跳”计数器会暂停吗？
2. 点击“取消任务”后，`cancelTask()` 能立即执行吗？

请分别说明原因。

### 我的回答

GUI 的“界面心跳”计数器不会暂停。上述代码阻塞的是工作线程，而心跳计数器由 GUI 线程中的定时器更新，依赖 GUI 线程的事件循环。因此，工作线程睡眠不会阻止 GUI 线程继续处理心跳更新。

`cancelTask()` 无法立即执行。点击取消时，工作线程可能仍在执行 `processOneStep()`，因此需要等该函数返回后，工作线程才有机会从事件队列中取出取消请求并执行 `cancelTask()`。

### 反馈与补充

两点都正确。

GUI 心跳由 GUI 线程中的定时器更新。`QThread::sleep(3)` 让调用它的工作线程睡眠，GUI 线程仍能继续处理自己的事件，因此心跳不会暂停。

取消请求则需要由工作线程处理。如果点击取消时，工作线程还在执行 `processOneStep()`，排队的 `cancelTask()` 就要等它返回后，才有机会执行。

这也说明：界面保持响应，不代表 Worker 能及时响应取消请求。两个线程各自的响应情况，取决于它们能否及时处理自己的事件。

## 问题六：Worker 发出进度信号后，GUI 槽在哪个线程执行？

示例中有以下连接，其中 `this` 是 GUI 线程中的窗口对象：

```cpp
connect(worker, &EventWorker::progressChanged,
        this, &EventDrivenWorkerDemo::updateProgress);
```

Worker 在工作线程中发出 `progressChanged` 信号后，`updateProgress()` 会在哪个线程执行？Qt 根据什么决定这一点？

### 我的回答

`updateProgress()` 会在 GUI 线程中执行。

这条连接使用默认的 `Qt::AutoConnection`。`progressChanged` 信号在工作线程中发出，而 `this` 指向的窗口对象归属于 GUI 线程。由于发出信号的线程与接收对象的归属线程不同，Qt 会采用排队调用，由接收对象所属的 GUI 线程执行槽函数。

### 反馈与补充

判断正确，`updateProgress()` 会在 GUI 线程中执行。

更准确地说，`this` 指向的窗口对象归属于 GUI 线程。默认的 `Qt::AutoConnection` 在信号发出时，会比较：

- 当前发出信号的线程：工作线程。
- 接收对象的归属线程：GUI 线程。

两者不同，因此采用排队调用，由 GUI 线程的事件循环执行 `updateProgress()`。

术语上需要区分：连接类型仍是 `Qt::AutoConnection`，这次调用采用了排队方式，并不是连接类型被修改成了 `Qt::QueuedConnection`。

## 问题七：直接连接到 GUI 槽是否安全？

如果将进度信号的连接改为：

```cpp
connect(worker, &EventWorker::progressChanged,
        this, &EventDrivenWorkerDemo::updateProgress,
        Qt::DirectConnection);
```

而 `updateProgress()` 内部会调用：

```cpp
progressBar->setValue(value);
```

那么，`updateProgress()` 会在哪个线程执行？这样更新进度条是否安全？为什么？

### 我的回答

`updateProgress()` 会在工作线程中执行，因此这样更新进度条是不安全的。

GUI 控件必须在 GUI 主线程中操作。从工作线程访问这些控件可能导致程序崩溃。

### 反馈与补充

判断正确。`Qt::DirectConnection` 会在发出信号的线程中立即执行槽。本例信号从工作线程发出，所以 `updateProgress()` 也在工作线程中执行。

`QProgressBar` 属于 GUI 控件，必须在 GUI 主线程中操作。跨线程调用 `setValue()` 不符合 Qt 的使用要求，可能导致显示异常或崩溃；没有立刻崩溃也不能说明安全。

因此，这里应使用默认的 `Qt::AutoConnection`，或显式指定 `Qt::QueuedConnection`，让 GUI 线程执行进度更新。

## 问题八：排队调用会让 Worker 等待 GUI 更新完成吗？

假设进度信号采用 `Qt::QueuedConnection`。Worker 在工作线程中执行：

```cpp
emit progressChanged(50);
```

它是否必须等待 GUI 线程执行完 `updateProgress()`，才能继续运行后面的代码？如果 GUI 线程正在忙，Worker 也会被卡住吗？为什么？

### 我的回答

Worker 不需要等待 GUI 线程执行完 `updateProgress()`。

执行该语句时，Qt 会将相应的槽调用及其参数投递到 GUI 线程的事件队列中，由 GUI 线程随后处理。GUI 线程与工作线程各自执行自己的代码，因此即使 GUI 线程正忙，Worker 也不会因为等待这次进度更新而被阻塞。

### 反馈与补充

这个理解正确。更准确地说，Qt 会把槽调用及其参数值 `50` 封装成事件，投递到 GUI 线程的事件队列中。

投递后，Worker 可以继续执行后面的代码，不需要等待 `updateProgress()` 执行完成。

如果 GUI 线程正忙，进度更新会延迟处理；Worker 仍能继续工作。这也意味着，界面上显示的进度可能暂时落后于任务的实际进度。
