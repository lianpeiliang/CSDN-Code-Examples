# 问答12：同一线程中的阻塞排队调用为什么会死锁？

## 问题十七：工作线程能阻塞等待自己的排队槽吗？

前面的窗口析构代码中，GUI 线程通过阻塞排队调用，请工作线程执行 `cancelTask()`。

现在换一种情况：假设在 Worker 的 `processOneStep()` 中写入以下代码：

```cpp
void EventWorker::processOneStep()
{
    QMetaObject::invokeMethod(
        this, "cancelTask",
        Qt::BlockingQueuedConnection);
}
```

此时，调用这段代码的线程与 `this` 所属的线程，都是工作线程。

`cancelTask()` 能正常执行，并让 `invokeMethod()` 返回吗？请从“谁在等待、谁负责处理队列”的角度判断。

### 补充提问：这条语句和各个参数是什么意思？

在判断执行结果之前，我希望先了解 `QMetaObject::invokeMethod()` 这条语句的含义，以及各个参数的作用，尤其是 `Qt::BlockingQueuedConnection` 表示什么。

### 语句与参数解释

这条语句表示：请 Qt 调用指定对象的 `cancelTask()`，使用排队方式，并让当前调用线程等待它执行完。

```cpp
QMetaObject::invokeMethod(
    this,
    "cancelTask",
    Qt::BlockingQueuedConnection);
```

各部分的含义如下：

| 部分 | 含义 |
| --- | --- |
| `QMetaObject::invokeMethod()` | Qt 提供的方法调用接口，可以指定目标对象、方法和调用方式 |
| `this` | 目标对象；这里是当前 Worker 对象 |
| `"cancelTask"` | 要调用的方法名；这里传入字符串，不加括号 |
| `Qt::BlockingQueuedConnection` | 阻塞排队调用：将请求排队，并阻塞当前调用线程，直到目标槽执行完 |

项目中的 `cancelTask()` 声明在 `public slots` 下，因此 Qt 的元对象系统可以按名称找到它。由于该槽不需要参数，这里也不需要继续传入槽函数的实参。

`BlockingQueuedConnection` 可以拆成两个部分理解：

- `Queued`：把调用请求投递到目标对象所属线程的事件队列，由那个线程执行。
- `Blocking`：发起调用的线程停在 `invokeMethod()` 这里，等待目标槽执行完，才能继续向下运行。

例如，GUI 线程调用工作线程中的 Worker 时，过程是：

```text
GUI 线程                         工作线程

调用 invokeMethod()
        │
        ├── 投递调用请求 ───────→ 请求入队
        │                         ↓
        │ 等待                    执行 cancelTask()
        │                         ↓
        │                         cancelTask() 返回
        ↓                         │
结束等待 ←────────────────────────┘
继续执行后面的代码
```

与普通排队调用相比，区别在于调用者何时继续运行：

| 调用方式 | 发起调用的线程何时继续？ |
| --- | --- |
| `Qt::QueuedConnection` | 请求投递后就可以继续 |
| `Qt::BlockingQueuedConnection` | 等目标槽执行完才继续 |

被阻塞的是发起调用的线程。这个调用不会创建新线程，目标槽仍需要由目标对象所属的线程执行。

### 我的回答

我认为不能正常执行，这里会发生死锁，相当于工作线程在等待自己。

工作线程使用排队方式请求执行 `cancelTask()`，然后阻塞在 `invokeMethod()` 中，等待这个槽执行完成。但处理队列、执行 `cancelTask()` 的也正是这条工作线程。

由于工作线程已经阻塞在这里，无法返回事件循环处理排队请求，`cancelTask()` 就无法执行；而槽没有执行完，工作线程也无法结束等待。因此，它会一直阻塞在这个位置。

### 反馈与解释

这个判断正确，原因就是同一条线程在等待自己处理队列。

等待关系可以整理为：

```text
工作线程等待 cancelTask() 执行完
        ↓
cancelTask() 需要工作线程处理队列才能执行
        ↓
工作线程阻塞在 invokeMethod()，无法处理队列
        ↓
双方等待条件都无法满足，发生死锁
```

因此，`cancelTask()` 无法执行，`invokeMethod()` 也无法正常返回。Qt 官方明确说明，同一线程内使用 `Qt::BlockingQueuedConnection` 会导致死锁。

在这个假设场景中，`processOneStep()` 已经在 Worker 所属的工作线程执行，因此可以直接调用：

```cpp
cancelTask();
```

它会立即执行，执行完再返回，不需要排队。这个直接调用成立的前提是：当前已经处于 Worker 所属的线程中。不能因此推导出 GUI 线程也可以直接调用该槽；本例的 `cancelTask()` 会访问 Worker 的状态并停止属于工作线程的定时器。

参考：[Qt 官方文档：QMetaObject::invokeMethod()](https://doc.qt.io/qt-6/qmetaobject.html#invokeMethod) · [Qt 官方文档：连接类型](https://doc.qt.io/qt-6/qt.html#ConnectionType-enum)。
