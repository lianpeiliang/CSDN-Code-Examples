# 问答1：重写 `run()` 和在 `QThread` 子类中定义普通槽有什么区别？

## 问题

当前 `RunOverrideDemo` 中，`WorkThread` 继承 `QThread`，并把耗时任务写在 `run()` 里。为什么不能简单地给 `QThread` 子类添加一个 `doWork()` 槽，然后认为这个槽会自动在工作线程执行？

## 回答

关键是区分 **`QThread` 对象的线程归属**和**`run()` 的执行线程**。它们虽然都关联同一个 `QThread` 对象，但并不因此在同一线程执行。

```cpp
class WorkThread : public QThread
{
    Q_OBJECT

protected:
    void run() override;
};

WorkThread thread; // 在 GUI 主线程创建
thread.start();    // Qt 在新线程中调用 run()
```

- `start()` 会启动底层线程，并在新线程中调用重写的 `run()`。因此，把一次性任务写在 `run()` 里，任务代码确实会在工作线程执行。
- `QThread` 对象本身仍属于创建它的线程。本例的 `WorkThread` 由 GUI 窗口创建，所以对象归属 GUI 主线程。
- `doWork()` 如果是 `WorkThread` 的普通槽，通过排队连接（`Qt::QueuedConnection`）调用时，会在接收对象的归属线程执行；因此它可能在 GUI 主线程执行，并不会因为槽写在 `QThread` 子类里就自动转到工作线程。

### 补充理解

假设 `WorkThread` 对象是在 GUI 主线程中创建的，那么它的线程归属仍是 GUI 主线程。调用 `thread.start()` 只会让重写的 `run()` 在新启动的工作线程中执行，并不会把 `WorkThread` 这个对象移动到工作线程。

因此，信号若通过 `Qt::QueuedConnection` 发给 `WorkThread` 对象的 `doWork()` 槽，调用会投递到接收对象所属线程的事件队列，之后由 GUI 主线程的事件循环执行。槽写在 `QThread` 子类里，并不决定槽在哪个线程执行；排队调用看的是接收对象的线程归属。

这和在 `run()` 中直接调用 `doWork()` 不同：直接调用是普通的 C++ 函数调用，会在当前执行它的工作线程里运行。若此时 GUI 主线程也会访问同一份成员数据，就要考虑线程安全。

直接连接（`Qt::DirectConnection`）则会在发出信号的线程里立即执行槽，所以槽的执行位置还取决于连接类型和发信号的线程。

## 我的理解与需要补充的地方

### 我对问答一的理解

我理解的核心是：给 `QThread` 子类添加一个普通槽，并不意味着这个槽会自动在 `start()` 创建的工作线程中执行。槽实际在哪个线程执行，要结合连接方式、信号发出时所在的线程，以及接收对象的线程归属来判断。

例如，`QThread` 子类对象如果是在 GUI 主线程创建的，它的对象归属仍是 GUI 主线程。槽是这个类的成员，并不会因此自动转到工作线程。连接的第五个参数可以指定连接方式；如果使用 `Qt::AutoConnection`，Qt 会根据线程情况选择直接调用或排队调用；如果使用 `Qt::QueuedConnection` 或 `Qt::DirectConnection`，则分别按指定方式处理。

### 需要补充和修正的地方

**1. `Qt::AutoConnection` 比较的是信号发出时执行 `emit` 的线程和接收对象的线程归属。**

它不是简单比较发送对象和接收对象各自的线程归属。信号发出时，如果执行 `emit` 语句的线程就是接收对象的归属线程，槽会直接调用；如果不是，调用会排入接收对象所属线程的事件队列。因此，从 `run()` 中发出的信号，执行 `emit` 的线程是工作线程，即使发信号的 `QThread` 对象本身仍归属 GUI 主线程。

**2. `Qt::QueuedConnection` 无论是否跨线程，都会排队。**

它会把调用放进接收对象所属线程的事件队列，等该线程的事件循环处理。即使发送和接收处于同一个线程，也不会因此改成直接调用。 “同线程时直接调用、跨线程时排队”是 `Qt::AutoConnection` 的选择规则，不是 `Qt::QueuedConnection` 的规则。

**3. `Qt::DirectConnection` 不限于同线程。**

它会在执行 `emit` 语句的线程里立即执行槽，即使接收对象属于另一个线程也是如此。跨线程直接执行时，槽可能在接收对象归属线程之外访问对象或其数据，因此需要谨慎处理线程安全。

所以，连接的第五个参数很重要，但判断槽的执行位置时不能只看这个参数：还要知道信号发出时执行 `emit` 的线程，以及接收对象属于哪个线程。槽写在 `QThread` 子类中这一点，本身不能决定槽在哪个线程执行。

### 追问：发送者对象属于 UI 线程，但在工作线程中发出信号，应该怎么判断？

#### 问题

假设一个 `QObject` 子类对象是在 UI 主线程创建的，因此对象归属 UI 主线程。连接信号和槽时，这个对象作为发送者传给 `connect()`；但之后工作线程中的代码（例如 `run()`）调用该对象的信号。此时，发送者对象属于 UI 主线程，而执行 `emit` 的线程是工作线程。对于 `Qt::AutoConnection`，应该依据哪一个线程来判断槽的调用方式？

#### 回答

要依据**信号发出时执行 `emit` 的线程**，而不是发送者对象的线程归属。`connect()` 中的发送者参数用于指定哪个对象的信号参与连接；它不会限制信号只能由该对象归属的线程发出。

因此，在这个例子中，虽然发送者对象归属 UI 主线程，但如果工作线程正在执行发出信号的代码，那么发出信号时执行 `emit` 的线程就是工作线程。`Qt::AutoConnection` 会将这个线程与接收对象的线程归属进行比较：相同则直接调用，不同则排队到接收对象所属线程的事件队列。

这就是为什么描述 `Qt::AutoConnection` 的判断依据时，说“信号发出时执行 `emit` 的线程”比说“发送者对象属于哪个线程”更准确。

### 追问：排队调用和直接调用有什么区别？

#### 问题

`Qt::QueuedConnection` 会把槽调用放进接收对象所属线程的事件队列。与直接调用相比，排队调用有什么不同？为什么需要排队？

#### 回答

主要区别在于**槽何时执行，以及在哪个线程执行**：

- **直接调用（`Qt::DirectConnection`）**：信号发出后，槽会立即在执行 `emit` 的线程中运行。槽返回后，发信号的代码才能继续执行。
- **排队调用（`Qt::QueuedConnection`）**：信号发出后，槽调用先进入接收对象所属线程的事件队列。发信号的代码可以继续运行；之后由接收对象所属线程的事件循环取出并执行槽。

排队不代表一定发生了跨线程。即使发送者和接收者属于同一个线程，明确指定 `Qt::QueuedConnection` 也会排队；当前代码继续运行，槽要等事件循环处理到这次调用时才执行。排队调用要得到处理，接收对象所属线程需要运行事件循环。

在 `RunOverrideDemo` 中，工作线程发出进度信号，接收对象是 GUI 主线程中的进度条。使用默认的 `Qt::AutoConnection` 时，因为执行 `emit` 的工作线程和进度条所属的 GUI 主线程不同，Qt 会选择排队调用。这样，进度条更新会在 GUI 主线程执行，而不是让工作线程直接操作界面。

### 追问：排队调用会等当前代码执行完再运行槽吗？

#### 问题

我理解，直接调用时，执行到 `emit` 就会立刻执行槽函数；排队调用时，Qt 会先把槽调用放入事件队列，让当前代码继续执行，等事件循环处理到它时再取出并执行槽函数。这个理解对吗？

#### 回答

这个理解基本正确。两种方式的执行顺序可以这样表示：

```text
直接调用：执行 emit → 立即执行槽 → 槽返回 → 继续执行 emit 后面的代码

排队调用：执行 emit → 调用进入事件队列 → emit 返回并继续执行后续代码
          → 控制权回到事件循环 → 事件循环取出调用并执行槽
```

因此，排队调用不会在 `emit` 这一行同步执行槽。通常要等当前事件处理完成、控制权回到事件循环后，槽才会被执行。即使发信号和接收对象属于同一个线程，明确指定 `Qt::QueuedConnection` 也遵循这个异步顺序。

### 追问：跨线程使用 `Qt::DirectConnection` 时，槽会在哪里执行？

#### 问题

假设信号在工作线程 A 中发出，槽的接收对象归属于线程 B，并且连接类型是 `Qt::DirectConnection`。我理解槽会立即在执行 `emit` 的线程 A 中运行，而不是切换到接收对象所属的线程 B。由于这相当于在线程 A 中调用线程 B 所属对象的函数，如果线程 B 同时访问这个对象，就可能产生线程安全问题。这样的理解是否正确？

#### 回答

这个理解是正确的。`Qt::DirectConnection` 会在执行 `emit` 的线程中立即调用槽；它不会因为接收对象归属于线程 B，就把槽切换到线程 B 执行。接收对象的线程归属也不会因此改变。

因此，在线程 A 中执行的槽代码可能访问归属于线程 B 的对象。如果线程 B 同时处理该对象的事件或访问其数据，就可能发生并发访问和线程安全问题。是否真的发生冲突，取决于线程 B 是否同时访问相关对象或数据；但这种跨线程直接调用需要谨慎设计。特别是接收对象为 GUI 控件时，不应从工作线程直接调用其界面操作，应通过排队调用把操作交给 GUI 主线程处理。

### 追问：为什么说 `Qt::AutoConnection` 对新手比较友好？

#### 问题

通过上面对跨线程 `Qt::DirectConnection` 的讨论，我注意到 `Qt::AutoConnection` 会根据线程情况自动选择直接调用或排队调用。它在一定程度上能帮助初学者避免跨线程直接调用接收对象的槽，以及由此带来的线程安全问题吗？

#### 回答

是的。`Qt::AutoConnection` 是一种便于使用的默认策略：如果执行 `emit` 的线程与接收对象的线程归属相同，就直接调用槽；如果不同，就把调用排队到接收对象所属线程，由该线程的事件循环执行。这样，跨线程信号槽连接通常不会像 `Qt::DirectConnection` 那样，在发信号的线程中直接执行接收对象的槽。

不过，`Qt::AutoConnection` 只负责决定这次信号槽调用采用直接方式还是排队方式。它不会自动保护多个线程共享的数据，也不会让任意跨线程的普通函数调用变得安全。如果多个线程直接读写同一份数据，或代码绕过信号槽直接调用另一个线程对象的成员函数，仍需要自行设计同步或线程间通信方式。
