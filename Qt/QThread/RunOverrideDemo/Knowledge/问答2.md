# 问答2：重写 `run()` 后还会运行事件循环吗？

## 问题

当前 `RunOverrideDemo` 中的 `WorkThread::run()` 没有显式调用 `QThread::exec()`。这是否表示工作线程没有运行事件循环？没有工作线程事件循环时，进度信号和取消请求又是怎样工作的？

## 回答

是的，当前示例的工作线程没有运行事件循环。

调用 `QThread::start()` 后，Qt 会在新线程中调用重写的 `run()`。如果没有重写 `run()`，`QThread` 默认的 `run()` 实现会调用 `exec()`；但本例提供了自己的 `run()`，其中没有调用 `exec()`，所以它直接执行任务循环，返回后线程结束。

本例的 `run()` 大致执行以下逻辑：

```cpp
for (int value = 0; value <= 100; value += 5) {
    if (isInterruptionRequested())
        return;

    emit progressChanged(value);

    if (value < 100)
        QThread::msleep(150);
}
```

**进度仍能更新**，因为 `progressChanged` 信号发出后，连接到 GUI 进度条的调用会排队到进度条所属的 GUI 主线程。GUI 主线程的事件循环处理这个调用并更新控件；这不要求工作线程自己的事件循环正在运行。

**取消也不依赖工作线程事件循环**。GUI 线程调用 `requestInterruption()` 设置协作式中断请求，`run()` 在任务循环中主动检查 `isInterruptionRequested()`，读到请求后返回。`QThread::msleep()` 只让当前工作线程睡眠，不会替它处理事件；取消请求会在下一次检查时被发现。

这种写法适合在线程中执行一段明确的任务，然后让线程结束。如果希望工作线程持续接收排队槽、定时器或其他事件，就需要工作线程运行事件循环。常见做法是把独立的 `QObject` Worker 移入 `QThread`，由线程事件循环调度 Worker 的事件和槽。

参考：[Qt 5.12 `QThread::run()` 实现](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread.cpp)

## 追问：`run()` 返回后，线程会结束并发出 `finished()` 吗？

### 问题

在这个示例中，`WorkThread::run()` 执行到结尾并返回后，`QThread` 管理的工作线程是否就结束了？Qt 是否会发出 `QThread::finished()` 信号？这是否意味着 `QThread` 对象也被销毁？

### 回答

是的。`run()` 返回后，这条工作线程的执行就结束了，Qt 会发出 `QThread::finished()` 信号。本例中，任务正常执行到结尾会返回；如果收到中断请求，也会在检查点 `return`。两种情况都会结束 `run()`，随后发出线程的 `finished()` 信号。

`finished()` 通知线程执行已经结束，但**不会自动销毁 `QThread` 对象**。本例中的 `workerThread` 是窗口的成员对象，线程结束后对象仍然存在；等线程完全停止后，可以再次调用 `start()` 启动它。

本例将 `QThread::finished()` 连接到窗口的 `onThreadFinished()`。信号从工作线程发出，窗口对象属于 GUI 主线程，因此默认连接会把处理排队到 GUI 主线程；之后界面更新状态并重新启用“开始任务”按钮。

## 追问：发出 `finished()` 时，线程是不是已经完全停止？

### 问题

`run()` 返回后会发出 `QThread::finished()`。发出信号时，工作线程是否已经完全停止？“线程还在做清理”该怎样理解？

### 回答

这里要区分任务执行结束和线程完全停止：

```text
run() 返回
  → 工作线程发出 QThread::finished()
  → 工作线程完成最后的清理并完全停止
```

`finished()` 发出时，`run()` 中的任务已经结束，线程事件循环也已经停止；但线程还可能处于最后的清理阶段。因此，“线程还在”不是说 `run()` 还在执行任务，而是说底层线程的退出过程可能尚未全部完成。

本例中，`finished()` 信号从工作线程发出。连接到窗口的槽会排队到 GUI 主线程执行，所以 `onThreadFinished()` 处理通知时，工作线程通常已经完成退出。若需要明确等待底层线程完全结束，可以调用 `wait()`。线程完全停止后，同一个 `QThread` 对象可以再次调用 `start()`；`QThread` 对象本身不会因线程结束而自动销毁。

参考：[Qt 5.12 `QThread::finished()` 说明](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread.cpp)

## 追问：再次调用 `start()` 是不是创建了新线程？

### 问题

当前示例的 `run()` 返回后，工作线程就停止了。那么之后再次调用 `start()`，是重新创建一个线程，还是继续使用之前那条线程？`QThread` 对象会怎样？

### 回答

`run()` 返回后，这一轮对应的底层线程执行结束。之后再次调用 `start()`，Qt 会启动新一轮底层线程执行，并再次调用 `run()`；它不是让已经停止的那一轮线程继续运行。

与此同时，`QThread` 这个 C++ 对象仍然存在，可以管理后续的线程执行：

```text
同一个 QThread 对象
  ├─ start() → 一轮底层线程执行 run() → run() 返回，线程结束
  └─ start() → 新一轮底层线程执行 run() → run() 返回，线程结束
```

因此可以说，下一次 `start()` 会启动新一轮底层线程，但不会重新创建 `QThread` 对象。操作系统可能复用线程 ID，所以不应只凭 ID 是否变化判断是不是同一轮执行。若线程仍在运行时再次调用 `start()`，Qt 不会另开一轮执行。

当前 demo 采用的是“一次任务结束，线程也结束”的模式。如果希望工作线程持续存活并多次接收任务，需要设计持续运行的任务循环，或使用带事件循环的线程和 Worker 对象。

参考：[Qt 5.12 `QThread::start()` 说明](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread.cpp)
