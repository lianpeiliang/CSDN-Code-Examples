# 问答6：为什么 `QThread` 子类的成员数据也要注意线程安全？

## 问题

`QThread` 子类中的成员变量看起来属于线程类。为什么还需要考虑线程安全？如果重写的 `run()` 和普通槽都访问这些成员，会有什么问题？

## 回答

需要区分 **`QThread` 对象的线程归属**和**底层工作线程中正在执行的代码**。`QThread` 子类对象通常仍属于创建它的线程；调用 `start()` 后，Qt 则在新启动的底层线程中调用重写的 `run()`。所以同一个对象的成员数据可能被不同线程中的代码访问。

普通成员变量本身不是 `QObject`，没有独立的线程归属；它们只是 `QThread` 对象里的数据。如果 `run()` 在工作线程访问某个成员变量，而普通槽又在 GUI 主线程访问同一份数据，就会出现跨线程共享访问。若读写没有同步保护，可能产生数据竞争和难以预测的结果。

例如，假设 `WorkThread` 在 GUI 主线程创建：

```cpp
class WorkThread : public QThread
{
    Q_OBJECT

public slots:
    void resetCount(); // 排队调用时通常在对象归属的 GUI 主线程执行

protected:
    void run() override; // start() 会让它在工作线程执行

private:
    int count = 0; // 两个执行上下文若同时读写，就需要同步
};
```

如果 `run()` 更新 `count` 的同时，GUI 主线程中的 `resetCount()` 也修改它，这两个操作可能同时发生。即使变量写在 `QThread` 子类中，也不会自动变成“工作线程专属”或自动获得线程保护。

可以根据数据的使用方式选择保护方案：用互斥锁保护共享读写，用原子类型处理适合原子操作的简单数据，或者设计清楚的单线程所有权，让数据只由一个线程访问，并通过信号槽传递结果或请求。

当前 `RunOverrideDemo` 没有让普通槽和 `run()` 同时读写同一份任务状态：耗时循环直接写在 `run()` 中；进度通过 `progressChanged` 信号发回 GUI；取消通过 `requestInterruption()` 通知，再由 `run()` 主动检查 `isInterruptionRequested()`。

如果需要工作线程长期接收排队槽、定时器或其他事件，常见做法是创建独立的 `QObject` Worker，并用 `moveToThread(&thread)` 将它的线程归属转到工作线程。这样，排队调用（queued invocation）会把发给 Worker 的槽和事件交由工作线程的事件循环处理。
