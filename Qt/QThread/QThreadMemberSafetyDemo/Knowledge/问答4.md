# 问答4

## 问题二十五：`finished()` 发出后，线程还会做什么？

### 问题

`run()` 返回并发出 `QThread::finished()` 信号后，线程是否已经完成了所有清理？为什么有时还需要调用 `wait()`？

### 我的回答

`run()` 函数结束后，会触发 `finished()` 信号。这表示 `run()` 已经结束，但线程可能还在执行最后的清理工作。因此，线程的结束可以理解为两个阶段：先是 `run()` 返回并发出信号，然后线程完成剩余清理；调用 `wait()` 可以等待清理完成。

### 反馈与补充

对，你把这两个阶段分清楚了：先是 `run()` 返回，随后 Qt 发出 `QThread::finished()`；但线程还可能执行最后的清理。`wait()` 会等到线程完全结束，因此 `finished()` 信号和“线程的所有清理都完成”不一定是同一时刻。

## 问题二十六：`finished()` 信号与槽分别在哪个线程？

### 问题

`QThread::finished()` 信号是在哪个线程发出的？连接到窗口对象 `this` 的 `onThreadFinished()` 槽又会在哪个线程执行？

### 我的回答

`onThreadFinished()` 会在 GUI 主线程执行，因为接收方是窗口对象 `this`，它属于 GUI 主线程。`QThread::finished()` 信号本身应该是在工作线程发出的，虽然我起初不确定这一点。信号在哪个线程发出，不会改变接收方槽函数最终在 GUI 主线程执行这一点。

### 反馈与补充

你的判断是对的：`onThreadFinished()` 会在 GUI 主线程执行，因为接收对象是 `this`，而窗口对象属于 GUI 主线程。

`QThread::finished()` 是在线程结束流程中，从工作线程发出的；Qt 文档说明它会从关联的线程发出。虽然 `CounterThread` 这个 `QThread` 对象本身属于 GUI 线程，但**发射信号的代码正在工作线程中执行**。[Qt：QThread](https://doc.qt.io/qt-6/qthread.html)

因此，默认的 `Qt::AutoConnection` 会把这个调用排到 GUI 线程的事件队列，之后由 GUI 线程执行 `onThreadFinished()`。这也是它可以安全更新界面状态的原因。

## 问题二十七：使用 `Qt::DirectConnection` 会有什么问题？

### 问题

如果将 `QThread::finished()` 到 `onThreadFinished()` 的连接显式设为 `Qt::DirectConnection`，槽会在哪个线程执行？这会有什么风险？

### 我的回答

`Qt::DirectConnection` 会让槽在发出信号的线程中立即执行。由于 `QThread::finished()` 是在工作线程中发出的，`onThreadFinished()` 也会在工作线程执行。这样槽里更新界面控件，就违反了界面控件应由 GUI 主线程访问的要求；我原先认为这会直接导致程序崩溃。

### 反馈与补充

你的执行线程判断是对的：`Qt::DirectConnection` 会让槽立即在发出信号的线程执行。这里 `finished()` 是从工作线程发出的，所以 `onThreadFinished()` 也会在工作线程执行。

不过，“肯定直接崩溃”说得太绝对了。它会从工作线程调用 `setText()` 和 `setEnabled()`，这违反了 Qt 对界面控件线程使用的要求。具体表现可能因运行环境而异；即使暂时正常运行，也仍然是不安全的跨线程界面操作。[Qt：线程与 QObject](https://doc.qt.io/qt-6/threads-qobject.html)

这个项目还有一个更具体的问题：`onThreadFinished()` 里调用了 `counterThread.wait()`。如果槽因 `DirectConnection` 在工作线程执行，就相当于工作线程等待自己结束，形成自等待。Qt 5.12 的 Windows 实现会对此发出警告并让 `wait()` 失败。[Qt 5.12 源码](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread_win.cpp)

## 问题二十八：为什么默认连接会把槽排到 GUI 线程？

### 问题

为什么当前默认连接方式不会让 `onThreadFinished()` 在工作线程执行？

### 我的回答

`QThread::finished()` 信号是在工作线程发出的，而接收对象 `this` 属于 GUI 主线程。`Qt::AutoConnection` 检测到信号发出线程与接收对象所属线程不同，就会把槽调用排入接收对象所属的 GUI 主线程事件队列，之后由 GUI 主线程执行 `onThreadFinished()`。

### 反馈与补充

你的判断过程是对的：`finished()` 在工作线程发出，而接收对象 `this` 属于 GUI 主线程，所以 `Qt::AutoConnection` 会把槽调用排到接收对象所属的 GUI 主线程执行。

判断时要区分两件事：`QThread` 对象本身属于 GUI 线程；但 `emit finished()` 这行代码是在工作线程中执行。`Qt::AutoConnection` 会根据发出信号时所在的线程和接收对象的线程归属，决定直接调用还是排队调用。

## 问题二十九：同线程下 `Qt::AutoConnection` 如何调用？

### 问题

如果发出信号时所在的线程，与接收对象所属的线程相同，默认的 `Qt::AutoConnection` 会选择什么调用方式？槽会立刻执行吗？

### 我的回答

当发出信号的线程与接收对象所属的线程相同时，`Qt::AutoConnection` 会采用 `Qt::DirectConnection`。槽会立即执行。

### 反馈与补充

答对了。`Qt::AutoConnection` 在发信号时判断：如果当前发信号的线程与接收对象所属线程相同，就采用直接调用。槽会立刻执行，等槽返回后，`emit` 后面的代码才继续运行。

## 问题三十：直接连接下，发信号的代码何时继续？

### 问题

如果同线程下 `Qt::AutoConnection` 选择了直接调用，而槽需要耗时两秒，发出信号的那段代码会马上继续执行，还是要等槽执行完？

### 我的回答

代码先执行 `emit`，然后立即进入槽函数。槽函数执行完并返回后，才会继续执行 `emit` 后面的下一句代码。

### 反馈与补充

对。这里应该是 `emit`。同线程下 `Qt::AutoConnection` 会直接调用槽，所以顺序是：

```text
执行 emit → 进入槽 → 槽执行完并返回 → 执行 emit 后的下一句
```

因此，如果槽耗时两秒，发信号的代码也要等槽返回后才能继续。
