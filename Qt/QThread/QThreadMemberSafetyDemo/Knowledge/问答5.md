# 问答5

## 问题三十一：改用信号传递计数值后，还需要互斥锁吗？

### 场景

假设删除 GUI 定时器和 `readCounter()`，改成让 `run()` 每次递增后发出 `counterChanged(counterValue)`，并用排队连接让 GUI 显示信号参数。“重置计数”按钮仍调用 `resetCounter()`。

初始改动如下：工作线程在锁内递增，但离开锁的作用域后才读取 `counterValue` 作为信号参数。

```cpp
// CounterThread::run()：工作线程
void CounterThread::run()
{
    while (!isInterruptionRequested()) {
        {
            QMutexLocker locker(&counterMutex);
            ++counterValue;
        }

        emit counterChanged(counterValue);
        QThread::msleep(10);
    }
}
```

信号通过排队连接发送给 GUI，GUI 槽只显示收到的参数：

```cpp
connect(&counterThread, &CounterThread::counterChanged,
        this, &QThreadMemberSafetyDemo::showCounter,
        Qt::QueuedConnection);

void QThreadMemberSafetyDemo::showCounter(int value)
{
    counterLabel->setText(QStringLiteral("共享计数：%1").arg(value));
}
```

重置槽仍在 GUI 主线程调用，并使用同一把锁：

```cpp
void CounterThread::resetCounter()
{
    QMutexLocker locker(&counterMutex);
    counterValue = 0;
}
```

我们按访问发生的顺序，一步步判断这些操作是否仍需要锁。

### 第一步：递增操作在哪个线程？有没有加锁？

**提问：** `++counterValue` 在哪个线程执行？它是否处于互斥锁保护范围内？

**我的回答：** `++counterValue` 在工作线程执行，而且它位于 `QMutexLocker` 的作用域内，所以递增时持有 `counterMutex`。

**反馈：** 对。工作线程执行递增，离开对应的花括号时，`QMutexLocker` 析构并释放锁。

### 第二步：发信号时还会访问共享变量吗？

**提问：** 执行 `emit counterChanged(counterValue)` 时，工作线程还要读取 `counterValue` 吗？这次读取发生在信号进入 GUI 事件队列之前还是之后？

**我的回答：** 工作线程需要先读取 `counterValue`，才能把它作为信号参数传出；这个读取发生在信号进入 GUI 事件队列之前。

**反馈：** 对。发出信号时，工作线程要先求出实参 `counterValue` 的值。排队连接稍后才会把参数交给 GUI 槽；它不会把“读取共享成员”这一步也推迟到 GUI 线程。

### 第三步：读取信号参数时，锁还在吗？

**提问：** 递增代码的花括号已经结束后，`QMutexLocker` 还持有锁吗？如果 GUI 同时重置计数，会不会与信号参数读取发生冲突？

**我的回答：** 这时 `QMutexLocker` 已经释放了锁。GUI 可能正在重置 `counterValue`，因此信号参数读取可能与重置同时访问这个共享变量。

**反馈：** 对。`run()` 中递增虽受锁保护，但 `emit counterChanged(counterValue)` 在锁外读取成员变量。主线程重置时持有同一把锁，也无法阻止这次没有加锁的读取；因此仍可能发生数据竞争。

### 第四步：GUI 槽读取的是共享成员还是参数副本？

**提问：** `showCounter(int value)` 使用的是共享成员 `counterValue`，还是信号传过来的 `value`？GUI 槽是否直接读取了那份共享数据？

**我的回答：** GUI 槽使用传过来的 `value` 参数，不会直接访问共享成员 `counterValue`。

**反馈：** 对。排队连接把 `int` 参数的值传给槽；槽显示的是参数副本。GUI 槽这一步不直接读取共享成员，所以不需要为了这次显示再去锁 `counterValue`。

### 第五步：整体上能不能删除互斥锁？

**提问：** 递增、信号参数读取和 GUI 重置都直接访问 `counterValue`。哪些访问可能并发？能否因此完全删除 `counterMutex`？

**我的回答：** 递增、发信号时读取参数、GUI 重置都会直接访问同一个共享成员，需要用同一把锁协调。GUI 槽只使用信号参数副本，不直接访问共享计数器。

**反馈与补充：** 结论正确：不能删除互斥锁。递增和重置需要互斥；发信号时读取参数也要安全地取得计数值。可以在锁内先把成员值复制到局部变量，再释放锁并发出信号：

```cpp
int snapshot;
{
    QMutexLocker locker(&counterMutex);
    ++counterValue;
    snapshot = counterValue;
}
emit counterChanged(snapshot);
```

这样，工作线程在持锁时完成递增和快照读取；排队信号传递的是局部变量 `snapshot` 的值。GUI 槽显示这个参数副本，不会直接访问共享的 `counterValue`。
