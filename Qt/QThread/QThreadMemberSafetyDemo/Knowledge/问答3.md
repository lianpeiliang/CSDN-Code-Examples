# 问答3

## 问题十七：耗时槽执行时，事件队列和优先级会怎样？

### 问题

假设一个排队槽需要耗时两秒。它执行时 GUI 界面会发生什么？排在后面的槽调用和其他 GUI 事件会怎样？Qt 是否会根据事件优先级来处理它们？

### 我的回答

如果耗时槽在 GUI 主线程执行，GUI 界面肯定会卡住。至于后续的槽调用和 GUI 事件如何执行，我还不确定，也不清楚 Qt 底层是否会根据优先级安排它们。

### 反馈与解释

你的判断对：如果这个两秒的槽在 GUI 主线程执行，GUI 界面会卡住。槽还没返回时，主线程的事件循环就无法继续处理排队槽、用户输入等其他工作；它们先等在队列里，槽返回后事件循环才继续处理。Qt 对排队连接的描述也是：槽要等控制权回到接收对象所属线程的事件循环时才执行。[Qt：跨线程信号与槽](https://doc.qt.io/qt-6/threads-qobject.html)

关于“优先级”，可以这样理解：

- **优先级不会打断正在运行的槽。** 两秒的槽一旦开始，就会一直占着 GUI 主线程，直到它返回。
- Qt 确实允许给用 `postEvent()` 投递的事件设置优先级：优先级高的排在前面，同优先级的按投递顺序处理。[Qt：QCoreApplication::postEvent](https://doc.qt.io/qt-6/qcoreapplication.html)
- 但这不代表排队槽或界面事件能抢占当前正在运行的槽。对这里的现象，关键是**主线程被槽占用，事件循环暂时没机会处理其他事情**。

可以把过程想成：

```text
GUI 主线程：开始执行槽 A（耗时 2 秒）
事件队列：  槽 B、输入事件、界面更新等继续等待
GUI 主线程：槽 A 返回
事件循环：  恢复处理等待中的事件
```

所以，要让界面持续响应，耗时工作通常应该放到工作线程执行，再通过信号把结果送回 GUI 线程。Qt 也建议把长时间操作移出 GUI 线程，以免冻结界面。[Qt：事件队列与线程同步](https://doc.qt.io/qt-6/threads-synchronizing.html)

## 问题十八：槽 B 和其他 UI 事件谁先处理？

### 问题

耗时槽返回后，排队槽调用 B 和其他 UI 事件谁会先处理？Qt 会根据什么规则决定？

### 回答

**没有一个适用于所有 UI 事件的固定答案**，不能简单断定“槽 B 一定先执行”或“界面事件一定先执行”。

在这个场景里可以这样看：

- 槽 B 的排队调用会作为一个 `MetaCall` 事件放进 GUI 线程的事件队列。Qt 5.12 的源码显示，排队信号槽会通过 `QCoreApplication::postEvent()` 投递这个调用。[Qt 5.12 源码](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/kernel/qobject.cpp)
- 对通过 `postEvent()` 投递的事件，Qt 按优先级处理：优先级高的先处理；优先级相同的按投递顺序处理。[Qt：`QCoreApplication::postEvent`](https://doc.qt.io/qt-6/qcoreapplication.html)
- 但 UI 事件不全是同一类“排队事件”：鼠标输入可能来自系统事件，界面重绘也有自己的处理方式。因此，不能仅凭“槽 B 和 UI 事件都在等”就推断它们之间一定谁先。

可以确定的是：两秒槽 A 运行期间，主线程不会处理这些等待的工作；槽 A 返回后，事件循环才恢复处理。**优先级影响等待中的事件怎么排，但不会中断正在运行的槽 A。**

## 问题十九：`requestInterruption()` 如何让线程停止？

### 问题

点击“停止计数线程”后，`requestInterruption()` 会立即终止工作线程吗？结合 `run()` 里的循环，说说线程是怎样发现停止请求并退出的。

### 我的回答

`requestInterruption()` 可以理解为设置一个标志位，还需要结合 `run()` 中的代码配合使用。请求发出后，`run()` 里的 `while` 循环会检查这个标志，并在条件不满足时结束循环。由于本例的 `run()` 没有运行事件循环，循环结束后线程会退出，并进行线程相关的资源清理。

### 反馈与补充

你的理解基本正确。`requestInterruption()` 是协作式停止请求，不会直接杀掉线程；`run()` 在 `while (!isInterruptionRequested())` 处检查它。请求如果在 `msleep(10)` 期间到达，睡眠本身不会被打断，线程会在睡眠结束、下一次检查条件时退出循环。

因为这个 `run()` 没有调用 `exec()`，工作线程没有启动 Qt 事件循环。循环结束后，`run()` 返回，线程随后结束并发出 `finished()` 信号；Qt 再完成相关的线程清理。

## 问题二十：析构时为什么同时请求中断并等待？

### 问题

窗口析构时，为什么既调用 `requestInterruption()`，又调用 `wait()`？这两个操作各自解决什么问题？

### 我的回答

窗口析构时，首先调用 `requestInterruption()`，请求工作线程中的 `run()` 停止执行并退出。`run()` 返回后，工作线程就会结束。随后调用 `wait()`，等待工作线程完成退出和相关的后台清理工作。

### 反馈与补充

你的理解基本正确，应该是“窗口析构时”调用这两个函数：

- `requestInterruption()` 发出停止请求；`run()` 检查到请求后退出循环并返回。它不会直接强制结束线程。
- `wait()` 让析构函数所在的线程等到工作线程真正结束。它本身不负责释放工作线程资源，而是确保线程结束后，程序再继续销毁相关对象。

这样可以避免 `CounterThread` 对象已经销毁，工作线程却还在执行 `run()`。

## 问题二十一：`wait()` 等待线程结束是什么意思？

### 我的提问

反馈中提到，`wait()` 本身不负责释放工作线程资源，而是等待线程结束后再继续销毁相关对象。这句话应该怎样理解？

### 回答

这里的关键是：**`wait()` 负责等待，不负责停止线程或替它清理资源。**

窗口析构时大致按这个顺序执行：

```text
1. requestInterruption()：通知工作线程“请尽快停下”
2. 工作线程检查到请求，退出 run()
3. wait()：主线程在这里等待，直到工作线程确实结束
4. 析构函数继续完成，CounterThread 对象随后被销毁
```

`run()` 返回后，线程才会结束，线程运行时使用的资源也会随线程退出而清理。`wait()` 的作用是让主线程确认这件事已经完成，再继续销毁 `CounterThread` 等相关对象。否则对象已经销毁，工作线程却还在访问它，就可能出问题。

可以把它理解成：`requestInterruption()` 是发出“请下班”的通知，`wait()` 是等对方确认下班后，自己再离开。前者请求停止，后者等待结束。

## 问题二十二：线程不响应中断时，`wait()` 会怎样？

### 问题

如果 `run()` 不检查中断请求，或者长时间执行无法中断的操作，窗口析构时调用 `wait()` 会怎样？窗口能马上关闭吗？

### 我的回答

如果 `run()` 不检查中断请求，`requestInterruption()` 就不能让它停止。此时调用 `wait()`，调用线程会一直等到 `run()` 执行完，因此窗口不能马上关闭。这两个调用在析构流程中需要配合：中断请求让线程有机会主动停止，`wait()` 等它真正结束；中断请求不是强制终止线程的手段。

### 反馈与补充

你的理解基本正确：如果 `run()` 不检查中断请求，`requestInterruption()` 不会让它停下来；此时调用 `wait()`，调用它的线程就会一直等到 `run()` 自己返回。若它始终不返回，窗口也就无法继续完成析构、关闭程序。

补充一点：`wait()` 并不依赖 `requestInterruption()` 才能工作。线程自然结束时，单独调用 `wait()` 也能等它结束。它们在析构流程里配合使用：一个请求线程尽快停止，一个确保线程结束后再销毁对象。

## 问题二十三：停止按钮为什么不调用 `wait()`？

### 问题

点击“停止计数线程”时，`stopCounter()` 只调用 `requestInterruption()`，没有调用 `wait()`。这样设计有什么好处？如果在这个槽里直接调用 `wait()`，界面会怎样？

### 我的回答

如果在停止按钮的槽函数中直接调用 `wait()`，GUI 界面会卡住，直到工作线程结束后才恢复响应。这样的卡顿会持续到工作线程结束并完成相关资源清理。只请求中断而不立即等待，可以避免让界面同步等待工作线程。

### 反馈与补充

你的理解大体正确：如果在 `stopCounter()` 里调用 `wait()`，GUI 主线程会一直等到工作线程结束，这段时间界面会卡住。

补充一点：`wait()` 不负责释放线程资源，它只是阻塞调用它的主线程，直到工作线程结束。工作线程是 `run()` 检查到中断请求后退出的；线程结束时，相关清理随之完成。本例中它通常很快会退出，但仍没必要让停止按钮同步等待。现在的设计是先发出中断请求，再由 `finished()` 信号通知界面更新状态。

## 问题二十四：为什么等线程结束后才重新启用启动按钮？

### 问题

为什么程序要等到 `finished()` 后，才重新启用“启动计数线程”按钮？能不能在发出中断请求后就立刻启用？

### 我的回答

这是一个时机问题。发出中断请求后，旧的工作线程可能还没有完全结束；如果这时就重新启用启动按钮，用户可能会在旧线程尚未清理完成时尝试再次启动线程。

### 反馈与补充

你抓住了“时机”这个重点：要等旧线程结束后，再允许用户重新启动。

更精确地说，提前启用按钮不会直接创建第二条并行线程：`startCounter()` 会先检查 `isRunning()`，如果旧线程仍在运行就直接返回。但这时点击启动没有效果，界面状态也会让人误以为可以重启。所以程序等到线程结束后才重新启用按钮。

另外，Qt 的 `finished()` 信号发出后，线程可能还在做最后的清理；调用 `wait()` 可以确认这些工作完成，再允许重启。[Qt：QThread](https://doc.qt.io/qt-6/qthread.html)
