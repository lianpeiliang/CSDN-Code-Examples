# 问答2：`app.exec()` 起什么作用？

## 问题

在 Qt 程序中，`app.exec()` 是做什么的？调用它以后程序会怎样运行？它会不会创建新线程或导致界面卡住？

## 回答

`app.exec()` 用于启动 Qt 应用的主事件循环。在这个示例中，程序按顺序创建应用对象、创建并显示窗口，随后调用 `app.exec()`：

```cpp
QApplication app(argc, argv);
GuiBlockingDemo window;
window.show();
return app.exec();
```

进入事件循环后，Qt 会持续处理窗口相关事件，例如鼠标和键盘输入、窗口重绘、定时器超时等。事件循环会一直运行，直到应用要求退出。通常关闭最后一个窗口会使应用退出；代码也可以调用 `QApplication::quit()` 或 `QApplication::exit()`。

`exec()` 会持续运行，直到事件循环退出后才返回。因此，`main()` 中 `app.exec()` 后面的代码要等到那时才会执行。`return app.exec();` 还会把事件循环的退出码作为程序的退出码返回。

`app.exec()` 不会创建新线程，也不代表界面卡住。它是在 GUI 主线程中正常运行事件循环。这个示例真正让界面暂时卡住的，是按钮回调中的 `QThread::sleep(5)`：它阻塞了 GUI 主线程，使主线程无法继续处理事件循环中的其他工作。

## 追问：`app.exec()` 内部大致如何运行？

### 问题

以 Qt 5.12 为例，`app.exec()` 内部大致如何启动并运行事件循环？事件循环怎样等待和处理事件，又在什么情况下退出？

### 回答

`QApplication::exec()` 使用 `QCoreApplication` 提供的应用级事件循环。可以把内部过程简化理解为：

```cpp
while (!收到退出请求) {
    等待或处理可用事件();
}
return 退出码;
```

大致按以下步骤运行：

1. `QCoreApplication::exec()` 检查应用和线程状态，然后创建一个 `QEventLoop` 并调用它的 `exec()`。
2. `QEventLoop::exec()` 进入循环，反复调用事件处理逻辑，并带上“没有事件时可以等待”的选项。
3. 事件分发器等待操作系统或 Qt 的事件到来；有事件时，将它们交给相应的对象和控件处理。比如鼠标操作、定时器到期、控件需要重绘等。
4. 当前事件的处理函数返回后，控制权回到事件循环，循环继续处理其他事件。
5. 应用收到 `quit()` 或 `exit()` 请求后，事件循环结束，`exec()` 返回退出码给 `main()`。

因此，事件循环通常是在等待事件时休眠，而不是不断空转占用 CPU。这个示例中，按钮回调执行 `QThread::sleep(5)` 时，GUI 主线程还没从回调返回，控制权也就没有回到事件循环；事件分发只能等这次回调结束后继续。

参考：[Qt 5.12 `qcoreapplication.cpp`](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/kernel/qcoreapplication.cpp) · [Qt 5.12 `qeventloop.cpp`](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/kernel/qeventloop.cpp)

## 追问：主线程和 `QThread` 各自有事件循环吗？

### 问题

GUI 主线程有事件循环，`QThread` 管理的工作线程也可以有事件循环。这两种事件循环分别由哪个 `exec()` 启动？它们是否是同一个函数、处理同一批事件？

### 回答

GUI 主线程和工作线程可以分别运行自己的事件循环。它们在不同线程中运行，分别处理归属于相应线程的事件。

```text
GUI 主线程：app.exec() → 主线程事件循环
工作线程：  thread.start() → QThread::run() → QThread::exec() → 工作线程事件循环
```

这里有两个同名但不同的 `exec()`：

- `app.exec()` 启动应用的主事件循环，处理 GUI 主线程上的窗口、输入和定时器等事件。
- `QThread::exec()` 启动 `QThread` 所管理的工作线程中的事件循环。Qt 5.12 中，`QThread::run()` 的默认实现会调用 `exec()`；如果重写 `run()` 却没有调用 `exec()`，工作线程就不会运行默认事件循环。

所以，它们不是同一个函数，也不处理同一批事件。它们各自在所属线程里等待和分发事件。

还要区分 `QThread` 对象与它管理的底层线程：`QThread` 对象通常仍属于创建它的线程，例如 GUI 主线程；调用 `thread.start()` 后创建并运行的底层线程则不同。默认的 `run()` 和 `QThread::exec()` 在新线程中执行。

这个 demo 目前没有创建工作线程，只运行了 `app.exec()` 启动的 GUI 事件循环。因此，按钮回调中的 `QThread::sleep(5)` 阻塞的是 GUI 主线程。如果耗时任务放到工作线程执行，GUI 事件循环可以继续处理界面；工作线程中的同步任务返回后，它自己的事件循环也可以继续处理工作线程事件。

参考：[Qt 5.12 `QThread` 源码与说明](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread.cpp)

## 追问：`QThread` 对象和它管理的线程有什么区别？

### 问题

`QThread` 对象通常属于创建它的线程，而调用 `start()` 后运行的底层线程是另一条线程。这两者应该怎样区分？为什么还要把 `Worker` 对象移动到工作线程？

### 回答

可以把 `QThread` 对象理解为**线程管理器**，把它启动的底层线程理解为**实际执行代码的执行流**。两者有关联，但不是同一个概念。

```cpp
QThread thread; // 在 GUI 主线程中创建
thread.start(); // 启动另一条底层线程
```

`QThread` 本身是一个 `QObject`。它在哪条线程中被创建，默认就属于哪条线程；`thread.start()` 则启动一条新的操作系统线程，并在新线程中执行 `QThread::run()`。默认的 `run()` 会调用 `QThread::exec()`，进入该工作线程的事件循环。

因此需要区分：

- `thread.thread()` 表示 `QThread` 这个对象的线程归属，通常是 GUI 主线程。
- `run()` 中的代码运行在 `start()` 启动的新线程中。

常见的 Worker-object 写法会另建一个 `Worker` 对象，再调用 `worker->moveToThread(&thread)`。移动的是 `Worker` 的线程归属，让它的排队槽和事件由工作线程处理；`QThread` 管理对象本身仍留在创建它的线程中。

这也是通常不把耗时工作槽直接写进 `QThread` 子类的原因：`QThread` 子类对象的线程归属一般仍是创建它的线程，排队到这个对象的槽可能就在 GUI 主线程执行。实际工作对象应使用独立的 `QObject`，并将它移动到工作线程。

参考：[Qt 5.12 `QThread` 源码与说明](https://github.com/qt/qtbase/blob/v5.12.12/src/corelib/thread/qthread.cpp)
