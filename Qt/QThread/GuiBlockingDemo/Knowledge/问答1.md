# 问答1：为什么界面会卡住？

## 问题

在这个示例中，点击“阻塞主线程 5 秒”后，窗口会暂时无响应，计数器也停止更新。造成这一现象的原因是什么？

## 回答

原因是耗时操作在 GUI 主线程中执行，阻塞了 Qt 的事件循环。

点击按钮后，Qt 在 GUI 主线程中调用 `GuiBlockingDemo::blockMainThread()`。这个函数调用 `QThread::sleep(5)`，使当前线程睡眠 5 秒。由于调用发生在 GUI 主线程，这 5 秒里主线程无法继续处理界面事件。

Qt 的 GUI 主线程负责处理窗口重绘、用户输入、定时器回调等事件。主线程被阻塞时：

- `QTimer` 的超时回调不能及时执行，所以计数器暂停更新。
- 窗口重绘和鼠标、键盘输入无法及时处理，所以界面看起来无响应。
- `sleep()` 返回、按钮回调结束后，事件循环才能继续处理后续事件，界面随之恢复响应。

## 结合代码看

```cpp
void GuiBlockingDemo::blockMainThread()
{
    statusLabel->setText(QStringLiteral("状态：正在执行耗时操作……"));

    QThread::sleep(5);

    statusLabel->setText(QStringLiteral("状态：操作完成"));
}
```

`QThread::sleep(5)` 不会自动创建或切换到工作线程，它会让**调用它的当前线程**睡眠。本例的按钮回调运行在 GUI 主线程，因此 GUI 主线程被阻塞。

## 为什么“正在执行”状态可能看不到？

调用 `setText()` 会更新标签内容并安排界面重绘，但重绘事件仍要由 GUI 主线程处理。紧接着主线程进入 `sleep(5)`，无法处理这个重绘事件；睡眠结束后，代码又把文本改成“操作完成”。因此通常看不到中间的“正在执行”状态。

## 记忆方式

- GUI 主线程既运行界面事件循环，也执行按钮回调。
- 在 GUI 主线程中同步执行耗时操作，会让事件循环暂时停摆。
- `QThread::sleep()` 阻塞调用它的线程；它本身不会把代码放到工作线程。
- 实际应用中的耗时任务应放到工作线程执行，再通过信号和槽把结果传回 GUI 主线程更新界面。

## 追问：什么是 Qt 的事件循环？

### 问题

Qt 的事件循环是什么？调用 `app.exec()` 后程序会做什么？事件循环与这个示例中的界面卡顿有什么关系？

### 回答

Qt 的事件循环是应用运行时等待并分发事件的机制。它让窗口能够响应鼠标和键盘输入、重绘请求、定时器超时等事件。

在 `main.cpp` 中，`app.exec()` 启动 GUI 主线程的事件循环。概念上，事件循环不断等待事件，再把事件交给对应的控件或回调处理，直到应用退出。例如：

- 用户点击按钮时，Qt 处理鼠标事件，发出按钮的 `clicked` 信号，并调用连接的函数。
- 定时器到期时，Qt 发出 `timeout` 信号，调用更新计数器的函数。
- 窗口需要刷新时，Qt 处理重绘事件并重新绘制界面。

这些事件处理函数和按钮回调默认都在 GUI 主线程执行。一个回调运行时，事件循环要等它返回，才能继续处理其他事件。本示例的按钮回调进入 `QThread::sleep(5)` 后，主线程不能处理定时器、重绘和输入事件；睡眠结束、回调返回后，事件循环才继续工作。

可以把它简化理解为：

```text
启动 app.exec()
    ↓
等待事件 → 分发事件 → 执行对应回调
    ↑                    │
    └──── 回调结束后继续 ┘
```

因此，在 GUI 主线程中执行长时间不返回的代码，会挡住事件循环，让界面暂时无法响应。Qt 的界面更新依赖事件循环处理事件，而不是由程序手动反复刷新。

## 追问：Qt 中常见的主要事件类型有哪些？

### 问题

Qt 中有哪些常见且重要的事件类型？在这个示例中，哪些事件与界面卡顿直接相关？

### 回答

在 Qt Widgets 程序中，常见的事件可以按用途分为以下几类：

- **输入事件**：鼠标点击、移动和滚轮，以及键盘按下和释放等。用户点击按钮时，Qt 处理鼠标事件，按钮随后可能发出 `clicked` 信号。
- **绘制事件**：控件需要显示或刷新时产生，由控件的绘制逻辑处理。窗口被遮挡后重新露出、控件内容变化时，都可能需要重绘。
- **定时器事件**：定时器到期时产生。这个示例中的 `QTimer` 定期触发 `timeout` 信号，用来更新计数器。
- **窗口和控件状态事件**：例如窗口或控件调整大小、移动、显示、隐藏、获得或失去焦点，以及关闭。
- **拖放事件**：用户把文件或其他内容拖入、拖出控件时产生。
- **自定义事件**：程序可以定义并投递自己的事件，用于特定的对象间通知。

在这个示例中，按钮点击相关的输入事件、`QTimer` 的定时器事件，以及界面需要刷新时的绘制事件最相关。它们需要 GUI 主线程的事件循环来处理；主线程被 `QThread::sleep(5)` 阻塞时，这些事件无法及时处理。

需要区分的是，**信号和槽不等同于事件**。例如，`clicked` 是按钮发出的信号；它通常是在 Qt 处理相关输入后发出的。信号可以连接到槽函数，但信号本身不是一种 `QEvent`。

## 追问：鼠标事件、`clicked` 信号和槽函数是什么关系？

### 问题

用户点击按钮时，Qt 中的鼠标事件、按钮发出的 `clicked` 信号，以及与该信号连接的槽函数之间，按什么顺序发生？

### 回答

以鼠标点击按钮为例，整体过程可以概括为：

1. 鼠标在按钮上按下和松开，按钮收到相应的鼠标事件。
2. 按钮判断这次操作符合点击条件后，发出 `clicked` 信号。
3. Qt 根据 `connect()` 建立的连接，调用与这个信号相连的槽函数。

在本示例中，按钮和 `GuiBlockingDemo` 都属于 GUI 主线程。连接使用默认的 `Qt::AutoConnection`，同线程情况下会直接调用槽函数。因此，`clicked` 信号发出后，`blockMainThread()` 会在当前调用过程中执行；其中的 `QThread::sleep(5)` 会阻塞 GUI 主线程。

`clicked` 信号不只由鼠标操作触发，键盘操作等也可以触发按钮点击。信号与槽也不一定总是直接调用：跨线程时，默认连接通常会将调用排队到接收对象所属线程的事件循环中执行。
