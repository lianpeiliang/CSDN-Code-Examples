# 问答 3：fetch 是否需要指定分支

## 提问

运行 `git fetch lan` 时，是否还需要指定 `control` 分支？我之前使用过 `git push lan control` 和 `git pull lan control`，当时需要写出 `control`，因为它不是默认分支。我想知道，`fetch` 是否也必须明确指定这个分支。

## 回答

`git fetch lan` 会按照本地为远端 `lan` 配置的获取规则来获取更新。通常，这些规则会跟踪远端的多个分支，因此运行该命令时不一定要单独写出 `control`。如果配置跟踪了远端的 `control` 分支，fetch 后本地的远程跟踪分支 `lan/control` 会更新。这个操作不要求 `control` 是远端的默认分支，也不会自动改变当前本地分支或工作区。

在 `git push lan control` 和 `git pull lan control` 中写出 `control`，是为了明确指定要操作的分支。`git push lan control` 会将本地 `control` 分支推送到 `lan` 上对应的分支；`git pull lan control` 会获取 `lan` 上的 `control` 分支，并将其整合到当前本地分支。

## 疑惑点梳理

1. **`lan` 和 `control` 分别是什么**
   `lan` 是本地配置的远端名称，通常关联一个远程仓库地址。`control` 是远端上的分支名。`lan/control` 表示本地记录的远端 `lan` 上的 `control` 分支。

2. **默认分支和远端名称、分支名称的关系**
   默认分支也是一个分支，例如 `main` 或 `control`。它不会改变 `lan` 是远端名称这一点，也不会让其他分支无法被操作。命令中显式写出 `control`，就可以指定该分支。

3. **为什么有时命令要写 `control`**
   `git push lan control` 和 `git pull lan control` 显式指定了目标分支。省略分支时，命令会依赖当前分支的上游配置或相关 Git 配置，因此在没有相应配置时，写出分支名更明确。

4. **`git fetch lan` 如何选择分支**
   它依据本地配置的 fetch 规则获取更新，常见配置会跟踪该远端的多个分支。若只想针对某个分支操作，可以显式指定分支或检查远端跟踪配置。`fetch` 更新的是本地的远程跟踪信息，不会自动把提交合并进当前分支。

## 命令对照

| 命令 | 作用 |
|---|---|
| `git fetch lan` | 按配置获取远端 `lan` 的更新，通常会更新多个远程跟踪分支 |
| `git push lan control` | 将本地 `control` 分支推送到远端 `lan` |
| `git pull lan control` | 获取远端 `lan` 的 `control` 分支，并整合到当前本地分支 |

## 补充问答：`git fetch lan` 获取哪些分支

### 提问

如果本地仓库有 A、B、C 等分支，运行 `git fetch lan` 时，Git 是否会根据本地分支与远端分支的对应关系，分别获取远端的 A、B、C 分支？是否通常会把这些分支的更新都获取到本地？

### 回答

`git fetch lan` 通常不是根据当前所在的本地分支来选择远端分支，而是按照远端 `lan` 的 fetch 配置获取更新。常见配置会跟踪远端的多个分支，因此一次 fetch 通常会更新本地的 `lan/A`、`lan/B`、`lan/C` 等远程跟踪分支。

这些更新会记录在本地对应的远程跟踪分支上，不会自动合并到本地 A、B、C 分支，也不会修改工作区。实际获取哪些分支取决于 `lan` 的 fetch 配置，常见配置通常会跟踪所有远端分支。
