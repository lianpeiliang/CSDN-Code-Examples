# 问答 6：日常协作中的 merge 与 rebase

## 我的理解

在日常工作中，我很少使用 `rebase`，通常使用 `merge`。常见的情况是，同事先在某个分支上修改并提交代码，我也在本地完成修改并提交。之后通过拉取远端更新，将双方的提交自动合并。如果双方修改没有冲突，Git 可以完成合并；如果发生冲突，则需要检查并处理相关文件。

## 回复

这是常见的协作方式。通过 `pull` 获取远端提交并整合到本地时，通常由 `merge` 完成。

虽然示例中使用了 `feature` 和 `main` 两个分支，但本地分支与远端跟踪分支也可能从共同的旧提交开始，各自包含新的提交。此时 Git 需要整合两边的历史。使用 `merge` 会记录这次整合，因此日常采用合并工作流时，不需要经常使用 `rebase`。

## 补充问答：解决冲突后完成合并

### 提问

如果 `git merge` 出现冲突，手动修改文件解决冲突后，通常要运行什么命令告诉 Git 冲突已解决，并完成这次合并？

### 回答

解决冲突并保存文件后，运行 `git add <文件>` 将已解决的文件标记为解决状态，再运行 `git commit` 完成合并。

### 补充说明

也可以运行 `git merge --continue` 继续完成正在进行的合并。
## 补充问答：`git add` 的作用

### 提问

运行 `git add <文件>` 后，修改会被提交到远端，还是会先放入本地的暂存区？

### 回答

`git add <文件>` 会将文件的修改放入本地暂存区。

### 注释

回答正确。`git add` 只是把修改放入暂存区，还没有创建 commit，也没有推送到远端。之后运行 `git commit` 才会将暂存内容保存为本地提交，运行 `git push` 才会把本地提交发送到远端仓库。
## 补充问答：`git commit` 后提交保存在哪里

### 提问

运行 `git commit` 后，修改会保存到哪里？远端仓库会自动同步更新吗？

### 回答

`git commit` 后，修改会保存为本地仓库中的提交。远端仓库不会自动更新，需要运行 `git push` 将本地提交发送到远端。

### 注释

Git 的常见三步流程如下：

1. `git add <文件>`：将修改放入本地暂存区。
2. `git commit`：将暂存区中的修改保存为本地仓库中的提交。
3. `git push`：将本地提交发送到远端仓库。

```text
工作区 --git add--> 暂存区 --git commit--> 本地仓库 --git push--> 远端仓库
```
