# 问答1：对象的构造、析构与输出顺序

## 提问

根据当前 `main.cpp`，先不运行程序，判断控制台会按什么顺序输出，并写出完整输出。

```cpp
int main() {
    std::cout << "Entering scope\n";
    {
        Worker worker("worker");
        std::cout << "Working\n";
    }
    std::cout << "Left scope\n";
}
```

其中，`Worker` 的构造函数输出对象名称和 `constructed`，析构函数输出对象名称和 `destroyed`。

## 我的回答（书面化）

程序首先输出 `Entering scope`。随后创建局部对象 `worker`，调用其构造函数并输出 `worker constructed`。接着输出 `Working`。离开内部作用域时，`worker` 被销毁，析构函数输出 `worker destroyed`。最后，程序输出 `Left scope`。

完整输出如下：

```text
Entering scope
worker constructed
Working
worker destroyed
Left scope
```

## 批注

回答中的执行顺序正确：先输出进入提示，再构造对象、输出工作提示、析构对象，最后输出离开提示。

原回答用“构造”和“析构”概括了对应过程。若题目要求写出完整的控制台输出，应使用代码实际打印的 `worker constructed` 和 `worker destroyed`，并按换行符逐行列出。

## 追问：为什么不需要 `delete`，对象也会被销毁？

### 提问

`worker` 为什么会在输出 `Left scope` 之前被销毁？代码里没有写 `delete`，是谁触发了析构函数？

### 我的回答（书面化）

`worker` 是在内部大括号作用域中创建的局部对象，通常存放在栈上。它的生命周期与这个作用域相关：当程序离开该作用域时，`worker` 会被自动销毁，并调用析构函数，因此不需要手动使用 `delete`。

### 批注

回答正确，已经抓住了作用域结束与局部对象自动析构之间的关系。

更准确的说法是：`worker` 是具有自动存储期的局部对象。“存放在栈上”是常见的实现方式；离开作用域时自动销毁对象，则是 C++ 的语言规则。编译器会安排相应的清理代码，在正常离开该作用域时调用析构函数。

`delete` 用于销毁由匹配的 `new` 表达式创建的对象并释放对应存储空间，不应对这里的局部对象使用 `delete`。

## 追问：同一作用域内的对象按什么顺序析构？

### 提问

如果在同一个作用域内创建两个对象，离开该作用域时，`first` 和 `second` 谁先析构？

```cpp
{
    Worker first("first");
    Worker second("second");
    std::cout << "Working\n";
}
```

### 我的回答（书面化）

`second` 会先析构，随后才是 `first`。同一作用域内的局部对象按照构造完成顺序的逆序销毁：后构造的对象先析构，先构造的对象后析构。

### 批注

回答正确。在这段代码中，`first` 先构造，`second` 后构造，所以析构顺序是 `second`、`first`。

“从下往上析构”可以用来记忆这个例子，但准确的判断依据是对象构造完成的先后顺序，而不是源代码行的位置。离开作用域时，程序不会从下往上重新执行其中的语句。

完整输出为：

```text
first constructed
second constructed
Working
second destroyed
first destroyed
```

## 追问：通过 `return` 提前离开函数时，对象会析构吗？

### 提问

如果通过 `return` 提前离开函数，`worker` 还会自动析构吗？

```cpp
void doWork() {
    Worker worker("worker");
    std::cout << "Working\n";
    return;
}
```

### 我的回答（书面化）

`worker` 仍然会自动析构。执行 `return` 会使程序离开当前函数的作用域，因此，作为该作用域内具有自动存储期的局部对象，`worker` 会在函数返回调用者之前被销毁。

### 批注

回答正确。自动析构不要求程序一定执行到右大括号：通过 `return` 提前离开作用域时，已经构造完成的局部对象也会被自动销毁。

调用 `doWork()` 后，输出为：

```text
worker constructed
Working
worker destroyed
```

## 追问：`new` 创建的对象会随局部指针离开作用域而销毁吗？

### 提问

把创建方式改为 `new` 后，函数结束时，`new` 创建的 `Worker` 对象还会自动析构吗？为什么？

```cpp
void doWork() {
    Worker* worker = new Worker("worker");
    std::cout << "Working\n";
}
```

### 我的回答（书面化）

这里的 `Worker` 对象由 `new` 动态创建，通常存放在堆上。它不会在函数结束时随局部指针变量一起自动销毁。在这段使用原始指针管理对象的代码中，需要显式执行 `delete worker`，以调用对象的析构函数并释放对应的存储空间。

### 批注

回答正确。这里需要区分局部指针变量 `worker` 和它指向的 `Worker` 对象：指针变量具有自动存储期，离开函数作用域时其生命周期结束；`new` 创建的对象具有动态存储期，不会因为这个原始指针变量的生命周期结束而被销毁。原代码没有释放该对象，会造成内存泄漏。

可以这样补上释放操作：

```cpp
void doWork() {
    Worker* worker = new Worker("worker");
    std::cout << "Working\n";
    delete worker;
}
```

“需要手动 `delete`”适用于这里直接管理资源的写法。后续使用 `std::unique_ptr` 等资源管理对象时，可以由管理对象自动执行释放操作，无需手写 `delete`。

## 追问：`delete worker` 销毁的是指针变量还是对象？

### 提问

在下面的代码中，`delete worker` 销毁的是指针变量 `worker`，还是它指向的 `Worker` 对象？

```cpp
Worker* worker = new Worker("worker");
delete worker;
```

### 我的回答（书面化）

`delete worker` 销毁的是指针变量 `worker` 所指向的 `Worker` 对象。

### 批注

回答正确。对于这里由 `new` 创建的对象，执行 `delete worker` 会调用该对象的析构函数，并释放它占用的动态存储空间。

指针变量 `worker` 本身仍然存在，它的生命周期并不会因为这次 `delete` 而结束。需要分别理解“指针变量的生命周期”和“它所指向对象的生命周期”。

## 追问：执行 `delete` 后，指针会自动变成 `nullptr` 吗？

### 提问

执行 `delete worker` 后，`worker` 会自动变成 `nullptr` 吗？

### 我的回答（书面化）

不会。执行 `delete worker` 后，指针变量不会被自动置为空，仍保留原来的地址值。但该地址处的 `Worker` 对象已经被销毁，存储空间也已释放，因此 `worker` 成为悬空指针。

### 批注

回答正确。指针没有自动变成 `nullptr`，不代表它指向的对象仍然有效。此时不能通过 `worker` 访问已销毁的对象，也不能再次用它释放同一块存储空间，否则会产生未定义行为。

可以在释放后显式将该指针置空：

```cpp
delete worker;
worker = nullptr;
```

置空只是修改这个指针变量的值，不会延长或恢复被销毁对象的生命周期。如果还有其他指针指向同一对象，它们也不会随之自动置空。

## 追问：对 `nullptr` 执行 `delete` 是否安全？

### 提问

下面最后一次 `delete` 安全吗？会不会再次调用 `Worker` 的析构函数？

```cpp
Worker* worker = new Worker("worker");
delete worker;
worker = nullptr;

delete worker;
```

### 我的回答（书面化）

我尚不确定对 `nullptr` 执行 `delete` 是否安全，但我认为最后一次 `delete` 不会再次调用 `Worker` 的析构函数。

### 批注

关于析构函数的判断正确。对空指针执行 `delete` 是 C++ 允许的安全操作，不会销毁任何对象，也不会调用对象的析构函数。因此，最后一次 `delete worker` 是安全的。

第一次 `delete worker` 已经销毁了对象；随后 `worker = nullptr` 将指针置空，所以最后一次 `delete` 操作的目标是空指针。整个例子只会调用一次 `Worker` 的析构函数。

需要区分空指针与悬空指针：对空指针执行 `delete` 是安全的；如果省略 `worker = nullptr`，最后一次 `delete worker` 就会重复释放已经释放的存储空间，产生未定义行为。

## 追问：提前 `return` 会导致动态创建的对象泄漏吗？

### 提问

调用 `doWork(true)` 时，会发生内存泄漏吗？为什么？

```cpp
void doWork(bool stop) {
    Worker* worker = new Worker("worker");

    if (stop) {
        return;
    }

    delete worker;
}
```

### 我的回答（书面化）

当 `stop` 为 `true` 时，这段代码会发生内存泄漏。

### 批注

判断正确，还可以补充原因：`new` 已经创建了 `Worker` 对象，但程序随后进入 `if` 分支并执行 `return`，跳过了函数末尾的 `delete worker`。

函数返回时，局部指针变量 `worker` 的生命周期结束，但它所指向的动态对象不会因此自动析构。这段代码没有保留其他指针来管理该对象，对象占用的存储空间也没有被释放，因此发生内存泄漏。

这个例子说明，手动管理资源时，必须考虑每一条退出路径上的释放操作。

## 追问：怎样避免提前返回造成的内存泄漏？

### 提问

如果不需要动态分配对象，怎样改写这个函数，使它即使提前 `return`，也能自动销毁 `Worker`，而且不用写 `delete`？

### 我的回答（书面化）

可以直接在函数作用域内创建一个具有自动存储期的局部对象，替代原来的 `new` 和原始指针：

```cpp
void doWork(bool stop) {
    Worker worker("worker");

    if (stop) {
        return;
    }
}
```

### 批注

改写正确。`worker` 的生命周期与当前函数作用域关联。无论 `stop` 为 `true` 时提前执行 `return`，还是 `stop` 为 `false` 时正常执行到函数末尾，离开作用域时都会自动调用其析构函数，不需要手动释放。

这里不再动态创建 `Worker` 对象，从而消除了原先遗漏 `delete` 的问题。如果确实需要动态分配，可以进一步使用 `std::unique_ptr` 等资源管理对象，将动态对象的释放与管理对象的生命周期绑定起来。

## 追问：智能指针与它管理的对象分别具有什么存储期？

### 提问

`std::unique_ptr` 可以管理动态创建的对象，在自身析构时自动销毁所管理的对象。下面代码中的智能指针变量 `worker` 本身与它管理的 `Worker` 对象，分别具有自动存储期还是动态存储期？

```cpp
#include <memory>

void doWork(bool stop) {
    auto worker = std::make_unique<Worker>("worker");

    if (stop) {
        return;
    }
}
```

### 我的回答（书面化）

局部智能指针变量 `worker` 具有自动存储期，而它管理的 `Worker` 对象具有动态存储期。

### 批注

回答正确。这里的 `auto` 推导出的类型是 `std::unique_ptr<Worker>`，而不是原始指针类型 `Worker*`。`std::make_unique` 动态创建一个 `Worker` 对象，并返回拥有该对象的智能指针。

需要区分管理对象和被管理对象的存储期：使用智能指针并不会把动态创建的 `Worker` 对象变成具有自动存储期的对象。

## 追问：为什么智能指针能在离开作用域时释放动态对象？

### 提问

原始指针变量也可以具有自动存储期，为什么它离开作用域时不会释放所指向的对象，而 `std::unique_ptr` 可以？

### 我的回答（书面化）

`std::unique_ptr` 负责管理它所拥有的对象。当 `unique_ptr` 自身被析构时，它会自动销毁所管理的对象。这利用了 RAII 的思想，将被管理资源的释放与管理对象的生命周期关联起来。

### 批注

理解正确。原始指针只保存地址，不会在自身生命周期结束时自动销毁所指向的对象。`std::unique_ptr` 则是具有资源管理行为的类对象，它的析构函数会在拥有对象时调用删除器。

对于这里的 `std::unique_ptr<Worker>`，默认删除器执行相应的 `delete` 操作：既调用 `Worker` 的析构函数，也释放对象占用的动态存储空间。因此，不仅要理解“对象被析构”，还要理解其存储空间也得到了释放。

在当前例子中，清理过程为：离开作用域 → 析构局部 `unique_ptr` → 调用删除器 → 析构 `Worker` 并释放其存储空间。这正是利用具有自动存储期的管理对象来管理动态资源的 RAII 用法。

## 追问：`std::unique_ptr` 可以复制吗？

### 提问

下面这段代码能编译通过吗？请从独占所有权的角度考虑。

```cpp
auto first = std::make_unique<Worker>("worker");
auto second = first;
```

### 我的回答（书面化）

这段代码不能编译通过。`first` 独占所管理的 `Worker` 对象的所有权，只能将所有权转移给另一个智能指针，不能通过复制让两个 `unique_ptr` 共同拥有同一个对象。

### 批注

判断正确。第二行试图复制构造一个 `std::unique_ptr<Worker>`，但 `unique_ptr` 的复制构造函数被删除，因此编译器会拒绝这段代码。它支持通过移动操作转移所有权。

“不能共用”应准确理解为不能让两个 `unique_ptr` 同时拥有同一个对象，而不是不允许其他代码访问这个对象。例如，可以通过 `first.get()` 取得不拥有对象的原始指针进行临时访问，但该指针不能负责释放对象，也不能延长对象的生命周期。

## 追问：移动后，两个 `unique_ptr` 分别处于什么状态？

### 提问

执行第二行后，`first` 和 `second` 分别处于什么状态？

```cpp
auto first = std::make_unique<Worker>("worker");
auto second = std::move(first);
```

### 我的回答（书面化）

执行所有权转移后，`second` 接管原来由 `first` 管理的 `Worker` 对象，而 `first` 成为不再管理任何对象的空 `unique_ptr`。

### 批注

判断正确。这里通过移动构造将所有权从 `first` 转交给 `second`。转移完成后，`first == nullptr`，而 `second` 指向并拥有原来的 `Worker` 对象。

`first` 这个智能指针对象本身仍然存在，可以被重新赋予新的所有权；它不再拥有原来的对象，因此不能通过它访问原对象，也不会在自身析构时释放原对象。

这里移动后源指针为空，是 `std::unique_ptr` 的明确保证，不能据此认为所有 C++ 类型在移动后都会自动清空。

## 追问：转移所有权时会创建新的 `Worker` 对象吗？

### 提问

执行下面的第二行时，会再次调用 `Worker` 的构造函数、创建一个新的 `Worker` 对象吗？为什么？

```cpp
auto first = std::make_unique<Worker>("worker");
auto second = std::move(first);
```

### 我的回答（书面化）

不会。第二行既不会创建新的 `Worker` 对象，也不会调用原对象的析构函数。它只是将现有 `Worker` 对象的所有权从 `first` 转移给 `second`。

### 批注

回答正确。第一行创建了 `Worker` 对象；第二行移动构造的是 `std::unique_ptr<Worker>` 类型的智能指针对象 `second`，而不是 `Worker` 对象。

这里需要区分智能指针的移动构造与被管理对象的构造：原来的 `Worker` 对象继续存在，地址没有改变，也不会因为所有权转移而调用它的构造函数、移动构造函数或析构函数。

`std::move(first)` 本身是类型转换，用来允许后续选择移动操作；真正的所有权转移由这里的 `unique_ptr` 移动构造函数完成。

## 追问：移动赋值时，目标智能指针原来管理的对象会怎样？

### 提问

执行最后一行时，原来由 `second` 管理的 B 对象会怎样？

```cpp
auto first = std::make_unique<Worker>("A");
auto second = std::make_unique<Worker>("B");

second = std::move(first);
```

### 我的回答（书面化）

我认为 B 对象会被析构，原因是它不再由任何 `unique_ptr` 管理。

### 批注

B 会被析构，这个结果判断正确，但原因需要修正：`unique_ptr` 的移动赋值操作会主动释放目标智能指针原来拥有的对象，并接管源智能指针的所有权。对于本例，释放 B 时会调用其析构函数并释放对应的动态存储空间。

关键是有资源管理操作实际执行了释放，而不是对象在失去管理者后会自行销毁。动态对象如果只是失去所有可访问它的指针，而没有被释放，就会造成内存泄漏。

最后一行执行完成后，B 已被销毁，`second` 拥有 A，`first` 为空。A 不会因为这次所有权转移而被重新构造或析构。

## 追问：单独调用 `std::move` 会转移所有权吗？

### 提问

只执行一次 `std::move(first)`，没有用它构造或赋值给其他智能指针，`first` 会失去 A 的所有权吗？

```cpp
auto first = std::make_unique<Worker>("A");
std::move(first);
```

### 我的回答（书面化）

我认为 `first` 会失去 A 的所有权。我的推断是，`std::move(first)` 会创建一个匿名的 `unique_ptr` 对象并将所有权转移给它，随后匿名对象被析构，进而销毁 A。

### 批注

这个判断需要修正。`std::move` 本身只是类型转换，产生一个引用原对象、可用于移动操作的表达式，不会创建新的 `unique_ptr` 对象，也不会自动调用移动构造函数或移动赋值运算符。

因此，第二行没有创建匿名智能指针，没有转移所有权，也没有销毁 A。执行完成后，`first` 仍然拥有 A。

对比之前的代码：

```cpp
auto second = std::move(first);
```

这一行明确创建了 `second`，并调用 `unique_ptr` 的移动构造函数，才真正完成所有权转移。不能把 `std::move` 的类型转换与随后可能发生的移动操作视为同一件事。

如果显式创建一个匿名智能指针，推断中的释放过程才会发生：

```cpp
std::unique_ptr<Worker>{std::move(first)};
```

这里会移动构造一个临时 `unique_ptr` 并接管 A；在该完整表达式结束时，也就是这条语句的分号处，临时智能指针析构，销毁 A 并释放其存储空间。此时 `first` 为空。
