# 问答4：成员初始化与构造函数体内赋值

## 提问：进入构造函数体时，成员是否已经构造？

对比以下两种写法，成员变量都是 `std::string name_;`。

```cpp
// 写法一：成员初始化列表
explicit Worker(std::string name)
    : name_(std::move(name)) {
}
```

```cpp
// 写法二：在构造函数体内赋值
explicit Worker(std::string name) {
    name_ = std::move(name);
}
```

第二种写法中，执行 `name_ = std::move(name);` 之前，`name_` 是否已经被构造了？

## 我的回答（书面化）

我认为，在执行这条赋值语句之前，成员变量 `name_` 已经完成构造。

## 批注

判断正确。进入构造函数体之前，成员初始化阶段已经完成。对于这里没有默认成员初始化器、也没有在成员初始化列表中指定初始化方式的 `std::string name_`，会调用 `std::string` 的默认构造函数，创建一个空字符串。

随后执行函数体中的 `name_ = std::move(name);`，是在给一个已经存在的字符串对象赋值，调用的是 `std::string` 的移动赋值运算符，不是移动构造函数。

两种写法的区别如下：

| 写法 | `name_` 的处理过程 |
| --- | --- |
| `: name_(std::move(name))` | 直接通过移动构造创建 `name_` |
| 函数体内 `name_ = std::move(name);` | 先默认构造 `name_`，再执行移动赋值 |

初始化列表能直接表达成员的初始状态，避免先默认构造再赋值。对于当前字符串例子，不应仅凭多一个步骤就认定有明显性能差异；默认构造空字符串通常很轻量，也不意味着一定额外申请堆内存。

## 追问：成员加上 `const` 后，两种写法都能编译吗？

### 提问

如果把成员改为 `const std::string name_;`，下面两种写法还能都通过编译吗？为什么？

```cpp
// 写法一：成员初始化列表
explicit Worker(std::string name)
    : name_(std::move(name)) {
}
```

```cpp
// 写法二：在构造函数体内赋值
explicit Worker(std::string name) {
    name_ = std::move(name);
}
```

### 我的回答（书面化）

写法一可以通过编译，写法二不可以。成员加上 `const` 后，可以在构造时初始化，但不能在初始化完成后再对它赋值。

### 批注

回答正确。写法一在成员初始化列表中直接构造 `name_`，此时是在建立它的初始状态，因此允许使用 `std::string` 的移动构造函数初始化这个 `const` 成员。

写法二进入构造函数体之前，`const std::string name_` 已经默认构造为空字符串。随后执行 `name_ = std::move(name);`，是在尝试修改一个已经初始化完成的 `const` 对象，无法调用需要修改目标对象的字符串赋值运算符，所以不能编译。

`std::move` 不会绕过目标对象的 `const` 限制。这里需要区分的是初始化和赋值，而不是赋值时有没有使用 `std::move`。
